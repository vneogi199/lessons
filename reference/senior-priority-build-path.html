Learning homeBuild and evidence workbook

Build one service you can explain under pressure

This path covers AWS/Terraform, database reliability, AI evaluation, Python service engineering, infrastructure operations, and Node/GraphQL. It also covers architectural impact and customer-facing delivery. It is tailored to a senior engineer; it does not claim that named employers use these exact exercises.

Use a document assistant as the shared project. It accepts a document, processes it through a durable job, answers permitted questions with citations, and routes uncertain results to review. Begin with the existing Support Copilot. That supplied application is a local Python/SQLite CLI. The FastAPI/PostgreSQL/cloud version below is a build assignment, not an already connected deployed system.

At 6–8 hours per week, take one section at a time. Read the explanation, predict the worked failure, use the linked lab, and record evidence. Repeat a section if you cannot explain its result. Start with AWS design, database reliability and evaluations; defer the optional Node boundary until the core works.

1. AWS and Terraform: own the path from request to recovery

A subnet is a network location; a route determines where packets go; a security group restricts traffic; an IAM policy restricts service actions. These controls do not replace one another. A private database can still be exposed through an overly privileged application.

Think of an office: routes are corridors, security groups are doors, and IAM grants permission to use particular equipment. The worker should read its input objects and publish processing results, not administer the account.

For the target service, draw an HTTPS ingress, private API/worker tasks, private RDS, object storage and a queue. Give API and worker separate roles. Decide how private workloads reach model providers: reviewed egress or supported private endpoints. Account for NAT and endpoint costs. Do not add a default route merely to make a failed call succeed.

Terraform describes intended resources; its state maps declarations to actual objects. Review both configuration and the saved plan. Separate environment identities and state. A workspace name alone is not an authorization boundary. Protect state and plans: marking a value sensitive can hide display without removing it from stored artifacts. See Terraform sensitive-data handling.

  1. Open the existing AWS/Terraform lab. Explain its private routes, restricted roles, state storage and restore procedure. It provisions a foundation, not the entire assistant.
  2. Write the missing application resources in your plan: API ingress, image source, worker, queue permissions, restricted database user and secret access. Choose EC2 or ECS first; justify EKS only if its operating cost is useful.
  3. Define dev/staging/prod isolation, short-lived deployment identity, image digest, secret rotation, migration ordering and plan approval. Keep provider credentials out of files.
  4. On an approved future deployment, test allowed and denied paths, restart one task, rotate a synthetic secret, and restore a test database to a new private instance.
  5. Record resource IDs privately, measured recovery time, expected data-loss bound, cost by service and cleanup ownership.

Worked failure: the API task is healthy but model calls time out. Check DNS, route, egress controls, provider access and deadline evidence. Restarting the application will not create a missing network path. AWS's reliability guidance calls for testing recovery, not merely configuring it.

Interview: what cloud infrastructure did you personally own?

Name the resources, policies, deployment decisions and recovery checks you implemented. Distinguish a provisioning contribution from operating the full service. Show the plan review and one failure investigation.

2. PostgreSQL and distributed reliability: preserve one business invariant

Choose the invariant: one document revision creates at most one published result, even if its processing message arrives repeatedly. A transaction can atomically save a document revision and an outbox event. It cannot, by itself, atomically commit an unrelated broker or model-provider operation.

A simple analogy is writing a parcel and its dispatch note in the same ledger. The messenger can deliver the note twice. The receiver needs a durable record of what it already processed.

Give each tenant/document/revision a unique identity. Store an idempotency key with a payload hash; the same key with changed input is a conflict. Publish with a stable event ID. Commit the consumer's inbox record and local effect together. Acknowledge only after commit. For external effects, use provider idempotency or reconcile uncertain outcomes.

  1. Read the outbox and saga lab. Predict crashes before source commit, after broker publish, and after consumer commit but before acknowledgement.
  2. Implement the PostgreSQL schema in an approved test database. Define uniqueness, foreign keys, revision ordering and retention. A single-process SQLite fixture does not prove PostgreSQL concurrency.
  3. Run two sessions against the same document revision. Compare a conditional update with a read-then-write implementation. Inspect lock waits and the final invariant.
  4. Use EXPLAIN (ANALYZE, BUFFERS) on safe representative SELECTs. Measure rows, scans, sorting and buffer work before adding indexes. ANALYZE executes the statement.
  5. Kill/restart the relay or worker at each durable boundary. Confirm recoverable pending work, deduplicated effects, conflict rejection and visible quarantine.

Read Committed and Repeatable Read provide different snapshots; neither automatically encodes every multi-row invariant. Serializable can reject unsafe concurrent executions, so the caller needs a bounded whole-transaction retry. Lock rows consistently, keep transactions short and avoid provider calls while holding locks. Consult PostgreSQL isolation semantics.

Worked failure: version 8 finishes after version 9. Both messages have distinct valid IDs, so duplicate suppression alone does not help. Publish only if the expected revision still matches; otherwise mark version 8 obsolete. Use expand-contract migrations and bounded backfills so old and new code can coexist during rollout.

Interview: does the outbox give exactly-once delivery?

No. It closes the source database dual-write gap. The relay can repeat messages. Durable consumer deduplication, transactional effects and external reconciliation determine the business outcome.

3. AI evaluation: decide whether a change deserves release

A test set is a collection of representative tasks with reviewed expected behaviour. It is not just a list of easy questions. Include exact facts, paraphrases, conflicting policies, stale documents, missing evidence, denied documents, prompt injection and dependency failures.

For each case, store source version, access scope, relevant evidence IDs, answer rubric and abstention expectation. Keep related document versions and near-duplicates in the same split. Develop prompts on development data, select changes on validation data, and reserve test data for the frozen release decision.

Worked example: ten answerable questions contain twenty labelled relevant passages. Retrieval finds sixteen, so pooled passage recall is 16/20 = 80%. That does not imply 80% answer accuracy. A retrieved passage can be ignored, misread or cited for an unsupported claim. Report case-level averages separately if used; name the denominator.

  1. Run or inspect the existing offline evaluation. Its synthetic cases validate mechanics, not your production assistant's quality.
  2. Write an initial human-reviewed dataset with the slices above. Use synthetic or authorized redacted inputs; a fixed count is not proof of representativeness.
  3. Score retrieval recall/precision, answer correctness, claim support, abstention, permissions, latency and cost separately. Count timeouts and invalid output rather than dropping them.
  4. Compare baseline and candidate on the same cases, model settings and source snapshot. Repeat stochastic runs and report uncertainty; repeated runs of one case are not new independent cases.
  5. Calibrate any LLM judge against human labels. Review false passes, rubric ambiguity, disagreement and prompt/model-version changes. Keep deterministic permission and schema checks outside the judge.
  6. Add a CI report that blocks release on explicit critical failures and agreed quality/cost/latency regressions. Run provider-dependent evaluations only in a controlled environment with a budget.

Do not treat unknown token pricing as zero. Separate successful-call latency from overall success, queue delay and failures. A faster candidate that abstains on everything is not automatically better. Use trajectory evaluation when tools and multi-turn decisions matter, and stage percentiles for performance analysis.

Interview: how did you know your RAG change improved the product?

Describe the dataset and its limitations, unchanged baseline, measured slices, human review and release gates. Production users demonstrate adoption, not automatically correctness or a rigorous evaluation process.

4. Python service engineering: bound work and handle cancellation

Async code can overlap waiting. It does not make CPU-heavy parsing disappear. An event loop can serve other tasks only when work yields control. Blocking I/O or CPU work on that loop delays unrelated requests.

Imagine a receptionist who can accept another call while waiting for a reply. If the receptionist starts doing a long calculation without stopping, every caller waits. Use async clients for async I/O, bounded thread offload for suitable blocking I/O, and a process/worker design for substantial CPU work.

A request deadline must include queueing, connection-pool wait, calls and retries. Give each dependency only the remaining budget. Limit both active operations and queued requests. A semaphore bounds active calls but an unbounded set of waiting tasks can still exhaust memory.

  1. Trace timeout and cancellation propagation through request, task group and client. Clean up in finally blocks and do not swallow cancellation. See Python task cancellation.
  2. Build a bounded admission queue and separate dependency concurrency limits. Reject overload with a documented retry policy rather than spawning unlimited work.
  3. Test client disconnect, dependency timeout, partial parallel failure and shutdown during work. Use events/barriers in tests where possible instead of timing-sensitive sleeps.
  4. Move durable ingestion to the worker. FastAPI background tasks are not a replacement for persisted jobs that must survive a crash.
  5. Profile a representative workload. Separate CPU, serialization, database/pool waits and model latency. Optimize the measured bottleneck, then repeat correctness and load checks.

Worked failure: cancelling an await on a thread does not forcibly stop that thread's database write. Use driver deadlines and an outcome-reconciliation policy. A timeout is evidence that the caller stopped waiting, not proof that the side effect did not happen.

For load evidence, record offered load, achieved throughput, concurrency, errors, p50/p95/p99, queue age and resource limits. Explain the generator and test duration. Do not infer production capacity from one laptop or from latency that excludes failures. Continue with the FastAPI profiling lessons and bounded production optimization.

Interview: why did adding workers make the service worse?

Each process may add its own connection pool and provider concurrency. Total demand can exceed shared capacity. Inspect aggregate pools, queue delay, throttling and retry amplification before scaling again.

5. Operations: diagnose an incident and prevent recurrence

A readiness probe asks whether the pod should receive traffic. A liveness probe asks whether restarting this container can help. A startup probe gives initialization time before the other probes take over. An unavailable shared database should not normally trigger every container to restart. See Kubernetes probe semantics.

Resource requests inform scheduling; limits constrain consumption. Too little CPU can increase throttling and tail latency. A memory limit can lead to termination. HPA scaling cannot repair a fixed downstream quota. Set maximum replicas together with pool sizes and provider limits.

  1. Port the already-working service to a reviewed Kubernetes deployment only when this learning goal is relevant. Supply resource requests/limits, probes, non-root settings, configuration and graceful termination.
  2. Trace API → queue → worker → database/model. Use bounded labels and redact sensitive payloads. Define request success and an SLO window before setting alerts.
  3. Inject one safe staging failure: block a synthetic dependency or deploy a deliberately unready image. Record detection, triage, mitigation and recovery times.
  4. Inspect events, rollout state, restart reason, CPU/memory, pool waits and dependency spans. Roll back the application only if its schema remains compatible.
  5. Write a blameless incident report with contributing causes, a regression test, an alert/runbook improvement and an owner.

Worked failure: readiness fails, so rollout stalls. The previous healthy pods may still be serving, depending on rollout settings and capacity. Inspect availability before declaring an outage. Conversely, “all pods ready” does not prove permission-aware answers work. Test the user workflow too.

For a fictional 99.9% request-success SLO over 100,000 eligible requests, the budget is 100 failures. Twenty failures consume 20% of that budget. Define eligible requests carefully. Security violations need their own release/incident policy rather than being hidden inside an availability average. Use Datadog practice or existing OpenTelemetry/Grafana material; one verified telemetry path is enough.

Interview: what changed after the incident?

Show the specific failure mechanism, mitigation and preventive change. Distinguish reducing recurrence from merely adding a noisy alert. Include verification and remaining risk.

6. TypeScript and GraphQL: add one useful boundary

Keep FastAPI responsible for ingestion and AI work. Add an optional TypeScript backend-for-frontend that combines document status and author/reviewer information for React. Do not duplicate the whole service simply to list another technology.

Define Query.documents(first, after) and nested owner fields. A naive implementation fetches a page, then fetches one owner per document: one plus N calls. A request-scoped loader batches owner IDs. Its result array must preserve input-key order and missing positions. See GraphQL.js batching guidance.

  1. Write TypeScript boundary types and runtime input validation. Types alone do not validate JSON or GraphQL authorization.
  2. Use a verified actor in request context; never accept tenant identity as proof of permission. Scope every repository call and loader to that actor.
  3. Port the behaviour of the existing Python GraphQL lab into your approved Node framework. That supplied lab is Python, not evidence of a completed TypeScript service.
  4. Implement bounded pagination, per-request batching, deadline propagation and masked errors. Set query depth/cost, alias and body limits; a small page size alone does not bound repeated aliases.
  5. Test unordered repository results, missing owners, cross-tenant IDs, denied mutations and dependency timeout. Measure backend call counts instead of assuming DataLoader removed N+1.
  6. Package the Node service with pinned dependencies, tests, graceful shutdown and a reviewed deployment plan. Add it only if the target role benefits from this evidence.
Requested owner IDs: [7, 3, 9]
Repository returns: [{id: 3}, {id: 7}]
Loader must return: [{id: 7}, {id: 3}, null]

Worked failure: a global loader caches tenant A's owner under ID 7, then serves it to tenant B. Use request-scoped loaders and authorization within data access. Caching is not permission enforcement. GraphQL mutations also need domain transactions and idempotency when clients retry.

Interview: why introduce GraphQL here?

Explain the client composition need and measured benefits. Compare REST aggregation and the added resolver, authorization and query-cost complexity. “More flexible” alone is not enough.

7. Architecture and impact: make your contribution verifiable

Use a five-minute account: problem and constraints, your scope, chosen design, failure handling, measured result and remaining limitations. Prepare one happy-path diagram and one failure sequence. An ADR records a decision, alternatives, accepted cost and when to revisit it.

For each reported percentage, retain the numerator, denominator, time window, source and changed conditions. A drop from 100 incidents to 83 is a 17% count reduction, but a lower workload may explain it. Compare rates or matched workloads when appropriate. A drop from 10% to 8% is two percentage points and a 20% relative reduction.

For cost, distinguish lower total spend from lower cost per successful operation. For “same-day updates,” define start/end timestamps, working days, median/tail and approvals. Separate personal ownership from team outcomes. Do not invent platform adoption, release reliability or support reductions.

  1. Choose one real architecture decision and write its rejected alternative.
  2. Attach a sanitized artifact: diagram, code change, runbook, report or approved measurement.
  3. Write the result with uncertainty and attribution. If unmeasured, say what evidence you would collect next.
  4. Rehearse a constraint change: double load, revoked permission, provider outage or smaller budget.

Continue with project walkthrough practice. The workbook includes prompts for your reported outcomes without treating them as independently verified facts.

Interview: was the improvement caused by your design?

Describe the comparison and confounders. If attribution is uncertain, say so. Explain your contribution without taking ownership of unrelated changes.

8. Customer-facing AI delivery: start with the user's job

A stakeholder asking for a chatbot may need faster policy lookup, fewer escalations or a clear audit trail. Observe the existing workflow before choosing an agent. Identify the user, buyer, process owner, security approver and operations owner.

Define success with the users: correct evidence, time to resolution, appropriate abstention, permission protection and acceptable cost. A high demo completion rate is not the same as sustained adoption. Keep a human fallback and explain where the system should not be trusted.

  1. Use the discovery-to-adoption guide to write a ten-question interview and current workflow map.
  2. Scope one bounded use case with exclusions, data access, baseline metrics and an owner. Agree on what makes the pilot stop.
  3. Demo success, uncertainty and a denied request. Explain outcomes in the user's language rather than leading with framework names.
  4. Write UAT cases with users, resolve critical defects and obtain explicit go-live approval. Provide rollback, support and escalation paths.
  5. Train users, hand over a runbook and review adoption alongside quality. Investigate abandonment and repeated corrections; do not count logins as value by default.

Technical-sales roles add qualification, commercial discovery, proof-of-value planning and procurement conversations. That is a distinct responsibility, not automatically implied by client-facing engineering. Do not claim it from a technical demo alone.

Interview: the customer wants unrestricted automated actions. What do you do?

Clarify the outcome and risk, propose a bounded pilot with deterministic permissions and approval for consequential actions, and document exclusions. Demonstrate useful progress without promising unsafe autonomy.
