One project from documents to an approved support ticket

Work through these eight sessions in order. Each starts with an explanation, then a small action and an expected result. Use the README commands. The local application runs without installations; Elasticsearch, learned embeddings and a model are explicit optional integrations. Ask your teaching assistant when a result differs from your prediction.

1. Choose the outcome and safety boundary

A support worker needs the right policy and a safe way to request help. The product retrieves permitted evidence and creates a review ticket after human approval. It cannot issue refunds. Success means useful evidence, no permission leaks and one approved ticket. A fluent answer alone is insufficient.

Documents → validate → chunk → permission filter → search → rerank

                                       cite excerpts / request human help
                                                          ↓
                                          proposal → approval → local ticket
Every stage → trace → evaluation and error review

Run python3 -B run.py demo. Expect a delivery citation, a proposal hash and one ticket. Explain which step would be dangerous if a model controlled it.

2. Understand Elasticsearch before connecting it

An inverted index is like a book's index: a word points to documents containing it. Elasticsearch analyzes text into terms and stores postings. BM25 ranks keyword matches using term frequency, rarity and document length. A text field supports analyzed search; a keyword field supports exact tenant and group filters.

An index is distributed into primary shards with replica copies. A search coordinator asks relevant shards for candidates and merges results. More shards add coordination and memory costs; they do not automatically make a small search faster. A refresh makes new segments searchable. It is different from a durability commit. See Elastic's refresh explanation.

This project's adapter uses BM25 plus exact vector scans, then reciprocal rank fusion. RRF combines ranks instead of adding incompatible raw scores. At larger scale, approximate vector indexes trade recall, memory and latency; benchmark before switching. See hybrid search and vector fields.

Read adapters.py. Find the tenant and group filters in both retrieval branches. With an authorized existing service, follow the README's index and ask commands. Without one, inspect the contract test; it does not prove server compatibility.

Check: why recheck Elasticsearch hits against SQLite?

The index can lag behind deletion or permission changes. It returns candidate IDs; the application releases only current authorized source text. That protects this read path, but does not remove stale sensitive data from external storage.

3. Prepare data, chunks and embeddings

Inspect documents.json. Each document has identity, version, tenant, groups, title and pages. Ingestion rejects malformed fields, empty pages, duplicate batch IDs and conflicting immutable IDs. Clean extraction errors before indexing: broken tables, repeated headers, missing pages and obsolete policies can produce convincing but wrong evidence.

The splitter takes 80 whitespace words every 60 words and preserves the page. These are word counts, not model tokens. Overlap helps boundary recall but repeats content. Test a fact crossing a chunk boundary, then compare retrieved evidence and context size.

An embedding represents text as numbers so related text can be close under a similarity measure. Our default hashes words into 64 bins. This demonstrates vector plumbing but is not a semantic model: collisions and synonyms remain problems. The optional existing local encoder supplies learned embeddings. Keep its revision, dimension and normalization consistent between indexing and queries.

Ask as alice for PRIVATE-42. Expect no finance evidence. Repeat as finance. Authorization happens before local encoding and retrieval, and again before releasing results.

4. Split examples and measure errors

Training data fits model parameters. Validation data selects configuration and thresholds. A test set estimates behavior after decisions are frozen. Split related examples together; do not place chunks of one source in both train and test when measuring new-source generalization. See Google's dataset guide.

Precision asks how much retrieved material was relevant. Recall asks how much required material was found. If two of three retrieved documents are relevant and four relevant documents exist, precision is 2/3 and recall is 2/4. Neither measures whether the final answer is true.

Run evaluate.py. The deliberately bad memorizer fits training queries exactly and does poorly on other queries: an overfitting example. The actual pipeline uses a deterministic reranker, not this memorizer. Its strongest-overlap rule improved two validation cases, but can discard useful lower-overlap evidence. Add multi-document cases before trusting it.

Keep an error ledger: missing source, permission mismatch, retrieval miss, poor ranking, insufficient evidence, unsupported generation or failed action. “Wrong answer” does not locate the fault. The ten included cases have been inspected during development and are regression fixtures; collect a fresh test set for an independent estimate.

Check: the model cites a real page. Is its answer proven?

No. The page may not support the claim, may be obsolete or may conflict with another source. Check provenance, relevance and entailment separately. This project displays excerpts instead of claiming synthesized truth.

5. Bound the model's job

Tokens are model-specific text units. A context window must fit instructions, question, evidence and reserved output. Shortening text by characters does not guarantee a token budget. The optional adapter bounds characters and output and requests a fixed context size; a production adapter needs tokenizer-aware admission and overflow tests.

Read the system prompt in adapters.py. It gives the model one job: select evidence IDs or abstain. JSON schema constrains shape; the application checks values and permissions. The model has no tools, and output cannot create a ticket. Prompting alone is not the security boundary.

Retrieval finds current permitted knowledge. Generation produces new text and can introduce unsupported claims. Fine-tuning changes model behavior from training examples; it is not a replacement for fresh knowledge or access control. Begin with retrieval and explicit rules. Consider fine-tuning only after a stable labeled task and held-out evidence show a need.

Compare candidate models on the same cases: relevance, abstention, schema failures, task success, latency and cost per successful task. Choose the least expensive model that meets the actual requirements; do not assume parameter count establishes suitability. Use the optional local model adapter only with an already available model.

6. Trace state and human approval

This is bounded orchestration, not an open-ended agent loop. The sequence is retrieve, optionally select evidence, answer, propose, approve and create. Persistent state lets a new CLI process continue. Empty evidence goes to human review. A human reviewer must have access to the cited evidence and approve the exact result hash.

Run ask, propose and approve separately. Retry approval; expect the same ticket. Try another role, a changed hash and deletion before approval; expect rejection. A local ticket is a real SQLite row, not a remote Jira action. External actions need an outbox and uncertain-outcome recovery.

7. Observe failures and control exposure

Run metrics. Explain p50, p95 and p99 by stage before comparing end-to-end latency. The demo is serial, so concurrency and production tail behavior are untested. Token counts come from provider usage; local compute cost is unknown. Do not report unknown costs as free inference.

Read the tests for invalid model output, source changes, search failure and permission boundaries. Injection defense comes from constrained output, no model write authority, explicit approval and current ACL checks. Malicious source text can still appear as a labelled excerpt. Do not render it as active HTML or treat it as instructions.

Default retrieval caching includes the authorized snapshot and actor. A deleted source invalidates that snapshot. The external search and custom encoder paths bypass cache. Fallbacks are visible: failed search uses local lexical retrieval; failed model selection shows source excerpts. Neither fallback grants broader access.

8. Package and defend the design

The Dockerfile packages the offline CLI; it does not deploy a public chatbot. The README gives test commands for CI and a production gate. Before serving clients, add real authentication, hardened APIs, quotas, model budgets, indexed publication, retention and recovery tests. Do not mistake local actor names for secure login.

Interview rehearsal: explain a query from intake to ticket. Show one permission test, one validation error you fixed and one limitation. Discuss when lexical search is enough, why a learned reranker may help, and why fine-tuning would not solve stale ACLs. Use measured results only; no live model or Elasticsearch result is claimed.
