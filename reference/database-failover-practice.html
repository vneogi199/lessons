A received transaction is not necessarily applied

Imagine copying a numbered receipt book. One worker receives pages; another enters their contents into the accounts. Having page 20 in the inbox does not mean receipt 20 is visible in the accounts.

Source commits → binary log → replica receiver → relay log → applier → readable data
                               received position            executed position

A MySQL binary-log coordinate includes a file and a byte position. Compare coordinates only in the appropriate source-log history. A larger position in another file or another server's log is not proof of newer data. A replica's local relay-log coordinates are a different location again.

A GTID identifies a transaction independently of its location in a binary log. A basic MySQL GTID uses a source UUID and sequence number; newer formats can also include a tag. Executed GTIDs form a set, which can have gaps and multiple sources. Auto-positioning uses transaction history to find missing work; it does not make replication synchronous. See MySQL's GTID definitions.

Abbreviated source A (teaching notation, not a real UUID):
Source executed:    A:1-100
Replica R received: A:1-100
Replica R executed: A:1-95

R still needs to apply 96-100 before those transactions are visible.

Use SHOW REPLICA STATUS to inspect receiver/applier health, source coordinates, retrieved/executed GTID sets and errors. An apply error can stop progress while receiving continues. Seconds_Behind_Source alone is not a proof of freshness. Observe the stages, current workload and a known transaction marker. See the status-field documentation.

Promotion requires compatible histories and an understood data-loss bound. If R1 has A:1-100 and R2 has A:1-99 plus B:1, counting transactions gives a misleading tie. Investigate B:1 as a possible errant transaction. Do not erase GTID evidence or skip errors merely to make replication appear healthy. Purged logs may require reseeding a replica.

Try: R has received all 100 transactions. Can you immediately promise that reads include transaction 100?

No. It has executed only through 95. Verify apply completion and the application's actual data. A received position, executed position and durable recovery guarantee answer different questions.

What does the commit acknowledgement mean?

Asynchronous replication allows the source to acknowledge before a replica has the transaction. Failover can lose acknowledged writes. Synchronous configurations wait for a specified remote stage; name that stage rather than saying “all replicas are current.”

MySQL semisynchronous replication waits for the configured replica acknowledgement of received, logged work; it does not wait for replica query execution. It can fall back to asynchronous behavior after timeout. Monitor actual mode and durability settings. A replica acknowledgement does not authorize promoting an arbitrary stale replica. See MySQL semisynchronous replication.

Sentinel's configured quorum determines agreement that a primary is down. Authorizing failover also requires a majority of Sentinels. These are different checks. Redis replication remains asynchronous; Sentinel is not a consensus-replicated data store. Write-admission settings based on connected replicas can reduce exposure but do not provide general split-brain safety. See the Sentinel documentation.

Orchestrator understands MySQL topology and recovery options. Its control-plane availability does not turn MySQL writes into consensus commits. Validate manager leadership, recovery hooks, permissions and routing together. The original openark repository was archived in February 2025 and points to the Percona fork. Select and validate a maintained distribution for the exact database version; this comparison is not an installation recommendation.

Promotion does not stop the old writer

A network partition can hide a healthy database from the manager while some clients can still reach it. Before reopening writes on a replacement, the recovery design must establish that the old writer cannot accept conflicting writes.

Fencing can involve verified host shutdown, storage access revocation or a write path that enforces a newer ownership epoch. The target resource must reject stale epochs. Issuing tokens without checking them provides no protection. DNS changes and proxy updates alone leave direct clients and old connections as possible paths.

A read-only setting is useful defense, but check privileged bypasses, existing sessions and whether the isolated node can receive the setting. If fencing cannot be established, stop and escalate according to the safety policy rather than promoting blindly. Rejoin the former primary only after comparing histories and rebuilding or reconciling as required.

Interview: a controller has a majority. Why can data still split?

The controller can agree on a decision while an isolated database continues serving old clients. Control-plane agreement and enforcement at the write target are separate mechanisms.

Measure RPO and RTO from application evidence

RPO is the tolerated recovery-point gap, commonly expressed as time. RTO is the tolerated time to restore the defined service. These are targets. A drill measures actual loss and recovery time.

Example: failure begins at 12:00:00; the recovered contiguous history includes all acknowledged writes through 11:59:57; valid application reads and writes resume at 12:00:40 and remain healthy for the agreed observation window. The observed recovery-point gap is three seconds and service recovery took forty seconds. Also report missing transaction IDs and count. If history has holes, do not summarize it using only the newest surviving timestamp.

Distinguish client-acknowledged, rejected and unknown writes. A timeout can conceal a committed transaction. Reconcile it using a business key. Replication does not replace backups: a replicated deletion or corruption may require point-in-time recovery.
