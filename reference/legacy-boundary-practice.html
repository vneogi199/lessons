Read legacy data without widening access

The supplied project contains a WSDL/XSD bundle, XML success/fault fixtures, Zeep envelope generation, a strict converter, connection factories and typed SQL templates. Tests have not been run.

Translate a form without changing its meaning

Think of XML as a form with named boxes and labels. The namespace identifies which form definition owns a box. Removing every namespace can make two different fields look the same.

The sample has two records. The first contains 12.50 USD and an explicitly null note. The second contains 3.00 GBP and no note field. The converter keeps decimal values as strings, preserves currency, and treats absent and null differently. It does not add the amounts because they have different currencies.

Absent Note → no JSON key
Note xsi:nil="true" → "note": null
Present empty Note → "note": ""

Zeep constructs the request from local schemas. The test transport rejects remote imports and network calls. The XML parser rejects DTDs and external entities before conversion. A SOAP fault becomes a safe category; raw diagnostic text is not copied into the answer.

Interview: a write timed out with BUSY. Retry immediately?

No. The server may have performed the write before losing the response. Reconcile by the agreed operation ID. A read-only BUSY can follow a bounded retry policy.

Let a model choose an intent, not write SQL

A restaurant menu offers named dishes. Ordering one does not grant access to the kitchen's tools. The SQL exercise uses the same boundary: latest_rfq or exposure_by_desk selects one reviewed query. Tenant comes from the server, and desk/date are validated parameters.

The latest-record query sorts by timestamp and unique RFQ ID, so equal timestamps do not make the result arbitrary. The exposure query assumes a defined currency and row grain. If the user omits the desk or date, ask for it. Missing data stays missing.

Database connections verify TLS and use bounded pools/timeouts. Parameterization protects values; read-only database permissions limit the principal. Neither replaces tenant authorization. The included denial procedure needs a real approved database and remains unexecuted.

Practice: can a SELECT-prefix check make arbitrary SQL safe?

No. This project avoids arbitrary SQL altogether. More flexible SQL requires a dialect-aware parser, object/function allowlists, database restrictions and resource controls.
