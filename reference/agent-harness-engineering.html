Harness engineering for bounded agents

A harness is the application code around a model. It supplies context, exposes tools, checks proposed actions, saves state and decides when execution must stop. An evaluation harness runs cases and grades their outcomes. Keep these responsibilities separate so a grading change cannot change production permissions.

A simple example

A child asks a librarian for a book. The child can describe what they want. The librarian checks the library card, finds an allowed book and records the loan. In an agent, the model proposes; application code checks identity and performs the action. A convincing request cannot change the library rules.

Follow one RFQ through the controller

Authenticated request → load tenant-scoped state → assemble bounded context
 → model proposal → validate shape → check policy and remaining budget
 → read-only tool → record observation → next step or explicit terminal result
                                  ↘ write proposal → exact human approval

Separate trusted context from model arguments. Tenant identity comes from authentication. Policy versions come from your store. The model may supply an RFQ identifier, but the repository must still check its owner. A schema-valid identifier can refer to another customer's record.

Store a run ID, workflow version, current state, step count, deadline, budget reservation and terminal reason. Tool attempts need their own IDs. Business operations need stable idempotency keys that survive retries. A new run ID must not create a second trade or ticket.

Make the limits executable

Check step count before starting the next model call. Reserve the worst permitted call cost before admission. Restrict output tokens and transport duration. Reconcile reported usage after completion. Unknown usage remains unknown; do not refund an uncertain reservation as though the call were free. Concurrent workers must reserve against one shared budget atomically.

A timeout stops waiting. It does not prove a remote write failed. Record an unknown outcome and reconcile by operation key before retrying. Apply a process or container deadline for tools that cannot be cancelled cooperatively. Keep files, credentials and network destinations limited outside the model runtime.

Define terminal states such as completed, denied, needs_review, budget_exhausted and unknown_effect. Return these explicitly to the caller. A generic “success” after a denied tool hides useful evidence.

Choose a workflow you can test

For “parse RFQ, validate fields, check limit, request approval,” a fixed workflow has predictable branches. A planner helps when the required reads depend on missing information. It adds decisions and failure paths. Test both with the same cases and count calls, violations and unresolved results before accepting that extra flexibility.

The lab's replay adapter checks expected call order and exact arguments. It cannot execute tools. Use it to test orchestration changes without provider cost. The existing bounded workflow project supplies the guard, planner and approval exercises used below. Then test real adapters separately with disposable fixtures. A mock that always returns success misses the crash between a committed effect and a saved checkpoint.

Practice and expected evidence

  1. Set a two-step budget. Make a scripted model request a third read. Expect budget_exhausted before dispatch.
  2. Put “ignore policy” in retrieved text. Expect unchanged permissions.
  3. Crash after a fake effect commits. Resume with the same operation key. Expect one effect and one recovered result.
  4. Change the approved payload. Expect rejection and a new approval request, not silent reuse.
Interview: why does a typed tool schema not secure a tool?

It constrains argument shape. It does not establish the actor, current authorization, safe resource scope, affordable work or approval of an irreversible effect. Those checks belong at the execution boundary, including direct calls that bypass the model.

MCQ: an action timed out after dispatch. Choose: A) retry with a new key; B) reconcile with the same key.

B. The external system may have committed. A fresh key can produce a duplicate effect. If no reconciliation contract exists, preserve uncertainty and require review.
