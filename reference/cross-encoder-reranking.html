Cross-encoder reranking

Goal: decide whether a second ranking stage earns its latency budget, and defend that decision in a senior AI engineering interview.

Return to lesson 0596 · RAG evaluation

Score the query and passage together

A bi-encoder represents the query and documents separately, allowing stored document vectors to be searched efficiently. A cross-encoder processes each query–passage pair jointly. Token interactions help distinguish a passage that answers the question from one that merely shares vocabulary. Its output is a relevance score, not an answer or a factuality guarantee.

Use lexical or hybrid retrieval to gather N authorized, deduplicated candidates; score those N pairs; sort descending; send the best k passages to context assembly. Keep document IDs, versions and source spans attached throughout. Reranking cannot recover a relevant passage missing from the candidate set.

Some models return logits, including negative values. A sigmoid preserves their ordering but does not establish calibrated relevance probabilities. Select models using the domain, language, supported sequence length and measured quality. See the official CrossEncoder usage guide.

Connect a real scorer

In an environment that already has Sentence Transformers and approved local model files, replace the fixture scores with the following adapter. Model inference has not been executed as part of this lesson's local checks.

from sentence_transformers import CrossEncoder

# Existing local directory; record its model revision and package version.
model = CrossEncoder("/path/to/existing/reranker", local_files_only=True)
query = "How do I revoke an API key?"
passages = ["Create a key in settings.",
            "Revoke the key in settings to disable access.",
            "Invoices are available under billing."]
scores = model.predict([(query, text) for text in passages], batch_size=8)
ranked = sorted(zip(passages, scores), key=lambda item: item[1], reverse=True)
print(ranked)

Compare actual output with human relevance judgments; never assert that a chosen model must put B first. Inspect model-specific truncation: if the answer is at the end of a long passage, it may never reach the scorer. Preserve the original passage for citations even when scoring a bounded excerpt.

Batch size is a throughput decision

N controls candidate coverage and total pair work; k controls how much evidence reaches generation. Batch size controls how many pairs are processed together. Larger batches can improve device utilization but increase memory use, padding and queue delay. They do not reduce the number of pairs. Grouping similar lengths may reduce padding; restore document IDs after any reordering.

Example budget: a 250 ms pre-generation deadline with 60 ms retrieval and 40 ms assembly leaves 150 ms for reranker queueing and inference. With 48 candidates and batches of 16 there are three batches. At a hypothetical 30 ms each, 90 ms inference leaves 60 ms for queueing and overhead. Measure under concurrency: these numbers are planning arithmetic, not a benchmark.

Record N, token lengths, batch size, hardware, queue wait, warm/cold p50 and p95 latency, timeout rate and cost per query. For a dedicated device, allocated cost/query is hourly device cost divided by completed queries/hour; for an API, use its actual billing units. Tune N and model size jointly. On a deadline failure, use an explicitly measured authorized first-stage fallback or abstain; never present fallback results as reranked.

Evaluate the whole retrieval path

Freeze a held-out query set, corpus version, relevance labels and first-stage candidates. Compare baseline and reranked results on identical candidates and k. Measure candidate recall@N, MRR@k for first-answer rank, nDCG@k for graded ordering, and precision@k. Define empty-label, duplicate and tie policies. Then evaluate answer correctness and grounding separately: better ranking need not produce better answers.

Do not inject missing positive passages into evaluation candidates. In Sentence Transformers, use the documents sample field with always_rerank_positives=False for a realistic pipeline comparison; the evaluator's default can include positives absent from retrieval. See the official reranking evaluator.

Slice by language, exact identifiers, long documents, ambiguous queries and no-answer cases. Sweep N and batch size on a development set, then report held-out quality, uncertainty, latency and cost together. A reranker that improves average MRR but breaks the latency budget or a critical slice may not belong in production.

Defend the design

  1. Candidate recall is 0.45 but reranked precision looks excellent. What should you improve first?
  2. Doubling batch size improves throughput while p95 worsens. What measurements explain that?
  3. Scores shift after a model upgrade. Why is reusing a fixed acceptance threshold risky?
  4. A passage scores highly but contains malicious instructions. Which boundaries keep relevance separate from permission and trust?
Compare your reasoning

First inspect missing candidates, ingestion, filters and retrieval before tuning ordering. Separate queue wait, padding, memory pressure and inference time when diagnosing batches. Revalidate thresholds against labeled data after any model change. Enforce access before scorer exposure; treat retrieved text as untrusted data and keep tool authority outside retrieval scores.
