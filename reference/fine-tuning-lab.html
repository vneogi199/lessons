Fine-tune a small task, then prove whether it helped

Read the decision example first. Then inspect the dataset and loss mask. The supplied recipe trains a LoRA adapter on an already-present local causal language model. It does not install packages, fetch weights or call a provider. Model execution requires a separately approved environment and has not run here.

Which problem are you fixing?

A support service needs exactly one label: urgent, routine or review. A prompted model sometimes adds a paragraph instead. First try clearer examples and strict output validation. If behaviour still fails often enough to justify training, compare an adapter against that prompted baseline.

Fine-tuning changes model weights to fit examples. It is like practising one response format repeatedly. Retrieval supplies evidence from a source at request time. If the problem is yesterday's policy replacing today's policy, fix retrieval and versioning first. Fine-tuning is not a reliable live facts database.

LoRA freezes base weights and trains small low-rank updates in selected layers. In simplified form, the layer uses W + BA, with rank r smaller than the full matrix dimensions. This reduces trainable parameters and optimizer state; you still need the base model for training and inference. Quantization is a separate choice. See LoRA concepts and configuration and target modules.

Make labels and splits trustworthy

Define urgent as an explicit active safety issue, routine as a clear non-emergency request, and review as insufficient or conflicting information. This is a fictional support policy, not an operational safety classifier. Human policy owners must define real labels and error costs.

Each JSONL row contains id, group, split, text and label. Keep messages from the same incident, customer thread or template family in one split. Train updates weights. Validation chooses hyperparameters and the release candidate. Test is reserved for the frozen final comparison. A public toy fixture cannot be a genuine untouched benchmark.

The supplied validator rejects duplicate IDs, identical normalized text, cross-split groups, invalid labels and missing classes in a split. It cannot detect semantic paraphrases, private data or wrong labels. Review those manually. Use only authorized data; remove sensitive identifiers and track licence, provenance and deletion obligations.

Understand one training example

Prompt: classify the request; return one allowed label.
Request: smoke is coming from the motor
Label:
Target: urgent + end-of-sequence

Input IDs: [prompt tokens ...] [target tokens ...]
Labels:    [-100 ... -100]    [target tokens ...]

The causal model predicts the next token. Its implementation shifts predictions and labels internally. -100 tells the loss to ignore prompt and padding positions. The target remains supervised, including its end token. Do not let silent truncation remove the answer; this lab rejects oversized examples.

Training loss is not task accuracy. A model can reduce token loss while returning the wrong label or becoming overconfident. Always generate outputs and score the actual application contract.

Run the lab in stages

  1. Read the practice README. Run standard-library checks only. Predict which leakage examples should be rejected.
  2. Inspect the local model's licence, tokenizer, architecture, safe weight format and target module names. Record exact package versions and model artifact hash. The default q_proj/v_proj targets suit some architectures, not every model.
  3. Use the supplied predict command without an adapter on validation rows. The prompt includes examples from the training split only. This is the prompted baseline.
  4. Run train with bounded steps on approved hardware. Inspect loss and trainable parameters. The recipe uses fixed-length completion-only loss, AdamW and a fixed seed. It is a small teaching loop, not a distributed training platform.
  5. Predict validation labels with the adapter. Compare exact accuracy, invalid outputs, per-class recall, latency and failure examples. If you change rank, learning rate or examples, record a new run. Do not inspect test to choose settings.
  6. Freeze the candidate, prompt and scorer. Run baseline and adapter on the test split once for the release decision. Report both results, sample counts and uncertainty. The bundled tiny synthetic rows only check plumbing.
  7. Reload the saved adapter in a fresh process. Verify parity with the selected candidate, then apply the same serving validation, auth and quotas as before. Weights never authorize tool actions.

The script writes predictions with elapsed time and output token counts. It does not convert unknown hardware cost into zero. Keep training time, hardware rate, storage and engineering effort in the cost report. Use identical prompts and decoding when comparing baseline and tuned model.

Choose a release, not just a lower loss

Before training, set task-specific gates. For example, a fictional evaluation may require higher macro recall with no increase in missed urgent cases, no invalid labels, and a latency budget. Choose real thresholds with stakeholders; do not use these as universal safety standards. If rare critical cases are absent, the test cannot establish their safety.

Compare a keyword/rule baseline, the prompted base and the adapter. Check out-of-domain and instruction-injection examples separately. A tuned model can memorize data or regress outside its training task. Route ambiguous inputs to review rather than treating an allowed label as correctness.

Serve the exact base revision with the adapter, tokenizer, prompt and schema versions. Merging an adapter changes artifact handling and may affect quantized serving; test the resulting artifact separately. Keep a previous approved version for rollback. Shadow requests must not perform duplicate external actions.

Break-even requests = training and setup cost / saving per request, if the saving is positive and quality passes. Include idle capacity and operational effort. A smaller tuned model is not automatically cheaper than a managed baseline at low volume.

Interview practice

Why does a perfect training score not prove improvement?

It can reflect memorization or leakage. Compare held-out task metrics against the unchanged baseline, inspect slices and keep test data out of candidate selection.

What does LoRA save, and what remains?

It reduces trainable weights and their optimizer state. The frozen base model and forward/backward computation still consume memory and compute. Serving needs a compatible base plus adapter or a separately verified merged artifact.

MCQ: should prompt padding receive labels “-100” or “token”?

-100. Padding and prompt positions are ignored by this completion-only objective; target tokens remain supervised.
