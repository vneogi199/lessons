Client delivery

Review AI-assisted changes

Use Claude Code for this exercise. The deliverable is one reviewed RFQ parser change. An assistant can draft the change, but you must explain each changed line and show what the checks establish. This written exercise does not install tools, connect accounts or execute code.

Write the contract before the patch

Synthetic requirement: accept an RFQ ID, currency and positive decimal amount. Preserve the amount exactly. Reject missing IDs, unsupported currencies and non-finite amounts. Repeated IDs with identical content are replays; changed content under the same ID is a conflict. The parser must not send an order.

Ask the assistant: “Read the existing parser and callers. Ask the questions that affect this contract before editing. Then give a file-level plan and acceptance cases. Do not install, run, commit or call external systems.” Resolve currency support, whitespace, duplicate ownership and error format. Record the answers in the spec.

  1. Inspect the implementation, tests and dependency versions. Identify the function that owns validation.
  2. Write a failing case for each new rule. Include a previously valid RFQ to protect existing behavior.
  3. Implement one rule and review its diff before starting the next.
  4. When execution is authorized, run narrow checks, then relevant regression tests. Record commands, versions and actual results.
  5. Review the staged diff and remove unrelated edits. Commit the contract, implementation and checks together.

Catch a plausible mistake

An assistant changes Decimal(raw_amount) to float(raw_amount) and calls an undocumented SDK method. The happy-path test still compares only the currency.

What should the review reject?

The float conversion loses the exact-decimal contract. The test does not assert the amount. Verify the SDK method against the installed version and official documentation. Add malformed, non-finite, duplicate and conflicting-ID cases. A mock that invents the same nonexistent method cannot prove compatibility.

Read exception paths too. A broad catch that returns an empty result can turn an upstream failure into a false “no RFQs” answer. Check for hardcoded secrets, token logging, disabled TLS validation and retries around irreversible actions. Unit tests cannot establish deployed permissions or recovery behavior.

Review security findings with Aikido

Use a synthetic repository only after its owner approves a connection. Aikido's GitHub instructions distinguish account authorization from organization app installation. Select only the approved repository. Review the exact requested permissions; do not assume they are read-only.

  1. Record the repository owner, approved data boundary, requested access, retention requirements and removal procedure. Obtain approval before granting access.
  2. After an authorized scan, record the commit and finding ID. Keep credentials and private source excerpts out of public tickets.
  3. Check reproducibility, reachability, affected runtime and exposure. Severity alone does not determine the fix.
  4. Patch the cause, add a regression check and rescan the same scope. Record the result.
  5. For an exception, record evidence, owner, expiry and compensating control. Revisit it when code or exposure changes.
  6. Remove the integration when no longer required and verify access removal.

Example: a scanner reports a hardcoded credential. Investigate history and rotate a real exposed credential even if the latest file no longer contains it. A synthetic string may be a false positive after you establish that it has never authorized access. An infrequently used code path is not automatically safe.

Practice: can a green scan replace authorization tests?

No. A cross-tenant read can use safe SQL and still disclose data. Keep explicit denial tests and human diff review.

For the interview, explain a defect, the test that exposes it and the remaining deployment check. Ask your teacher to challenge the evidence. No scan or runtime result is claimed here.
