Enterprise security

Choose an OAuth grant

A visitor badge identifies a visitor. A room key permits entry to certain rooms. Authentication establishes identity. Authorization decides which operations that identity can perform. Login does not grant access to every document.

OAuth lets a client obtain limited API access. OpenID Connect (OIDC) adds authentication. An OIDC ID token describes the authentication event for its client. An access token is presented to its intended API. Do not substitute an ID token for an API access token. See OIDC Core.

A public client, such as browser JavaScript, cannot keep a client secret. A confidential backend can protect credentials. A browser application can keep provider tokens on its backend and use a session cookie. This adds session storage and CSRF responsibilities. API object permissions still apply.

Follow one login

  1. Create a random PKCE verifier and its S256 challenge. Store a short-lived login transaction bound to the browser, including state and an OIDC nonce.
  2. Send the browser to the configured authorization endpoint with the challenge, client ID and registered redirect URI. The identity provider authenticates the user.
  3. At the callback, check the transaction and state. Exchange the code with the verifier at the configured token endpoint.
  4. Use a maintained OIDC library to validate the ID token: signature, allowed algorithm, issuer, audience, expiry and nonce, plus applicable authorized-party checks. Decoding JSON is insufficient.
  5. Consume the login transaction once and create a fresh session. Resolve local roles and tenant access before returning private data.

PKCE binds code redemption to the client that began the flow. It does not decide whether that user may approve a trade. Enforce exact redirect rules and reject issuer mix-ups. Avoid implicit token delivery in new designs. The password grant must not be used under the current security BCP. Read RFC 9700 before implementation.

Handle tokens after login

A client-credentials token has application authority. Give an importer only feed-read permissions. It must not impersonate an approver. Confidential clients authenticate using the method registered with the provider. See client credentials.

Keep refresh tokens out of URLs and logs. Public-client refresh tokens need rotation or sender constraint under RFC 9700. With rotation, atomically save the replacement. Reuse of an old token can indicate theft. Serialize refresh for one session so concurrent requests do not create accidental reuse. Define how revocation ends local sessions.

Device authorization displays the provider's verification URL and user code. Poll at the returned interval. Continue on authorization_pending; increase the interval on slow_down. Stop on expiry or denial. Users must verify the device request: an attacker can ask them to approve an attacker's code. See RFC 8628.

Practice: should a nightly importer reuse a trader's refresh token?

No. Use service identity and client credentials if the API supports application access. Give it a narrow grant and an owner. A person's departure should not silently break an unrelated service.

Practice: can this API accept a valid token intended for another API?

No. Validate the audience. A valid signature proves who signed the token, not that this API should accept it.

Senior interview: why can a revoked user still see a cached answer?

The cache may outlive the authorization decision. Recheck permissions and partition caches by relevant identity and policy version. Token expiry alone does not define a suitable revocation window.
