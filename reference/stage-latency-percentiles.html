p50, p95 and p99 by stage

A percentile locates a value in an ordered set. p50 describes its middle. p95 and p99 describe the slower tail. Always state the population and time window: “p95 of successful model attempts over five minutes” differs from “p95 of all client requests.”

Ten children wait 1, 2, 3, 4, 5, 6, 7, 8, 9 and 100 seconds. With the nearest-rank convention, p50 is 5 seconds; p95 and p99 are both 100 seconds. Ten observations give a very coarse tail estimate. A smooth chart does not create more evidence.

Use a monotonic clock for elapsed time within a process. Do not subtract wall-clock timestamps from different machines unless your measurement accounts for clock uncertainty. Record the full request duration separately, including queue wait and retries. For streaming, also measure time to the first answer token actually released to the client.

Aggregate buckets before calculating percentiles

The metrics adapter now supplies ai_stage_seconds with bounded stage and outcome labels. Its dashboard has separate p50, p95 and p99 panels. The following classic-histogram query merges compatible bucket counts across instances before estimating a percentile. Keep the same bucket boundaries across the fleet. See Prometheus histogram guidance.

histogram_quantile(0.95,
  sum by (le, stage) (rate(ai_stage_seconds_bucket[5m]))
)
# Change 0.95 to 0.50 or 0.99 for the other panels.
# Keep outcome in the grouping to compare success/error populations.
sum by (stage) (increase(ai_stage_seconds_count[5m]))

The last query is sample count. Put it beside tail latency. An empty stage has no percentile, not a zero-second percentile. Bucket interpolation gives an estimate; choose boundaries near the thresholds you need to investigate. An overflow bucket cannot describe arbitrarily large latency precisely. The query reference defines the calculation.

Do not add percentiles

Consider 100 synthetic requests. Request 1 spends ten seconds in retrieval and zero in generation. Request 2 does the reverse. The other 98 spend zero in both. Each stage's nearest-rank p99 is zero, yet request p99 is ten seconds. Stage percentiles come from different ranked populations. Measure total request latency directly.

Parallel stages overlap. Two 200 ms reads may add about 200 ms to the critical path, not 400 ms. Parent spans already include child time, so adding all span durations double-counts work. Use traces to inspect overlap and histograms to compare populations.

Do not average p95 values from pods either. A quiet pod and a busy pod have different weights. Sum histogram buckets, then calculate the fleet quantile. Filter by environment and service before merging; combining unrelated workloads can conceal a regression.

Diagnose a slow release

Suppose queue p99 rises while model p95 stays flat. Check admission concurrency, pool waits and retry amplification before switching models. Compare offered load, successful throughput, error rate, cache hit rate and stage counts. A faster p95 caused by rejecting slow requests is not automatically an improvement.

Interview: why is p99 unstable with low traffic?

Few samples place the percentile near a small number of observations. One slow request can move it sharply. Show counts, use an appropriate window, and retain incident traces. Do not hide long failures by treating timeouts as missing data.

MCQ: two pods report p95=1s and p95=9s. Choose: A) fleet p95 is 5s; B) merge their histogram buckets.

B. The two quantiles omit sample counts and distribution shape. Their arithmetic mean is not the fleet percentile.
