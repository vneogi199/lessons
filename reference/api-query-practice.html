GraphQL batching and API versions

These are two separate exercises. Start with the order query. Study versioning in another sitting. Source and tests are supplied; neither project has been executed.

Fetch the right customer for each order

Think of four shopping bags with customer labels: 1, 2, 1, and missing. You can fetch each label separately, or collect the unique labels and look them up together. A batch lookup saves repeated work, but the result still has to go back onto the correct bag.

The Strawberry project defines orders, customers and a rename mutation. A real SQLite repository supplies the rows. The test data contains a second tenant with the same customer ID. Every query includes the trusted actor's tenant.

Requested IDs:       2, missing, 1, 2
SQL returns rows:    2=Ben, 1=Ada
Loader returns:     Ben, null, Ada, Ben

The adapter builds a dictionary keyed by ID, then walks the requested IDs. Returning the SQL rows directly would shift the missing position and could attach a name to the wrong order. Tenant filtering happens before any row reaches that dictionary.

Read test_schema_shape_and_actual_select_count. It executes the schema, checks every returned field, and expects two SQL SELECT statements: one for orders and one for customers. Repository calls alone are a weaker measurement because a repository can issue several SQL queries internally. Here a SQLite trace callback counts statements. The count is an expected assertion until the test runs.

A new context creates a new loader for each request. Its cache lives only for that request. The rename mutation commits the change and clears that customer's cached value. Its test first loads Ada, renames her to Ana, then loads the same ID again. Removing the clear should make that assertion fail.

A query can return GraphQL errors even when an HTTP integration responds with status 200. These tests inspect result.errors directly. They execute the schema without HTTP; an exposed service still needs authentication, query-cost limits and safe error formatting.

Interview: why does a shared loader cause a tenant leak?

Customer ID 1 is not globally unique in this schema. A cache shared across tenants can return the first tenant's value for the next tenant. Request-scoped loaders and tenant-scoped SQL address separate parts of that failure.

Practice: what should the missing child return?

A. The previous customer value.
B. An explicit missing position.
C. The next customer's value.

Answer: B. The field allows null. Keeping that position preserves the association between orders and customers.

Keep two response shapes separate

Imagine an old form with a numeric ID and a name field. A newer form uses a string ID and a label field. The stored item can stay the same while the API prints either form. A client must receive the version it requested.

The versioning project serves one public synthetic item. /v1/item and /v2/item choose through the URL. /item chooses through X-API-Version and defaults to 1. Unsupported versions and conflicting URL/header choices return 400.

v1: {"id":7,"name":"Demo bond","quantity":10}
v2: {"id":"7","label":"Demo bond","units":10}

The header-dependent response includes Vary: X-API-Version. The warmed-cache test keeps separate entries for both versions and asks for v1 again after v2. It also checks the Vary header. A real CDN must implement the same cache-key distinction; the local fixture does not prove CDN configuration.

The tests replace only the data dependency. Version selection and serialization still run. This makes the expected data predictable without mocking the behavior under test. The project includes a pytest configuration and a debugger configuration matched to its filenames. Open that project directory as the editor workspace.

If coverage tools are already available and execution is approved, collect branch coverage. An untested conflict branch needs a conflicting request. A covered branch still needs an assertion about its output. To check test quality, deliberately remove the conflict check in a temporary local change: the conflicting-version test should fail. Restore the code afterward. No such mutation test has been run here.

Interview: should a private RFQ use this public cache policy?

No. This example contains public fixture data. Private responses need an explicit identity-aware cache design or a no-store policy. Vary on API version alone cannot separate users.
