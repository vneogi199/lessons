FastAPI production operations practice

Start with the existing RFQ CRUD project. It has a bounded request body, tenant checks, versioned writes and replay handling. Its SQLite fixture and injected identity are teaching boundaries. Do not present it as a deployed PostgreSQL service with production authentication.

A restaurant can have many waiters but only four kitchen stations. Adding waiters does not make the kitchen faster. In an API, request concurrency must fit database connections and downstream capacity. A long queue makes clients wait and then retry.

Own resources for their actual lifetime

Create the database engine and shared HTTP client in application lifespan. Close them during shutdown. Give each request or transaction its own database session. Never share one mutable session across concurrent tasks. A rollback belongs to the unit of work that owns the transaction. Avoid holding a database transaction while waiting for an LLM.

Each worker process owns its own lifespan resources. In a fictional deployment with four workers and a pool of ten plus five overflow connections each, the service can demand 60 connections. A rollout with twice as many replicas can double that demand. Reserve database capacity for migrations and operations too. See lifespan and deployment concepts.

Keep blocking work away from the event loop

An async endpoint can serve other requests while it awaits nonblocking I/O. A synchronous database call or CPU-heavy PDF parse inside that endpoint blocks the loop. FastAPI runs ordinary synchronous path functions in a thread pool; moving CPU work there still competes for finite capacity. A durable worker queue is a better boundary for long document jobs. Return 202 only after durable acceptance, with a job URL and tenant-scoped status checks. FastAPI's concurrency guide explains the async/sync distinction.

Set separate limits for body receipt, queue wait, connection acquisition and downstream work. Give the whole request a deadline and pass its remaining time downward. Retrying every layer can multiply load. Pick one retry owner for each remote operation.

Keep liveness cheap: it reports that the process can respond. Readiness decides whether it can accept useful work. A shared dependency outage should not cause every pod to restart endlessly. Use bounded dependency probes and document which failures remove readiness.

Measure before tuning

Record route templates, outcomes and stage times. Never put RFQ IDs in metric labels. Compare a warm baseline with overload under the same request mix. Include malformed input, denied access, retries and disconnected clients. Report offered load and completed throughput; a closed-loop client can hide queue growth by sending less work when the service slows.

Release with an immutable image and reviewed configuration. Set resource limits, pool limits and graceful-shutdown deadlines together. Use backward-compatible schema changes, a small canary and explicit rollback thresholds. Keep secrets outside the image and telemetry. Do not run destructive failure drills against production without a separate approved plan.

Interview: p95 doubled, CPU stayed low. What do you check?

Separate queue wait, pool acquisition, database time and provider time. Low CPU is consistent with waiting. Compare concurrency and retries before adding workers; more workers can worsen a saturated database.

MCQ: a job must survive process death. Choose: A) in-process background task; B) durable queue and worker.

B. In-process work has the process's lifetime. The queue still needs idempotent consumers, bounded retries and a dead-letter or review path.
