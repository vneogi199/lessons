Production AI interview questions and answers

Also practise behavioral, leadership and culture interviews.

These 35 original practice questions cover the seven production AI extensions. They are not claims about any employer's question bank. Answer aloud for two minutes before opening each answer. For design questions, state your assumptions first.

Score yourself 0 if you cannot explain the mechanism, 1 if you can explain it, 2 if you can also identify a failure and trade-off, and 3 if you can defend your choice after the follow-up changes a constraint. This is a rehearsal rubric, not a hiring prediction. Repeat missed questions tomorrow, then mix topics next week. Ask your teacher to challenge an answer you cannot support with evidence.

Harness engineering

Review the explanation and sources.

1. What does an agent harness own that the model should not own?

The application owns authenticated identity, permissions, tool dispatch, durable state and resource limits. The model proposes actions using supplied context. Validate a proposal's shape, then check authority and budgets before dispatch. A prompt cannot give the model permission to change its own limit.

Follow-up: a tool is callable directly without the model. Its executor still needs the same authorization checks; the harness must not be the only protection.

2. Would you use an agent or a fixed workflow to review an RFQ?

Use a fixed workflow when the steps are known: parse, validate, read exposure, compare limits and request review. A planner can help choose reads when required evidence varies. Compare failure rate and cost on the same cases before accepting the extra decision paths.

Follow-up: an unknown instrument appears. Stop for clarification or use a bounded lookup path. Do not let the planner invent instrument metadata.

3. How do parallel workers share a spending ceiling?

Reserve funds atomically in a shared ledger before each call. Bound output and duration, then reconcile known usage. Separate run, tenant and account limits. Unknown usage cannot be treated as free. Per-worker counters allow all workers to spend the same remaining balance.

Follow-up: a worker dies after dispatch. Preserve the reservation until billing or reconciliation resolves the attempt; an expired lease alone does not prove zero spend.

4. How do you stop a loop that keeps producing different wording?

Count steps and elapsed time independently of text. Track semantic work identities such as tool, normalized arguments and authoritative evidence version. Detect repeated work and lack of new evidence. Return an explicit terminal reason. A text comparison alone misses paraphrases.

Follow-up: polling is legitimate. Permit a stated polling interval and attempt budget; do not disable the loop guard entirely.

5. A write timed out. How should the harness recover?

Record an unknown effect. Query the destination using the original operation key or reconcile its receipt. If a retry is safe, reuse that key and unchanged intent. A new key can create a duplicate. If the destination provides no reliable contract, require review.

Follow-up: the user changes the payload. Treat it as a new proposal and obtain new approval after resolving the original effect.

FastAPI production practice

Review the operations lesson and sources.

6. Why can an async endpoint make unrelated requests slow?

Blocking I/O or CPU work inside the event loop prevents other tasks from progressing. Measure event-loop delay and stage timing. Use compatible async clients for I/O. Move long CPU jobs to bounded workers with durable acceptance where survival matters.

Follow-up: moving work to threads still saturates the service. Thread capacity is finite; apply admission limits and examine whether process workers or a queue fit the workload.

7. How would you size database pools across workers?

Count processes across all replicas, including rollout overlap. Multiply each process's pool plus allowed overflow, then reserve capacity for other services and operations. Bound pool wait. Adding web workers can increase database pressure without increasing useful throughput.

Follow-up: four processes each allow ten connections plus five overflow. They can demand 60 connections before other clients or rollout overlap.

8. What should happen during graceful shutdown?

Stop new admission, allow accepted work to drain within the platform deadline and close owned clients. Persist long work through a durable queue. Reconcile incomplete external effects after restart. Align load-balancer draining and process termination deadlines.

Follow-up: one provider call ignores cancellation. The process needs an outer termination bound, and recovery must preserve uncertainty about any effect.

9. How do you deploy a database schema change without breaking old workers?

Expand the schema compatibly, deploy code that can handle the transition, migrate data with observable progress, then remove obsolete fields after old readers are gone. Test rollback before the destructive contract step. A code rollback cannot automatically undo an incompatible migration.

Follow-up: the migration runs for hours. Bound batches and lock duration, track resumable progress and assess load before continuing.

10. How do you demonstrate production depth honestly?

Describe a service you actually operated: constraints, your responsibility, one failure, the evidence you used, the mitigation and the follow-up test. State whether results came from a local fixture, staging load test or production. Distinguish your work from team decisions.

Follow-up: you have only the RFQ lab. Present it as a production-style exercise and explain which deployment and operational checks remain. Do not invent incidents or measurements.

Logfire

Review instrumentation and privacy boundaries.

11. Which spans would you add to an RFQ review?

Start with the request span. Add bounded stages for validation, authorized retrieval, model attempts and output checks where they aid diagnosis. Record outcomes and workflow versions. Preserve each failed retry. Avoid putting request text or account identifiers in span names.

Follow-up: the trace has duplicate request spans. Check whether two integrations instrumented the same framework before adding more spans.

12. How would you verify that telemetry does not expose RFQ contents?

Define allowed fields, restrict captured arguments and headers, and inspect exports from synthetic requests containing recognizable fake secrets. Test error paths as well as success. Review URLs, exceptions and additional instrumentors. Scrubbing is a layer, not proof of complete removal.

Follow-up: an exception contains a payload. Sanitize it before export and keep enough non-sensitive error classification for diagnosis.

13. A slow request has no slow model span. What next?

Check admission wait, database pool acquisition, retrieval and time after generation. Inspect missing instrumentation and gaps between spans. Confirm that the model span measures the full attempt. Compare with the total request timer before declaring the trace complete.

Follow-up: queue time is absent. Instrument the admission boundary instead of attributing unexplained time to the provider.

14. Should a telemetry outage fail the business request?

Usually keep ordinary diagnostic export off the critical path, with bounded buffers and a documented drop policy. Observe exporter failures separately. Audit evidence required for a privileged operation may need stronger durability and a different availability policy.

Follow-up: buffers fill during an outage. Do not allow unbounded memory growth or indefinite blocking; decide which telemetry can be dropped and which operations must stop.

15. Can sampled Logfire traces establish service p99?

Only with a measurement design that supports that inference. Prefer unsampled request histograms for service percentiles. Traces selected because they are slow describe a biased population. Use them to diagnose individual requests and inspect overlaps.

Follow-up: all failures are retained but most successes are dropped. Show the sampling policy and compare against complete metrics before reporting a fleet latency figure.

Replayable traces

Review the replay fixture and limits.

16. What distinguishes replay from re-execution?

Replay supplies recorded responses to application logic. Re-execution calls current models or services and can produce new costs or effects. Keep a live executor out of the replay process. Missing fixtures must fail closed rather than fall back to a real tool.

Follow-up: replay returns a recorded ticket receipt. It must not create that ticket again.

17. What must you capture to reproduce an application decision?

Capture relevant code and workflow versions, configuration identities, ordered inputs, tool arguments and observed responses. Include clock or random inputs if they affect the decision. Keep immutable source versions. A sampled trace with omitted values may be insufficient.

Follow-up: privacy rules forbid raw payload storage. Use a reviewed synthetic equivalent and state that it reproduces the failure class, not the exact private run.

18. Why does replay diverge after a harmless refactor?

The refactor may change call ordering, defaults, serialization or clock use. Compare the first mismatched boundary. Decide whether behavior should remain exact or whether the fixture's contract was unnecessarily strict. Do not automatically update expected outputs to silence the test.

Follow-up: two independent reads swapped order. A dependency-based fixture may be appropriate; the sequential lab deliberately rejects that change.

19. Does a fixture hash make replay trustworthy?

A separately pinned digest detects changed bytes. It does not prove that the original record was accurate or prevent an attacker replacing both fixture and digest. Review provenance, access and storage protections. Keep artifact integrity separate from business truth.

Follow-up: a response was scrubbed. Hash the actual sanitized artifact and document the transformation instead of claiming byte-identical reproduction.

20. How would you replay concurrent tool calls?

Assign stable call IDs and record dependencies, inputs and results. Validate required partial ordering without forcing one incidental completion order. Preserve failures and cancellations. A single global sequence is simpler but can reject valid concurrent schedules.

Follow-up: both calls write the same record. This is a concurrency-control problem as well as a replay problem; specify the transaction or conflict rule and test both outcomes.

Claude Agent SDK

Review the SDK exercise and current primary sources. Verify release-specific options against your installed SDK and runtime.

21. How does using an agent runtime change your service design?

The runtime can take multiple model and tool steps. You must own its permissions, lifecycle, workspace, budgets and terminal outcomes. A response timeout must not leave an uncontrolled child running. Start with the smallest capability set the task needs.

Follow-up: extraction needs no tools. Use the text-only exercise before granting filesystem or terminal access.

22. Why is an allowed-tools list insufficient as a security boundary?

In the documented SDK permission model, it pre-approves named tools. Other capabilities can still be available under other rules. Inspect the effective tools and permission order. Enforce resource access in the executor and isolate the runtime.

Follow-up: an approval callback never fires. Check whether an earlier rule already approved the call; do not assume every tool passes through that callback.

23. How would you prevent one user resuming another user's session?

Map sessions to authenticated tenant and user scope on the server. Recheck access before resumption. Treat the session identifier as a lookup key, not proof of ownership. Apply retention and revocation policies to stored context.

Follow-up: a user loses access after the first turn. Deny further use of that protected context rather than relying on the original login.

24. The agent emits valid JSON and then ends with an error. Is the job complete?

Inspect the terminal result and independently verify the output contract. Preserve the failure reason. Decide which outputs are safe to release under the workflow policy; valid shape alone does not prove completed work or authorized effects.

Follow-up: a tool may already have written something. Reconcile its operation record before retrying the session.

25. How do you make an SDK budget useful in production?

Use it as one local bound and maintain an application ledger across parallel calls and resumed work. Reserve before admission, constrain call size and account for failed attempts. Reconcile unknown usage. Do not equate a local estimate with a guaranteed account invoice ceiling.

Follow-up: the process crashes before reporting usage. Keep the uncertain reservation visible until reconciliation resolves it.

Trajectory and multi-turn evals

Review the labelled conversation fixture.

26. How can an agent give the right answer and still fail evaluation?

It may use forbidden data, propose an unauthorized action or ignore an approval boundary. Grade final fields and observable behavior separately. Distinguish a denied proposal from an executed violation, but do not hide either in an answer-quality average.

Follow-up: the executor safely denied the call. Report enforcement success and unsafe model behavior as separate results.

27. How would you test whether corrections survive a long conversation?

Use reviewed conversations with corrections at different positions, distracting turns and explicit final fields. Check account scope and action restrictions throughout. Compare failures by length and correction type. Reset state between independent cases.

Follow-up: “proceed” follows “review only.” The expected behavior must preserve that restriction; vague wording is not new trade authorization.

28. Which checks should use an LLM judge?

Use deterministic checks for exact fields, tool identities and verifiable authorization rules. A judge can assess qualities such as explanation clarity against a rubric and evidence. Calibrate with held-out, human-reviewed labels and measure false passes and false failures.

Follow-up: judge agreement is high overall but low on unsafe cases. Inspect the unsafe slice and block release on policy violations regardless of the average score.

29. How do you compare two agent versions fairly?

Use the same cases and controlled dependencies. Pin dataset, rubric and configuration identities. Repeat noisy trials, retain timeouts and report per-slice results. Separate independent cases from repeated trials. Show the size and uncertainty of a change.

Follow-up: the candidate ran against newer documents. The comparison confounds agent and data changes; rerun a controlled comparison or label that limitation.

30. What belongs in the CI regression gate?

Fast deterministic contract and safety checks should run on relevant changes. Approved provider evaluations need separate budgets, version records and failure handling. Set thresholds before viewing candidate results. A security veto should not disappear inside a weighted quality score.

Follow-up: a vendor alias changes without a commit. Scheduled sentinel evaluations can detect changed behavior; investigate data and tool changes before assigning the cause.

p50, p95 and p99 by stage

Review the numerical examples and Prometheus queries.

31. What information must accompany a p99 number?

Name the measured operation, population, time window, sample count and units. State whether it includes failures, retries and queue wait. Explain whether the value is an exact sample quantile or a histogram estimate.

Follow-up: only ten requests occurred. Tail resolution is coarse; show the count and individual failures rather than implying a precise distribution.

32. Can you add retrieval p95 and model p95 to obtain request p95?

No. Each percentile can describe different requests. Parallel work can overlap, and request time includes other stages. Measure total latency directly. Use stage percentiles to locate population changes and traces to inspect individual critical paths.

Follow-up: stages run strictly sequentially. Individual durations add per request, but their separately calculated percentiles still need not add.

33. How do you combine percentile data from several pods?

For compatible classic histograms, aggregate bucket rates across the intended instances, preserving the bucket boundary label, then calculate the quantile. Keep service and environment scope correct. Averaging pod p95s loses distribution and traffic-weight information.

Follow-up: one pod changed bucket boundaries. Restore a compatible measurement scheme or query the populations separately before claiming a fleet quantile.

34. Queue p99 rose, but model p95 stayed flat. What would you investigate?

Check admitted concurrency, pool waits, worker capacity and retry amplification. Compare offered load with completed throughput and rejection rate. A stable provider stage does not rule out overload before provider dispatch.

Follow-up: error rate also rose. Determine whether requests are being shed earlier; lower observed latency after rejection can conceal worse user outcomes.

35. How should timeouts and skipped stages affect latency metrics?

Record the actual observed wait for timed-out attempts with their outcome. Preserve unknown external effects separately. A cache hit that skips model inference should not add a zero-duration model sample. Record the full client request independently.

Follow-up: a streaming request never releases an answer token. Count it as a no-token outcome rather than giving it a zero time-to-first-token.
