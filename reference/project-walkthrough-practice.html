Explain a project clearly

Use this with lessons 0637 and 0640. The interviewer needs to understand the user's problem, the system boundary and your contribution. Start there before listing technologies. Prepare a short introduction, a five-minute walkthrough and deeper answers on demand.

Your RFQ project: a safe starting point

The confirmed description is a trader-facing RFQ blotter that displayed requests received from an upstream Bloomberg-integrated system and let traders access instrument-specific pricers and downstream trade-booking workflows. This does not establish that you built the Bloomberg integration, pricing models or booking service. Claim those only if you did.

Practise this editable introduction:

“I worked on a trader-facing RFQ blotter supporting front-office workflows. It displayed RFQs from an upstream Bloomberg-integrated system and gave traders access to instrument-specific pricers and downstream booking workflows. My responsibility was [actual scope]. One important challenge was [real problem]. I chose [decision] because [constraint], and we checked the result through [actual evidence].”

Replace every bracket before using it in an interview. Risk-limit checks, rates monitoring and AI parsing may be separate projects or learning exercises. Do not add them to this project's history unless they were actually part of it.

A five-minute walkthrough

  1. First 30 seconds: user, problem and why it mattered.
  2. Next 30 seconds: your role, team boundary and project status.
  3. Next minute: trace one request through the actual components.
  4. Next minute: one decision, the rejected alternative and its cost.
  5. Next minute: one failure path and how you tested or handled it.
  6. Final minute: observed result, limitations and what you would change.

Use one simple diagram. Mark systems you owned differently from external dependencies. Show the unhappy path as well as the happy path. Give scale numbers only when you know their source and can share them. “I do not have a verified figure” is better than guessing throughput.

Questions and answer checkpoints

1. What did you personally build?

Name the components, decisions and delivery work you owned. Explain what teammates or upstream teams owned. “I implemented the display and navigation flow; another team owned the upstream integration” is useful if true. Avoid using “we” to obscure your scope.

Follow-up: which decision would have been different without your contribution?

2. Walk me through one RFQ.

Start with the actual input contract. Explain parsing or mapping, validation, identity, storage if any, state shown to the trader and the action that opens the next workflow. State where the trace ends if you did not own pricing or booking.

Follow-up: what happens to a malformed or incomplete record? Describe implemented behavior first, then a proposed improvement.

3. How did you handle duplicate or out-of-order data?

Identify the actual record key and update semantics. Explain whether the system used a source sequence, version, timestamp or another contract. State how conflicts and late records were treated. Do not assume arrival order proves business order.

Follow-up: if you did not implement this boundary, say which team owned it and what guarantees your component relied on.

4. Why did you choose this stack?

Connect each important choice to a requirement: existing team support, browser behavior, API contracts or deployment constraints. Compare one credible alternative and the cost you accepted. Distinguish choices you made from technologies already mandated.

Follow-up: what changed requirement would make you reconsider the choice?

5. What was the hardest technical problem?

Pick one concrete problem. Explain the symptom, constraints, alternatives and evidence behind your decision. A useful answer can involve data correctness, UI state, integration failure or safe navigation; it does not require dramatic scale.

Follow-up: what was your first incorrect hypothesis?

6. How did you test it?

Name implemented unit, contract, integration or UI tests and what each proved. Explain one important failure fixture. Distinguish mocks from checks against real dependencies. If coverage was limited, describe the remaining risk honestly.

Follow-up: what defect could pass your existing tests?

7. How did you prevent unauthorized or duplicate actions?

Describe the actual authorization owner and action boundary. Opening a booking workflow is not the same as executing a trade. Explain which checks belonged to your component and which belonged downstream. Do not claim that hiding a button enforced backend permissions.

Follow-up: a user repeats an action after a timeout. What did the actual contract guarantee, and what remains uncertain?

8. What was the business impact?

Use verified evidence: adoption, workflow feedback, a supported action or an operational result you observed. Separate a design goal from a measured outcome. If no quantitative study exists, explain the observable change without inventing a percentage improvement.

Follow-up: what other changes could have contributed to that result?

9. What would you improve now?

Select a limitation connected to evidence. Explain the expected benefit, migration risk and smallest useful next step. Avoid dismissing the original design without acknowledging its constraints.

Follow-up: how would you show that the improvement worked?

10. How do you explain an AI project differently?

Keep the same project structure, then add the model's responsibility, deterministic boundaries, evaluation set, failure handling and cost/latency limits. Separate output schema validity from correctness. Explain which actions need human approval and how a failed provider call degrades.

Follow-up: if this is only a portfolio project, label it as such and state which services, loads and integrations were simulated.

A rehearsal that exposes gaps

Draw the system from memory and ask a partner to stop you at every vague claim: “fast,” “scalable,” “reliable,” or “we handled it.” Replace the claim with a mechanism or evidence. Then answer the same project question for a recruiter in 90 seconds and an engineer in five minutes.

Check that both versions agree on your role and results. Keep confidential details out of diagrams and recordings. Tomorrow, rehearse a different failure path. Ask your teacher to review the story after you fill in the confirmed project details.
