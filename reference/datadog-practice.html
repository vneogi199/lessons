Follow one slow request from alert to cause

First distinguish logs, metrics and traces. Then inspect the safe logging fixture. Finally design a dashboard and alert. Sending telemetry to Datadog requires approved credentials, destination and budget; nothing is installed or sent here.

Three views of one request

A log is an event record, such as “lookup timed out.” A metric summarizes measurements over time. A trace follows one request through spans of work. Think of a receipt, a daily sales chart and the route a delivery took. Each answers a different question.

An API request takes 900 ms. Its trace shows 700 ms waiting for a database connection and 20 ms executing SQL. Adding a SQL index is not the first response: investigate pool saturation and transaction duration. The trace identifies where to look; correlated logs can explain the failure.

The Datadog Python SDK can instrument supported frameworks. Start it early enough to instrument imports and choose versions supported by your runtime. Read Python tracing setup and the configuration reference.

Set stable service, environment and release version values. Configure a private Agent connection and the approved Datadog site. Keep API keys in the deployment's secret system, not source files. Do not expose trace intake ports publicly. A container's localhost is not automatically the host or another container.

# Example only: requires an already-installed, approved SDK/Agent and app.
DD_SERVICE=rfq-api DD_ENV=staging DD_VERSION=release-example \
DD_LOGS_INJECTION=true ddtrace-run uvicorn app:app

Log injection adds correlation attributes; it does not itself configure collection of stdout. Include dd.trace_id, dd.span_id, dd.service, dd.env and dd.version in the JSON formatter as strings. Check the exact library version and correlation guidance. Missing or zero trace IDs outside an active trace should not be fabricated into a real correlation.

If using OpenTelemetry, choose a supported collector/exporter path and verify propagation. Do not auto-instrument the same framework twice with competing SDKs. For jobs, propagate permitted context and define whether retries are child attempts or linked work. Never treat an incoming trace header as authentication.

Protect data before it leaves the process

Use allowlisted event names and structured fields. Prefer route templates such as /rfqs/{id}, not raw URLs with IDs or query strings. Exclude authorization headers, cookies, bodies, prompts, customer names and connection strings. A regular expression is a backup control, not proof that every secret was removed.

The supplied formatter emits only an event code, level, service metadata and valid injected trace/span IDs. Unknown messages become a fixed event. Exception text is deliberately omitted because it can contain private input. This illustrates minimization; it does not sanitize every other logger or exporter in an application. Test the complete pipeline with synthetic canary values before using real data.

Datadog supports log processing rules, including mask_sequences; verify where a rule runs. A cloud-side filter cannot undo sensitive data already sent across the network. Apply source-side controls and test collector processing. See Agent configuration fields.

Alerts that lead to action

Define a synthetic staging exercise: one hundred requests, ten controlled failures and one delayed dependency. Predict error rate 10/100 = 10%. Create a monitor scoped to the test service and environment. Choose an evaluation window, minimum traffic, recovery threshold and no-data policy. A monitor query depends on the actual metric names and types, so inspect those before copying syntax.

Route the exercise to a test destination. Verify alert, acknowledgement and recovery, and link a runbook with the first diagnostic queries and rollback authority. “No data” can mean collector failure, not a healthy service. Avoid paging on a single rare slow request or suppressing an outage with an excessive minimum-volume threshold.

Use SLO burn rates for sustained user-impact detection where appropriate. Attach deployment versions to investigations. Continuous profiling can reveal CPU or allocation hotspots, but measure its overhead and data capture settings before enabling it. A flame graph is evidence of sampled stacks, not a complete causal history.

Control observability costs

Budget log bytes, retention/indexing, custom metric series, traces and optional profiling separately. Pricing and plans change; inspect the account's actual contract. Avoid user_id, request_id and raw URL as metric tags. They can create many series. Request IDs belong in appropriately controlled event records, not every metric dimension.

Filter noisy safe events at the source, shorten unnecessary retention, and sample deliberately. Keep audit obligations separate from debug sampling. Preserve rare errors through a tested policy without assuming sampling retains every important incident. Compare usage before and after a change and confirm diagnostic value remains.

Guided exercise

  1. Run the offline logging tests and inspect their expected fields.
  2. In an approved staging service, instrument one route and one dependency. Send synthetic success, failure and timeout requests.
  3. Find the service, open a trace, and navigate to its correlated log. Confirm release tags match and canary secrets are absent.
  4. Build the panels above using discovered metric names. Trigger the test monitor, then restore the service and verify recovery.
  5. Record SDK/Agent versions, propagation path, sampling policy, data destination, cost estimate and untested boundaries. Remove test monitors through the approved change process.
Logs have trace IDs but no linked trace. What next?

Check active context, ID formatting, service/environment tags, collection/parsing, retention and sampling. Do not conclude that injection alone shipped a trace.

Why not tag every metric with request_id?

It creates high cardinality and often cost without useful aggregation. Use bounded dimensions and investigate individual requests through traces and logs.

MCQ: source-side redaction happens “before export” or “after export”?

Before export. Later filtering cannot retract information already transmitted.
