Run an outbox and recover a saga

This lab fills the implementation gap after lessons 0438 and 0439. First trace the pictures. Then run the demo and tests. Finally, explain what the local checks prove and which production assumptions remain untested. All records are fictional.

Save the work and the intention together

Imagine a shopkeeper writing an order and a note for the delivery team on the same receipt. Either both are saved or neither is. Later, a messenger copies the delivery note to another tray. If the messenger forgets that it delivered the note, it can copy it twice. The delivery team needs its own record of completed work.

source.sqlite             broker.sqlite                consumer.sqlite
order + outbox ──relay──→ message ──consume───────────→ inbox + effect
one local commit          separate local commit        one local commit
     ↑ record sent             ↑ acknowledge AFTER consumer commit

create() commits the order and event in one SQLite transaction. A repeated order ID with the same amount is a replay; a different amount is rejected. The event ID remains stable. relay_one() copies one pending event to the fake broker, commits there, then marks the source row sent. These two stores deliberately do not share a transaction.

Interrupt after broker commit and before the sent marker. On reopening, the event still appears pending, so the relay publishes it again. This is expected. consume_one() inserts its inbox identity and effect in one transaction. A repeat checks the saved payload and skips the effect. Only afterwards does it acknowledge the broker record. See the transactional outbox pattern for the dual-write problem.

InterruptionStored resultRecovery
Before producer commitNo order or eventRetry creation with the same identity.
After source commitPending outbox rowRelay resumes after reopening.
After publish, before sent markerMessage exists; outbox still pendingDuplicate delivery is possible; deduplicate the effect.

After effect, before acknowledgementEffect and inbox existRedelivery finds the prior result, then acknowledges.

The exercise covers one consumer and tenant. A real inbox identity normally includes that scope. Keep deduplication records for the documented replay window. Do not delete an inbox row while old events can still arrive unless another durable rule protects the effect. The sequential relay preserves its own sequence here; multiple workers and broker partitions need an explicit per-entity ordering design.

Recover a business workflow, not a global transaction

reserve → charge → completed
             └─ declined → release → compensated

Any action: effect may commit before the saga records the result.
Repeated failures: persisted attempt budget → manual_review

The saga reserves a fictional item, then asks a fake service to charge. A definitive decline moves to release. Successful release means compensated. An unavailable dependency is not a decline: the current action remains pending. A charge that may have succeeded must be reconciled before releasing resources or attempting a second charge.

advance() loads the action from sagas.sqlite. It first asks the service for the stored receipt keyed by saga and action. If found, it records the result without repeating the effect. Otherwise, it saves an attempt before dispatch. The fake service commits its receipt and effect together in another database. The saga then saves its next state and history atomically. This makes the effect/checkpoint gap visible instead of hiding it in one transaction.

Three failed dispatches exhaust the action's budget. The next advance records manual review. A restart does not reset attempts. Recovery checks for an already committed receipt before exhausting the budget, because the last permitted attempt may have succeeded. Production also needs scheduled retry times, jitter, deadlines and ownership controls; the lab uses explicit calls so you can see each transition.

Compensation is a new business action. Releasing the reservation is safe to repeat under the fake service's operation key. A real shipment or irreversible payment may need another procedure. If release cannot complete, the reservation stays active and the workflow enters manual review. Nothing silently pretends the original action was rolled back. Compare this with saga orchestration; it is not two-phase commit.

Work through one failure at a time

  1. Open lab.py. Identify the five separate database files and every transaction boundary.
  2. Run python3 -B practice/durable-workflows/demo.py from the repository root. Predict the delivery and effect counts first: two deliveries, one effect.
  3. Run the tests from the README. Inspect the cases that close and reopen state after publication or a service effect.
  4. Trace the declined-charge case. It must release the reservation, including when the release committed before a checkpoint was saved.
  5. Trace failed compensation. After the retry budget, explain why manual review leaves the resource visible instead of erasing it.

Python's SQLite connection context manager commits on normal exit and rolls back on an exception when a transaction is active; it does not close the connection. The lab closes connections explicitly when simulating restart. See the connection context manager.

Know what still needs a real environment

This is a runnable local implementation with file-backed checkpoints, not a production broker or workflow engine. The tests inject exceptions and reopen connections; they do not simulate power loss, process termination, network partitions or concurrent workers. The fake provider's receipt lookup is authoritative. A real provider may not offer that contract.

Before adding replicas, implement and test fenced claims, concurrency control and per-entity ordering. Before adding external effects, verify idempotency, uncertain-outcome reconciliation and authorization at dispatch. Add due-time scheduling, bounded quarantine, observability, retention and an audited operator recovery path. Do not introduce a global transaction merely to make the diagram appear atomic.

Interview: why is the outbox row still pending when the broker has the event?

The publisher crossed two commits. The broker accepted the event, but the relay did not record confirmation in the source database. Retrying is necessary to avoid loss and can duplicate delivery. The consumer must couple deduplication and its local effect atomically.

Interview: a payment timed out. Why not compensate immediately?

The payment may have committed. Resolve the operation using its stable key and the provider's authoritative status. If you cannot establish the outcome, preserve uncertainty and request review. A timeout alone does not justify an inverse business action.

MCQ: after reopening, the service has a receipt but the saga has its old state. A) Repeat with a new key. B) Record the prior result.

B. Reconcile the saved receipt and advance the checkpoint. A new key can create a second effect.
