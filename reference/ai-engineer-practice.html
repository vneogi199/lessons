A focused study order

  1. Python and data: typing, async, SQL, tests, FastAPI and Pydantic. Complete the API lifecycle and NumPy/Pandas/Polars practice. Pass malformed-input and dependency-failure cases before adding a model.
  2. Model foundations: study the ML and LLM-internals tracks, then explain train/validation/test separation, leakage, attention, sampling and context limits. Contrast a classifier with a generator. A fluent explanation is not a benchmark.
  3. Model integration: use one provider, structured output, bounded tool calls and streaming. Complete typed output and tool execution.
  4. Retrieval and evaluation: use one vector store, lexical and hybrid baselines, reranking and a versioned holdout. Build the RAG project below.
  5. Workflows and agents: add durable state, approval, permissions and effect reconciliation. Build the triage project below. Add a graph framework only when branching or recovery requires it.
  6. Operate one stack: Docker, one cloud, CI/CD, redacted traces, release gates, cost and incident handling. Use trace practice and delivery practice.

Keep advanced Kubernetes, additional clouds/vector stores and legacy enterprise connectors optional until the target role needs them. Prioritize evidence from one complete system over several untested framework demos. Study one section per session; attempt its changed-condition exercise tomorrow. Own the AI-generated diff

Use a spec-first loop: clarify unknown requirements → write acceptance criteria → inspect existing code → plan a small change → implement → read the complete diff → run independent tests → record remaining risks. Ask targeted questions about identity, data, effects and failure behavior rather than requesting unlimited questions. Do not let the coding assistant weaken a failing test to make its patch pass.

  1. Verify every new API against the installed package version or official contract. Import/type checks can catch invented names; a mocked method can conceal one.
  2. Trace untrusted input through authentication, authorization, validation, persistence and external effects. Read callers as well as the changed function.
  3. Inspect errors: swallowed exceptions, retry multiplication, lost transactions, resource leaks, raw secret logging and success responses after partial failure.
  4. Review new dependencies and configuration for provenance, permissions and secret exposure. A secret scanner is a layer, not proof of absence.
  5. Use unit tests for pure policy, integration tests for database/auth boundaries, contract tests for providers and end-to-end tests for the user outcome. Mock the external boundary, not the rule being tested.
  6. Run a mutation drill: deliberately remove one security check in an isolated copy and verify the appropriate test fails. Restore the original before proceeding.

This small contract fixture handles only post-authentication validation; it is not a payment service.

def validate_adjustment(actor, payload):
    if not actor.get("can_adjust"):
        raise PermissionError("role denied")
    if set(payload) != {"tenant", "amount_cents"}:
        raise ValueError("unexpected schema")
    if payload["tenant"] != actor["tenant"]:
        raise PermissionError("tenant denied")
    amount = payload["amount_cents"]
    if type(amount) is not int or not 1 <= amount <= 10000:
        raise ValueError("invalid amount")
    return {"tenant": actor["tenant"], "amount_cents": amount}

actor = {"tenant": "A", "can_adjust": True}  # Trusted, verified context.
assert validate_adjustment(actor, {"tenant": "A", "amount_cents": 50})["amount_cents"] == 50
for payload, error in [({"tenant": "B", "amount_cents": 50}, PermissionError),
                       ({"tenant": "A", "amount_cents": True}, ValueError),
                       ({"tenant": "A", "amount_cents": -1}, ValueError)]:
    try:
        validate_adjustment(actor, payload)
    except error:
        pass
    else:
        raise AssertionError("unsafe proposal accepted")
try:
    validate_adjustment({"tenant": "A", "can_adjust": False}, {"tenant": "A", "amount_cents": 50})
except PermissionError:
    pass
else:
    raise AssertionError("role bypass")

A model comparison that includes failures

Choose one task first: extract typed fields, classify a work order, or answer a cited question. Build development and held-out datasets separated by source/customer/time as appropriate. Freeze the holdout before tuning prompts. Run each candidate on the same cases with recorded model, prompt, decoding settings, tools and source revision. Randomize or interleave run order to reduce timing bias.

Store case ID, slice, correctness, schema validity, authorization violations, timeout/error, time-to-first-token, completion latency, input/output usage and total attempt cost. Count all retries. Compare task success and critical-slice failures before cost. Unknown usage stays unknown; it must not become zero cost. For self-hosting include billed GPU time, utilization, idle capacity and operational overhead, not only token arithmetic.

from decimal import Decimal
from math import ceil

def summarize(rows):
    if not rows:
        raise ValueError("empty benchmark")
    costs = [r["cost"] for r in rows]
    times = sorted(r["seconds"] for r in rows)
    successes = sum(r["ok"] for r in rows)
    total = None if any(c is None for c in costs) else sum(costs, Decimal(0))
    return {"success_rate": successes / len(rows),
            "p95_seconds": times[ceil(.95 * len(times)) - 1],
            "cost_per_success": total / successes if total is not None and successes else None}

# Fictional observed outcomes, not live model prices or recommendations.
cheap = [{"ok": True, "seconds": 1, "cost": Decimal("0.01")},
         {"ok": False, "seconds": 5, "cost": Decimal("0.04")}]
strong = [{"ok": True, "seconds": 2, "cost": Decimal("0.02")},
          {"ok": True, "seconds": 3, "cost": Decimal("0.02")}]
assert summarize(cheap)["cost_per_success"] == Decimal("0.05")
assert summarize(strong)["cost_per_success"] == Decimal("0.02")
assert summarize([{**cheap[0], "cost": None}])["cost_per_success"] is None
assert summarize(cheap)["p95_seconds"] == 5

Two cases illustrate arithmetic, not reliable p95 estimation or a production decision. Timeouts contribute their observed deadline duration and remain failed/censored outcomes, not successful completion times. Use enough representative cases, repeated trials and paired uncertainty estimates; repeated outputs from one case are not independent new tasks. Inspect results by task length, language, permission and difficulty.

Project one: evaluated knowledge assistant

Build a small policy-document assistant with citations, abstention and two tenant scopes. Use FastAPI, PostgreSQL plus one chosen vector store, a durable ingestion worker and one provider. Keep framework choice secondary to the acceptance contract.

  1. Data contract: assign immutable document/version IDs, source pages, tenant ACLs and ingestion status. Implement upload limits, parse failures and deletion propagation. Keep ingestion independent of the query path.
  2. Baseline: create a manually reviewed dataset with answerable, unanswerable, stale, conflicting and forbidden-document cases. Start with keyword retrieval and an explicit no-evidence response.
  3. Retrieval: add dense and hybrid retrieval, then reranking only if paired evidence supports it. Enforce ACLs before external model/reranker exposure.
  4. Answer API: define request and response models, citations with document versions, structured errors and a response mode distinguishing answered/insufficient-evidence/unavailable. A citation existing is not proof that it supports the claim.
  5. Evaluation: record recall@k, ranking quality, supported claims, abstention behavior, permission failures, latency and cost. Use deterministic citation checks plus calibrated human/judge review.
  6. Release: containerize, gate CI on tests/evals, deploy only to an approved environment, run smoke/load tests and rehearse rollback to the previous model/prompt/index configuration.

Acceptance evidence: an allowed answer with supporting passages; a denied cross-tenant query; deletion removing retrievable evidence; a provider timeout producing a safe error; and a reproducible baseline/candidate report. Deliver source, locked dependencies, configuration template without secrets, dataset provenance, architecture diagram, runbook and measured limits.

Project two: work-order triage with approval

Use a standalone synthetic tracker because no Week 1 tracker contract has been supplied. Ingest a work order, retrieve the allowed policy, propose category/priority/owner, validate it, request approval when required, then record an assignment. Never close orders or send purchases autonomously in the MVP.

Persist order, proposal version/hash, evidence IDs, approval actor/time, operation ID, execution status and audit events. Define states received → proposed → needs_review/approved → executing → succeeded/failed/uncertain. Keep uncertain external effects distinct from ordinary failure. Resume from durable state; do not trust a model's claim that a tool ran.

def may_execute(proposal, approval, actor, now):
    # Pure policy fixture; caller atomically checks persisted current state.
    return (actor["can_approve"] and actor["tenant"] == proposal["tenant"]
            and approval["tenant"] == proposal["tenant"]
            and approval["reviewer"] == actor["id"]
            and approval["hash"] == proposal["hash"]
            and approval["expires_at"] > now
            and proposal["status"] == "approved")

p = {"tenant": "A", "hash": "synthetic-v1", "status": "approved"}
a = {"tenant": "A", "reviewer": "u1", "hash": "synthetic-v1", "expires_at": 20}
u = {"id": "u1", "tenant": "A", "can_approve": True}
assert may_execute(p, a, u, 10)
assert not may_execute({**p, "hash": "synthetic-v2"}, a, u, 10)
assert not may_execute(p, a, u, 20)
assert not may_execute(p, a, {**u, "tenant": "B"}, 10)

The hash is a fixture label, not a cryptographic implementation. Production must compute a canonical payload hash, verify authenticated reviewer authority and atomically claim the operation. The boolean function does not prevent concurrent execution. Use a database uniqueness constraint and effect reconciliation to handle retries; an idempotency header works only if the upstream contract honors it.

Test misclassification, unknown owner, injected ticket text, revoked access, expired/changed approval, duplicate delivery, worker crash and timeout after assignment. Compare a fixed workflow with a bounded agent on identical cases. Report classification confusion matrix, per-class precision/recall, valid-tool rate, actual assignment success, human escalation, latency and cost. Model self-reported confidence alone is not a safe approval gate.

Advanced depth after the two projects

  • ML judgment: distinguish class imbalance from data leakage; use stratified/group/time splits appropriate to deployment. Fit preprocessing on training data only. Compare accuracy with per-class precision/recall, macro-F1 and a simple baseline. Calibrate probability thresholds against error costs.
  • Open-weight serving: estimate weights as parameter count × bytes per parameter, then add KV cache, activations, runtime overhead and concurrency headroom. Quantization reduces some memory and can change quality; it does not guarantee faster inference. Benchmark prefill/decode, time-to-first-token and saturation separately. Check model license and provenance.
  • LoRA and fine-tuning: first determine whether the problem is missing evidence, task behavior or output consistency. RAG supplies changing knowledge; fine-tuning adapts behavior and is not a reliable live database. LoRA trains low-rank update matrices while the base weights are frozen; rank, target modules and data quality affect the tradeoff. Compare prompting, RAG and an adapter on the same held-out suite. Prevent source-family overlap and inspect regressions outside the tuned task.
  • Release design: version model, prompt, retrieval configuration, schema and adapter together. Shadow execution observes candidates without effects; a canary limits operational exposure; randomized A/B testing estimates a product difference. They are not interchangeable. Define stop criteria, permission invariants and rollback before starting.

Sources: LoRA concepts and the existing vLLM capacity lesson. No training or GPU benchmark is performed. Acceptance: write a decision record identifying the failure you intend to fix, the cheaper baseline, the controlled experiment and the evidence that would make you reject tuning.
