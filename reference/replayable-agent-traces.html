Replayable agent traces

A trace shows what a run did. A replay fixture supplies recorded responses so you can run application logic again without calling the original services. An ordinary sampled trace may omit bodies, ordering or configuration, so it may not contain enough information for replay.

Think of replay as practising a conversation with cue cards. Your code asks a question; the fixture checks that it is the expected question and returns the recorded answer. If the question changes, the exercise stops instead of inventing an answer.

Keep three operations separate

OperationWhat happensRisk
InspectRead recorded eventsPrivate information may be exposed
ReplayRun code with recorded model/tool responsesAn accidental live fallback can repeat an effect
Re-executeCall current models and servicesNew cost, different outputs and real side effects

The supplied replay adapter has no network client or dispatch function. It fails on an unexpected call, changed arguments, missing response or unused response. This makes accidental live fallback impossible within that adapter. Keep the real executor out of the replay process too.

Record a reproducible boundary

Keep a schema version, application revision, workflow version, prompt hash, model identifier, tool schema version and fixture identity. Each recorded call has a sequence number, tool name, canonical arguments and response. Preserve recorded errors as well as successes. Capture the application's clock and random inputs when they affect decisions.

For concurrent tools, a single global sequence may reject valid alternative completion orders. Use per-call IDs and explicit dependencies for those workflows. The supplied lab intentionally covers sequential calls only. Its SHA-256 digest detects accidental fixture changes when compared with a separately pinned digest; it does not authenticate a maliciously replaced fixture and digest.

Recorded call 1: read_limit({account: "A"}) → {limit: 10}
Recorded call 2: read_exposure({account: "A"}) → {exposure: 8}
Request: add 3 units
Replay decision: 8 + 3 > 10 → needs_review

Change the proposed quantity to one. The same read responses can support the changed decision, but this is now a counterfactual test. Do not label it the original run. Change the account to B and the adapter must reject the argument mismatch.

Do not replay writes against production

A recorded “ticket created” result represents a past effect. During replay, return that fixture result without creating a ticket. Live recovery is a separate path: verify current authority, find the original operation key and reconcile the external result. Checkpoint replay alone cannot establish exactly-once effects. Continue with the existing approval and checkpoint lab.

Store sanitized fixtures separately from operational traces. Scrubbing can remove information needed for exact replay; then use a synthetic equivalent and document the substitution. Keep access control, retention and deletion policy on replay artifacts. Do not save hidden model reasoning. Tool proposals, observations, policy decisions and terminal reasons are sufficient boundaries for these tests.

Run the failure cases

From the practice directory, run the supplied unittest suite in an existing Python environment. Predict which cases fail before reading the assertions. The suite tests normal replay, changed arguments, missing calls, unused calls and a changed fixture digest. The adapter makes defensive copies so mutations by a caller cannot rewrite later fixture values.

Interview: does temperature zero make a replay fixture unnecessary?

No. Provider revisions, retrieval changes, tool state and execution timing can change results. A recorded boundary isolates application behavior. A fresh model evaluation answers a different question.

MCQ: the fixture has no response for a proposed tool. Choose: A) invoke the live tool; B) stop with a replay mismatch.

B. Falling back to a live tool invalidates isolation and can repeat writes. Add a reviewed fixture only after deciding what the changed behavior should be.
