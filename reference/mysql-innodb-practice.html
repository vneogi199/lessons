Understand the work behind a MySQL query

Use three short sessions: row storage and SQL, plans and transactions, then operations. Read each example before trying the worksheet. The SQL targets MySQL 8.4 with InnoDB and has not run here. No server or driver is installed.

Where does a row live?

Imagine a filing cabinet ordered by order number. Its main directory leads to the actual order record. A customer directory gives you order numbers, which you then look up in the main cabinet. This resembles an InnoDB clustered index and a secondary index.

InnoDB stores row data in the clustered index, normally organized by the primary key. Secondary records include the primary-key value used to locate the row. A wide primary key therefore increases secondary-index storage too. If no suitable user key exists, InnoDB chooses or creates a clustered key according to its rules. Prefer an explicit stable key. See clustered and secondary indexes.

An index on (customer_id, created_at, id) can narrow a customer's orders and support ordered traversal. It is not equally useful for searching only created_at across all customers. A covering query can get its required values from the index without fetching the full row. Every extra index also costs storage, cache space and write maintenance.

Pages, memory and recovery

The buffer pool caches InnoDB pages. A cache miss may require storage I/O. Dirty pages contain changes not yet written back to their data files. Redo supports crash recovery; undo supports rollback and older row versions. The binary log records changes for replication and recovery workflows; it is not the same as InnoDB redo.

Commit latency depends on configured durability, storage and workload. Do not promise zero loss just because a transaction returned success without checking those settings and the failure model. Long transactions can retain old versions and delay purge. Monitor transaction age, buffer pressure, disk latency and lock waits together. See InnoDB architecture.

Practise SQL on orders

The worksheet uses customers and orders with integer cents. Predict a grouped total, a latest-order window query and a keyset page. NULL is not zero: comparisons with NULL need IS NULL, and aggregates have specific NULL rules. Choose decimal or integer units for money, not approximate floating-point arithmetic.

Use utf8mb4 for text and deliberately choose collation: equality and ordering may ignore case or accents. Keep timestamps in a documented time basis. MySQL TIMESTAMP and DATETIME have different conversion behaviour; test the driver/session time zone. Do not assume PostgreSQL casts, JSON operators, conflict handling or RETURNING syntax transfer unchanged.

Bind values through the selected driver's parameter API. Allowlist dynamic identifiers. Use a bounded connection pool; pool size across all replicas must fit database capacity. Return connections with transactions resolved and session state reset. A timed-out request must not leave an idle transaction holding locks.

Read a plan before adding an index

EXPLAIN estimates the access path. EXPLAIN ANALYZE executes the query and reports observed iterator work. Use it on approved data with safe statements and limits. Compare estimated and actual rows, loop counts, sorting and access paths; do not add nested iterator times as if they were independent. See MySQL EXPLAIN.

A selective predicate can still be slow if the index is missing, a function blocks useful access, or many random row lookups follow. Compare a range predicate on created_at with wrapping it in DATE(). Rewrite only if semantics remain correct. Tiny tables may reasonably use a scan. Use representative data distribution before judging an index.

For latest order per customer, ROW_NUMBER partitions by customer and orders by created_at DESC, id DESC. The ID breaks timestamp ties. An index helps some access patterns but does not guarantee every window query avoids sorting. For pagination, a stable composite cursor avoids the increasing skip work of a large OFFSET; concurrent updates still need a defined consistency policy.

Snapshots and locks answer different questions

InnoDB's default isolation is REPEATABLE READ. Ordinary consistent reads normally reuse a transaction snapshot established by the first consistent read; READ COMMITTED takes a new snapshot for each consistent read. Locking reads and writes have different current-state behaviour. Do not infer that a locking read must return the same rows as a prior snapshot read. See isolation semantics.

A next-key lock combines an index-record lock with the preceding gap. Range locking can block inserts into an interval, not only changes to returned rows. The exact locks depend on index access, predicate and isolation. Unique-key equality differs from a range scan. READ COMMITTED reduces gap locking in many searches, but does not remove every lock or every deadlock.

Try two sessions on the worksheet's account row: A locks it; B attempts to update it and waits. A rolls back; B proceeds and then rolls back too. For a deadlock drill, lock two rows in opposite order. On a deadlock error, retry the whole business transaction within a deadline using fresh reads and idempotent effects. Do not blindly replay only the last statement.

Enforce balance or inventory invariants with atomic conditions, constraints and appropriate transactions. A read followed by an unchecked update can lose another writer's change. External calls inside long transactions increase lock duration and make failure recovery harder.

Deliver schema changes safely

Many MySQL DDL statements cause implicit commits. Wrapping ALTER TABLE in a transaction does not provide PostgreSQL-style rollback expectations. See implicit commit rules.

Instant, in-place and copy algorithms have operation/version-specific limits. “Online” does not mean no metadata locks, no resource pressure or no replica lag. Use expand-contract: add compatible structures, deploy compatible readers/writers, backfill bounded batches, validate, switch, and remove old structures only after the rollback window. Test the chosen algorithm and lock behaviour first.

Use slow-query evidence and Performance Schema to find waits, then correlate application latency. Keep parameter values and credentials out of public diagnostic artifacts. Configure least-privileged accounts and verified TLS. Test backup restore plus binary-log recovery to a chosen point. Replicas are not backups; replication can copy a mistaken delete. Continue with the GTID, replication and failover drills.

Practice and interview checks

  1. Read the SQL fixture. Predict customer 1's total: 4,000 cents, and latest order: ID 3.
  2. Explain why the customer/date index helps one-customer pagination but not necessarily a date-only report.
  3. On a future disposable database, record plans before and after indexing. Do not invent an expected speedup.
  4. Run the two-session blocking drill and inspect the wait. Repeat under a reviewed different isolation level.
  5. Write a migration plan with backfill limits, metadata-lock risk, replica-lag checks and rollback.
Why can a long primary key make every secondary index larger?

Secondary records carry the primary-key value used to locate clustered records. Compare key width, access locality and uniqueness needs rather than choosing UUID or integer by habit.

Does REPEATABLE READ prevent every business race?

No. Snapshot consistency is not a complete invariant design. Select appropriate locking, conditional writes and constraints, then test concurrent schedules.
