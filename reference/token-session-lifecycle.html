Refresh tokens and logout across applications

Follow one person using a trading app and a reporting app. Both use the same identity provider, but each app owns a separate local session. Read the flow first. Then predict which sessions survive each logout before opening the exercise answers.

Know which object you are holding

TermPurpose and boundary
Session tokenIdentifies a local application session. An opaque cookie value can refer to server-side session state. It need not be a JWT.
Access token / bearer tokenAn access token authorizes access to its intended resource. Bearer describes how possession permits use; it does not specify the token format.
Refresh tokenPresented to the authorization server to obtain new access tokens under an existing grant, not sent as the business API credential.
JWTA claims format. A signed JWT is not automatically encrypted, appropriate for this API or still authorized. Validation and resource authorization remain necessary.
OAuth / OIDCOAuth defines delegated authorization flows. OIDC adds authentication, including an ID token for the client. An ID token is not interchangeable with an API access token.
SSO / SAMLSSO is the sign-in experience across apps. OIDC or SAML federation can support it. SAML uses its own assertions and protocol messages; do not parse them as JWTs.

Review 0326 for bearer/JWT validation, 0308 for headers, and SAML federation. The OIDC adapter and SAML adapter create local sessions; they do not implement the new cross-app lifecycle exercise as a deployed system.

Follow credentials through the browser

Browser → Cookie: local opaque session → application backend
Backend → Authorization: Bearer access-token → intended API
Backend → refresh-token exchange → configured authorization server

This is a backend-for-frontend design choice. Keep provider tokens on the server and issue a restricted local cookie. Use Secure, HttpOnly and an appropriate SameSite policy. Rotate local session identifiers after authentication or privilege changes. Enforce idle and absolute expiry on the server; deleting a cookie alone does not invalidate a stolen server-side session. See OWASP session management.

A cookie is attached automatically, which creates CSRF risk for state-changing requests. Use the framework's protection, session-bound tokens where appropriate and origin checks. SameSite is a supporting control, not a universal replacement. An explicitly attached Authorization header has different browser behavior, but does not make the whole application immune to CSRF. Review 0328 and OWASP CSRF prevention.

HttpOnly blocks JavaScript from reading the cookie. XSS can still make same-origin requests using the user's session. Prevent script injection with context-aware output encoding, safe DOM operations and sanitization when accepting HTML. Use CSP as defense in depth. Avoid storing long-lived tokens in script-readable storage. Read 0055 and OWASP XSS prevention.

Refresh one token, once

Think of a refresh token as a claim ticket that can be exchanged for a new ticket. In a rotating scheme, using R0 produces access token A1 and replacement refresh token R1. R0 becomes consumed. The token family links successive replacements so the authorization server can recognize reuse.

t0: R0 active
t1: exchange R0 → issue A1 + R1; consume R0 atomically
t2: exchange R0 again → detect reuse; revoke affected family under policy
t3: exchange R1 → denied after family revocation

For public clients, the OAuth security BCP requires refresh tokens to be sender-constrained or rotated to detect replay. Refresh-token issuance and lifetimes depend on policy. Rotation does not protect against every theft scenario. See RFC 9700, refresh-token protection.

On the client, serialize refresh for one session: concurrent requests share one refresh operation, then retry with the updated access token. Across backend replicas, a process-local lock is insufficient. Coordinate shared token state with a lease/version or transaction, and prevent an old response from overwriting newer credentials. On the authorization server, consume-and-replace must be atomic. Hash lookup values for high-entropy tokens where appropriate; never log raw tokens.

A timeout is ambiguous: the server may have consumed R0 but the client may not have received R1. Do not blindly retry R0 indefinitely. Follow the provider's documented recovery contract; if recovery is unavailable, clear the unusable local grant and ask for login. A grace window can reduce accidental reuse failures but also broadens replay opportunity. Do not invent a grace policy on the client.

Refresh only for an appropriate authentication failure. A resource-level 403 may mean the user lacks permission, not that the access token expired. Bound retries to prevent loops. Preserve the original request body safely and do not replay a non-idempotent business write unless its operation contract supports it.

Predict: two tabs submit R0 at nearly the same time. Is one success always enough?

No. The first exchange may issue R1, while the second reuse triggers family revocation. R1 can then be unusable. Serialize refresh and test the chosen provider's semantics. Our offline exercise uses strict family revocation and makes this consequence visible.

Define what “sign out” promises

ActionWhat it does not automatically do
End the trading app's local sessionEnd the reporting app session or the identity-provider session.
Revoke a refresh grantInstantly invalidate every already issued, independently validated access token.
End the identity-provider sessionGuarantee all apps received and processed logout notifications.
End sessions across apps/devicesHappen atomically across independent systems without an explicit coordination design.

Make local logout immediate and server-enforced. Revoke retained refresh grants where the provider supports it. Define the remaining access-token window: short lifetime, introspection or server-side revocation/version checks have different costs. Recheck authorization for protected operations. Do not claim “all devices signed out” merely because the current browser cookie disappeared.

For OIDC, an app can request provider logout using the configured end-session endpoint and the supported parameters. Register post-logout destinations; never redirect to an arbitrary user-supplied URL. Correlate the returning browser with state where used. This request starts a logout flow; it is not proof that every relying party is logged out. See OIDC RP-Initiated Logout.

Handle notifications without the browser

Back-channel logout sends a signed logout token from the provider to an app. Validate it with a maintained implementation and trusted provider keys: signature, permitted algorithm, issuer, audience, issued-at freshness, event claim and required session/subject information. A logout token must not contain a nonce. Do not accept an ordinary ID token as a logout token. See OIDC Back-Channel Logout.

Scope session lookup by issuer and client, then the validated sid or subject as specified. A subject-only event can end several sessions for that subject; a sid event targets the associated provider session. Do not use email as a globally unique identity. Record event IDs and session invalidation atomically so duplicates cannot restore or broaden state. Expire deduplication records according to your validated replay window.

In our worked case, the provider delivers separate audience-bound events to trading and reporting. Trading processes its event; reporting is unavailable. The user is signed out of trading, but reporting may remain active until notification delivery, another revocation check or expiry. Track failures, retry with bounds and tell the user the scope you can guarantee. Do not display a global success based only on the first acknowledgement.

Front-channel logout relies on browser-mediated delivery and can be affected by browser restrictions or a closed page. Back-channel delivery avoids that browser dependency but still needs reliable endpoints and state. Neither can undo a completed business action. Reauthorize queued actions at execution time and invalidate stale approvals according to policy.

SAML single logout has a separate contract

SAML Single Logout uses LogoutRequest and LogoutResponse messages. Associate local sessions with the validated identity and SessionIndex. Validate messages, signatures, destination, timing and request/response correlation using the toolkit and agreed bindings. Coordinate trusted metadata and signing-key rollover. A local cookie deletion is not SAML SLO.

Partial logout is possible when an app is unavailable. Preserve a record of remaining work, use bounded recovery and distinguish local success from federation-wide success. The existing SAML login lab intentionally does not implement SLO. This page adds the lifecycle explanation and acceptance plan, not an untested XML-signature implementation. Consult SAML Profiles, section 4.4.

Run the lifecycle exercise, then test real boundaries separately

  1. Read the small state model. Its R0/R1 values are labels, not real secrets.
  2. Predict rotation, duplicate reuse, expiry and explicit family revocation. Run the standard-library tests.
  3. Model two apps, a second device and another issuer. Deliver logout to only one app, then retry the other delivery.
  4. Confirm the same sid under another issuer is untouched. Confirm duplicate delivery has no additional effect.
  5. For an authorized provider integration, add signed invalid-token cases, key rotation, session-store restart, out-of-order delivery, logout during refresh and an HTTPS browser test. Do not treat the local model as proof of those boundaries.
Interview: why does a signed JWT still work after logout?

The API may validate signature and expiry without consulting revocation state. Logout changed a different state store. Explain the promised revocation window and how short expiry, introspection or a session/version check enforces it. Test the actual path rather than assuming a shared login means shared logout.

MCQ: App A logs out locally. Which statement is supported? A) A's session ends. B) Every session ends.

A. Other apps, devices, the provider session and issued access tokens have separate lifecycles unless the system explicitly coordinates them.
