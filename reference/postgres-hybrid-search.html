Find documents with words and meaning

Read the example first. Then trace the SQL without running it. Calculate the fusion scores on paper before answering the interview questions. Use one study session for retrieval and another for production failures. Nothing needs to be installed.

A simple example

You ask: “How do I reset an AX-42?” One manual contains the exact model number. Another says “restore the device to factory settings.” Word search helps find AX-42. Vector search can connect “reset” with “restore.” A manual for the wrong device can still sound similar.

Imagine two librarians. One checks exact words. The other looks for similar meaning. Each gives you an ordered list. Combine the lists, check the evidence, and use only documents you may read.

Verified identity → authorized scope
    ├─ BM25 candidates ──┐
    └─ vector candidates┴─ rank fusion → rerank → check sources → cite

Native text ranking is not BM25

PostgreSQL provides tsvector, tsquery, GIN indexes and ts_rank/ts_rank_cd. These support lexical search, but their scores are not BM25. See PostgreSQL text-search controls.

BM25 uses term frequency, document frequency and document length. Rare matching words can distinguish documents. Repeating a term gives diminishing benefit. Length normalization reduces the advantage of long documents. An inverted index maps terms to matching chunks, so search can follow postings rather than scan all text. Chunk size changes the indexed units and their length statistics.

Tokenization determines what counts as a word. Test identifiers such as AX-42, punctuation, languages and synonyms. Stemming can help prose but damage identifiers. Keep important exact identifiers in separate fields when needed.

This recipe uses pg_search for BM25 and the separate pgvector extension for vectors. The current ParadeDB index API uses USING paradedb. Its scoring API uses pdb.score(id) with a search predicate. The recipe targets the documented 0.26+ syntax. Older tutorials use different names. Confirm installed versions and hosting support; managed PostgreSQL providers may not allow this extension.

What the vector branch does

An embedding is a numeric representation from a model. Encode queries and documents with compatible model settings. Equal dimensions do not make two models compatible. Cosine distance compares direction; smaller means closer. Similarity is not the probability that a chunk answers the question.

Start with exact search: calculate distances over authorized rows and sort them. HNSW builds a graph to speed approximate search. IVFFlat searches selected clusters and needs representative data for index construction. Both can miss neighbors. Compare recall with the exact baseline before accepting faster results. See pgvector's index and filtering guidance.

Approximate scans can find candidates that later fail a filter. This can leave fewer than K results. Higher scan effort or supported iterative scans can help. For selective tenants, filtered exact search or partitioning may be better. Never remove permission checks to improve recall.

Fuse ranks rather than raw scores

BM25 returns A, B. Vector search returns B, C. Their score scales differ: adding BM25 12 to cosine similarity 0.8 creates an arbitrary preference. Reciprocal rank fusion uses positions instead.

RRF(chunk) = sum of 1 / (60 + rank) across lists containing it
Ranks start at 1. Missing items contribute zero.
A: 1/61            = 0.01639
B: 1/62 + 1/61     = 0.03252
C:        1/62     = 0.01613
Result: B, A, C

The constant 60 is a starting choice, not a universal optimum. Larger constants reduce the difference between nearby ranks. Tune candidate limits, weights and constants on validation queries. Preserve a separate final test set. Fusion cannot recover evidence absent from both lists.

Take a bounded pool from each branch, fuse their union, then choose the final context. A cross-encoder reranker reads each query/chunk pair and rescores the small union. It adds latency and cannot recover missing candidates. Limit repeated chunks from one document so they do not crowd out other evidence.

Trace the SQL

Open the SQL recipe. Three dimensions make a small hand-built vector fixture possible; use your model's actual dimension for real data. This recipe is not a Support Copilot database adapter.

  1. Inspect extension versions. No installation is part of this exercise.
  2. Read the schema: chunk ID, tenant, source version, page, text, vector and active flag.
  3. Trace lexical: filter visible rows, match words, score, sort and limit.
  4. Trace dense: apply the same filters, calculate cosine distance, sort and limit.
  5. Assign ranks within each list. UNION ALL keeps both contributions when a chunk appears twice. GROUP BY sums them.
  6. Join source metadata, repeat visibility checks and limit the final result.

Bind parameters instead of interpolating strings. $1 is a verified tenant, $2 query text, $3 its vector, $4 the per-branch limit, and $5 the final limit. Python drivers may use different placeholders. Validate query length, vector dimension and nonzero norm, and positive bounded limits. Derive tenant identity from authentication, not an unchecked request field.

Permissions belong inside retrieval

The sample permits all active documents in one authorized tenant. Real applications may also need document grants. Apply them in both branches before LIMIT. Filtering only after top-K can discard all candidates even when authorized evidence exists below the cutoff.

Use least-privileged roles and independently enforced row-level security where supported. Test the exact extension, query plan and role. Owners and bypass roles do not prove isolation. The sample does not supply authentication, RLS policies or a complete access model.

One statement provides a common statement snapshot under normal PostgreSQL execution. Separate queries can observe different versions unless you use a shared transaction snapshot. Recheck current permission before sending sensitive text to a model or user. Cache keys need tenant, permission version, source version and embedding model boundaries. Avoid private text in logs.

Updates, deletion and model changes

Keep stable source IDs and content hashes. Stage changed text with its new embeddings. Publish the ready version and retire old chunks atomically. Ordinary row changes maintain indexes; each document edit does not require rebuilding everything. Bulk changes still add write and maintenance work.

Never publish new text with an old embedding. Deactivate removed chunks and invalidate cached answers. Cite source ID, version and page. Test deletion visibility and concurrent updates with your chosen extensions. A citation must identify the source actually used.

For a new embedding model, build a parallel version, evaluate it, switch query and document embeddings together, and retain rollback. Do not compare vectors from different model spaces merely because dimensions match.

Quality, latency and failure tests

Label queries for identifiers, paraphrases, ambiguity, missing answers and permission denials. Decide whether labels refer to chunks or documents. Keep related versions and near-duplicates together when splitting development, validation and test data.

Candidate recall measures relevant evidence found in the union. Precision@K measures relevant results among the first K positions. Recall@K divides retrieved relevant items by all labelled relevant items. MRR measures how early the first relevant result appears. For no-answer queries, measure abstention separately rather than divide recall by zero. Retrieval relevance does not establish groundedness: verify each generated claim against its cited text.

Compare lexical-only, vector-only, RRF and RRF plus reranking on identical queries. Report categories and tenant sizes separately. Trace embedding, each retrieval branch, fusion, reranking and generation. Report p50/p95/p99 with sample counts. Summing stage p95 values does not give end-to-end p95.

On an authorized test database, inspect EXPLAIN (ANALYZE, BUFFERS) for each branch. ANALYZE executes the query. Inspect rows removed, sorting, index use and buffers. Compare exact and approximate recall under restrictive filters, cold/warm caches and concurrent load. No live timings or extension results have been measured here.

Use deadlines and bounded candidate pools. If one branch fails, record the failure and use an explicitly tested single-branch fallback or abstain. A timeout is different from a valid empty result. Do not bypass permissions during degradation. Monitor branch failures, empty results, candidate counts and stale-version rejections.

Practice after reading

  1. Calculate A/B/C fusion scores without looking.
  2. Remove the vector branch. Predict the order. Answer: A, B.
  3. Place a forbidden item first in both lists. Explain why filtering must precede candidate limits.
  4. Make lexical search empty. Explain why a semantic match still needs evidence checks.
  5. In a future disposable database, create identical documents in two tenants. Test tenant isolation with the actual application role, then revoke access and delete a chunk while requests run.
  6. Add HNSW later. Compare filtered result counts, recall and latency against exact search.

Interview rehearsal

Is ts_rank BM25?

No. Name the actual scorer. Native PostgreSQL FTS plus pgvector is hybrid search but is not automatically BM25 hybrid search.

Why not use vectors alone?

Exact identifiers and phrases can favor lexical search. Semantic similarity can return a related but wrong manual. Measure both branches on labelled data; hybrid does not always win.

Why does ANN return fewer than K rows?

Candidate scanning and filtering can leave too few survivors. Inspect scan effort and filtering, then compare iterative scans, partitioning and filtered exact search without weakening authorization.

How do you diagnose a wrong RAG answer?

Check scope and freshness. Inspect both candidate lists, fusion, reranking and final context. If evidence is present, inspect claim support. Distinguish missing retrieval from unsupported generation.

When would you keep native FTS instead?

When measured quality meets requirements and an extension adds unnecessary hosting and maintenance constraints. A separate search service may offer more capability but adds another consistency boundary.

MCQ: B is second lexically and first semantically. Its RRF score with constant 60 is A: 1/60, B: 1/62 + 1/61, or C: its raw scores added?

Answer B. Each branch contributes once using its rank.
