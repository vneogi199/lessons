Retrieval practice

Chunk spans and a connected hybrid index

Use the existing RAG project. Its hybrid extension keeps the same ingestion, tenant boundary and citation checks. Source and tests are authored but unexecuted.

Cut a page without losing its address

Imagine cutting a paragraph into strips. Write the page version and start/end positions on each strip. Those labels locate the original passage even when two strips contain identical words.

chunking.py returns half-open character spans: start is included, end is excluded. Fixed spans use a maximum size and overlap. The semantic variant accepts a similarity function for adjacent sentences and starts a new group when similarity is low. Oversized groups fall back to fixed spans. Sentence splitting is deliberately simple; abbreviations and layout need a better parser.

Text: 0123456789abcdefghij
Size 10, overlap 0: [0,10), [10,20)
Size 10, overlap 2: [0,10), [8,18), [16,20)
Gold answer span: [8,12)

Without overlap, neither chunk holds the complete answer span. With overlap 2, the middle chunk holds it. That version stores 24 characters from a 20-character source, so four character positions are duplicated. The report computes duplication, serialized record bytes and unique source coverage under a context budget.

Gold-span containment is a chunking measure. It does not show that a retriever found the chunk. Report retrieval recall separately on labeled queries. Character limits are not model-token limits.

Look up words through postings

A postings list records which chunks contain a word and how often. For ["refund refund", "payroll", "refund"], the refund entry is {0:2, 2:1}. A query for refund can score chunks 0 and 2 without scanning chunk 1's words.

Postings.rank applies a BM25-style length adjustment and term-frequency score. Its tokenizer and in-memory dictionary are teaching components. SQLite FTS5 illustrates a maintained full-text engine; a production index also needs durable updates and operational limits.

Join word search and vector search

HybridStore reads only the current tenant's chunks. It creates vectors through one encoder, builds postings, calculates exact cosine scores, and fuses the top lexical/vector candidates with reciprocal rank fusion. Context keeps at most three complete chunks within a character budget.

The synthetic test encoder maps refund and reimbursement to one dimension and payroll to another. It checks routing and provenance, not semantic model quality. LocalEncoder can use an already-provisioned SentenceTransformer directory with downloads and remote code disabled.

The index is rebuilt per query, so updates and deletes use current database content without a separate index synchronization window. This costs repeated encoding work and caps the fixture at 500 chunks. A production index should persist vectors by document version and embedding contract, with coordinated publication and revocation.

A chunk missing from both candidate lists cannot be recovered by RRF. Tests also check empty input corpora, context too small for a chunk, source-version replacement and deletion. Existing answer-release checks reject evidence changed during generation.

Compare dimensions carefully

For one million float32 vectors, 384 dimensions require 1,536,000,000 bytes of raw vector data. At 768 dimensions, that is 3,072,000,000 bytes. These figures exclude IDs, metadata, replicas, graph edges, allocator overhead and temporary build memory.

More dimensions do not guarantee better retrieval. Compare supported configurations on the same labeled questions, permissions and candidate count. Use separate indexes for each model/revision/dimension/normalization/metric contract. Equal dimensions do not make different models comparable.

If a model supports reduced dimensions, follow its documented procedure. Arbitrarily truncating an embedding is not a general optimization. Record recall, latency, storage and hosting cost for approved runs. No quality or speed results have been measured. See Sentence Transformers similarity.

Interview: why not average BM25 and cosine scores?

The values have different ranges and meanings. RRF uses rank positions. It still needs evaluation of candidate size and fusion constant, and cannot repair missing evidence.

Use an external index or reranker deliberately

The Pinecone recipe supplies creation, readiness, filtering, update/delete checks and ownership-checked cleanup. It uses synthetic vectors. Provisioning and deletion each require separate approval; nothing has been created.

The Cohere adapter reuses the bounded retry helper. It sends only authorized candidates, limits input/output size, and maps returned indexes back to the original records. Two identical text strings can still have different source IDs.

If the provider times out or returns duplicate/out-of-range indexes, the adapter keeps the original authorized order and returns mode=fallback with a reason. It does not label that result reranked. Tests cover reordered indexes, invalid results, denied candidates and bounded retries through a fake HTTP transport.

See the Cohere contract. A reranker score is a relevance signal, not a truth probability. Compare final answer evidence and added latency after an approved run; no improvement is claimed from supplied code alone.

Practice: does full gold-span containment imply full answer accuracy?

No. Retrieval can miss the chunk, the context budget can exclude it, or generation can misread it. Track each boundary independently.
