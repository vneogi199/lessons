An order-support chatbot that survives retries

This is an illustrative design, not a description of Swiggy's internal system. First trace one complaint. Then study fraud decisions and reconnects. Finally answer the failure exercises without opening the feedback. No payment provider, broker or trained model runs on this page.

Follow one complaint

Think of a help desk with numbered tickets. The receptionist records your request before passing it to a worker. If you ask again, the number lets the desk find the original request. The chatbot needs the same separation between accepting a message and completing its action.

Start with a deterministic workflow: identify the order, check ownership, fetch status, offer eligible options and resolve or escalate. An LLM may classify text or explain a result. It cannot invent eligibility or call an unrestricted refund tool.

  1. The client sends a stable message ID and conversation ID. The server verifies that the user owns the conversation and may access the order.
  2. One database transaction records the message and an outbox event. Acknowledgement means accepted durably, not resolved.
  3. A relay publishes the event. Consumers expect redelivery. Deduplicate using an event ID and commit the processed-event receipt with the state transition.
  4. The worker reads backend APIs and records a decision. Keep network calls outside a long database transaction. Revalidate state before committing a consequential action.
  5. Write the result and notification event durably. The client can fetch it even if a live notification is lost.

Use an envelope with event ID, tenant, conversation ID, message ID, schema version, expected state version and trace ID. Keep large sensitive payloads out of broker headers. Encrypt protected records and apply retention and deletion policies.

Partitioning by conversation can preserve broker order within a partition. It does not order concurrent publishers, retries on separate topics or external service responses. Assign an authoritative sequence when recording messages and reject stale state updates. Use the outbox lab to practise duplicate delivery and committed-state recovery.

Try: a tracking response arrives after a human has taken over. What happens?

Store it as evidence if useful, but reject any stale bot transition. Compare the conversation version and ownership generation. A delayed result must not switch the conversation back to bot mode.

Separate fraud scoring from refund authority

The refund decision service first checks authenticated ownership, payment state, refundable balance and policy eligibility. Then it obtains relevant evidence and a versioned fraud score. The payment service enforces the final money invariant, including concurrent requests from other channels.

Request → eligibility rules → feature snapshot → risk model
                 ↓                  ↓                ↓
           explain rejection   missing/stale → review queue
                                                    ↓
                              policy decision: approve / review / reject
                                                    ↓
                              durable refund operation → payment provider

Candidate features include prior verified refund outcomes, order value, delivery evidence and recent request counts. Define each feature's event-time window, freshness and missing-value behavior. Use only data authorized for the purpose. A missing feature is not zero risk. Keep the model version, feature snapshot reference, policy version and reason codes with the decision.

For training, distinguish confirmed abuse, legitimate claims and unresolved cases. Labels may arrive late. Human review is selectively applied, so reviewed cases alone can bias evaluation. Split by time, prevent future outcomes from leaking into features and test for duplicate-customer leakage where relevant. Start with a simple baseline and monitor training/serving differences; see Google's ML engineering guidance.

Evaluate precision, recall, calibration, false declines and loss at the chosen policy thresholds. Accuracy alone hides rare fraud. Compare review demand with reviewer capacity. Shadow a candidate model, inspect slices and set rollback criteria before increasing its authority. Score drift can be detected before delayed outcome labels arrive, but drift alone does not prove degraded accuracy.

Illustrative policy: an eligible request with fresh evidence and sufficiently low calibrated risk can proceed; uncertain cases enter review. Thresholds require business validation. Never treat a language model's “95% confident” text as calibrated fraud probability. Offer an appeal path and avoid exposing internal abuse-detection rules in customer messages.

Assign a stable refund operation ID across retries. Store its payload hash and reject conflicting reuse. The payment service must prevent total refunds exceeding the permitted balance; a conversation-level lock cannot protect requests from another channel. Provider idempotency retention may be shorter than your business history. Preserve your ledger and reconcile unknown outcomes. See one provider's idempotency contract; other providers differ.

Try: the provider times out after issuing the refund. Should the bot report failure and retry with a new ID?

No. Record an unknown outcome, keep the original operation ID and reconcile with the provider. Tell the user processing is unconfirmed. A new ID risks a second refund.

Reconnect without losing the conversation

An authentication session identifies the caller. A conversation stores support work. A network connection is only a temporary delivery channel. Closing the browser must not delete an in-progress refund or transfer ownership.

Store conversation ID, tenant/user, order reference, workflow version, owner mode, owner generation and last durable sequence. Keep messages, decisions and external operations as separate records. Cache hot reads if useful, but do not make a short-lived cache the sole refund ledger.

For two browser tabs, use client message IDs for duplicate sends and optimistic concurrency for conflicting actions. A state update succeeds only against its expected version. Return the latest state on conflict. Validate ownership on every read, write and reconnect; knowing a conversation ID is not permission.

Use POST for messages and SSE for server updates when one-way streaming is sufficient; WebSockets suit bidirectional live traffic. In either case, persist events before delivery. Resume from an authorized cursor, deduplicate rendered events and fetch a snapshot when the cursor predates retention. SSE provides event IDs and reconnection behavior, but your server must implement the durable replay. See SSE mechanics.

Conversation expiration, login expiration and audit retention have different purposes. Require authentication renewal after logout or expiry. Keep unresolved operations under the applicable retention policy. Do not replay private messages after the user loses access.

Try: a gateway crashes immediately after accepting a message.

If acceptance followed the database commit, another worker can process the outbox. The client retries with the same message ID or fetches history. If the commit never happened, retry can create the message once. An in-memory acknowledgement cannot provide this guarantee.

Scale connections and work separately

Connection gateways handle many mostly idle sockets. Workers handle backend calls and decisions. Scale them by their own limits: active connections and send-buffer pressure for gateways; queue age, processing time and dependency capacity for workers. Sticky routing can help efficiency but must not be required for correctness.

Illustrative sizing: 20,000 active chats sending one message every 20 seconds produce 1,000 messages/second on average. If processing takes 0.2 seconds, steady-state work in flight averages about 200. Bursts, retries, slow dependencies and connection memory need additional headroom. This arithmetic is not a benchmark.

Limit message size, per-user admission, worker concurrency and outbound buffers. Disconnect a slow stream with a recoverable cursor rather than retaining unlimited messages in memory. Separate tracking and refund resource pools so a tracking outage cannot occupy every connection. Drain consumers and connections during deployment.

Give each request a total deadline. Retry transient failures only when safe, with capped exponential backoff, jitter and a shared retry budget. Avoid independent retries at every layer. A tracking circuit breaker can fail fast and probe recovery; it does not replace a refund idempotency check. See AWS's retry guidance.

Make human takeover explicit

Use states such as bot_active, waiting_for_human, human_active and closed. Claim a case atomically. Increment the ownership generation on transfer, and require it for later bot actions. A bot command already sent to a provider needs reconciliation; takeover cannot recall it.

Queue by urgency with fairness and aging. Reserve capacity for high-impact cases without starving ordinary ones. Show realistic status rather than promising immediate support. Preserve the transcript, evidence, attempted actions and unresolved operation IDs for the reviewer.

If arrivals are 120 cases/hour and the team resolves 100/hour, the queue grows by 20/hour. More chatbot replicas do not fix that bottleneck. Reduce avoidable escalations safely, adjust staffing or offer asynchronous follow-up. Never auto-approve refunds solely to shorten the queue.

Failure drill and interview rehearsal

Draw the sequence for a duplicate complaint, a lost refund response and a reconnect after takeover. Label the durable record at each boundary. Then compare your design with these acceptance cases.

Monitor accepted-to-response p50/p95/p99, queue age, reconnect recovery, duplicate suppression, unresolved refund age, reviewer wait, false declines and cost per resolved case. Redact traces; restrict access to fraud evidence. These cases are a design checklist, not executed integration tests.

Interview: why not keep the whole chat in Redis and make every worker stateless?

Workers can avoid local durable state, but the system still needs durable message, ownership and operation records. A cache can accelerate reads. Its expiry or eviction must not erase proof of a refund or approval.

Interview: when is an event-driven design unnecessary?

A low-volume read-only FAQ may need only synchronous requests. Add queues when durability, long-running actions or load isolation justify their operational cost. Events introduce duplicates, lag and recovery work.
