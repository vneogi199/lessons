Model and retrieval practice

Keep model retries and context bounded

A model may return broken JSON, valid data for the wrong instrument, or a refusal. These outcomes need different responses. The supplied project separates them and includes fake-provider tests. Nothing has been executed.

Repair a form without repeating an action

Imagine a clerk copying an RFQ onto a form. A missing bracket is a formatting problem. A quantity written as true is a type problem. An instrument outside the desk's permissions is an authorization problem. Asking the clerk to rewrite the third form does not make it authorized.

Incomplete JSON → malformed_json → bounded retry
Wrong field type → schema_failure → bounded retry
Explicit refusal → stop
Truncated response → stop; review output budget separately
Valid fields, forbidden instrument → stop after validation

The parser accepts complete responses of at most 4096 characters. It rejects duplicate keys and non-finite JSON numbers before Pydantic checks the schema. The allowlist runs after the retry helper returns, so a business rejection cannot trigger a repair.

The fake provider first returns broken JSON and then a valid RFQ. Predict two calls and quantity 10. In the refusal case, predict one call. Read those assertions before looking at the implementation.

The provider interface only generates text. A trade submission or ticket creation must not be placed inside it. If an external action succeeded but its response was lost, repeating the action can duplicate the effect. Reconcile its operation ID or read its status instead.

One place owns retries

The helper permits three attempts within a twelve-second budget, with at most four seconds requested for each attempt. Transient failures wait with exponential backoff and jitter. Retry-After can request a longer delay. If that delay does not fit the remaining budget, the helper fails instead of retrying early.

Disable retries inside an SDK wrapped by this helper. Three attempts in each layer can produce nine transport calls. Those calls can consume tokens even when no answer reaches the user. The tests count calls; they do not measure provider billing.

Async timeouts depend on cancellation. An adapter that blocks the event loop or suppresses cancellation can exceed the requested time. A timeout also does not prove that a remote request stopped. Production needs transport limits and an explicit policy for uncertain outcomes.

Interview: a schema-valid quantity is outside the desk's limit. Should you repair it?

No. Apply the deterministic risk rule and reject or request human review. A model should not change a requested quantity merely to pass a limit check. The example's allowlist illustrates this boundary; it does not implement a financial risk engine.

Keep complete pieces of history

Imagine a notebook with an old policy saying 10 and a newer policy saying 20. The current-policy card must say 20 and cite the newer source. A summary that repeats 10 should be rejected rather than promoted to current policy.

The context exercise stores authoritative facts separately from conversation history. It compares three modes. Full history fails when it does not fit. Recent history keeps a suffix of complete turns. Summary mode adds checked fact references and then fits recent turns. All modes retain the instructions, current question and latest facts, or fail if those required inputs do not fit.

A tool call and its result occupy one turn. They are retained together or omitted together. Matching call IDs are checked when the turn is constructed. This prevents a retained result from losing the call that explains it.

Count a real request and return tool results

The project also supplies a Claude HTTP adapter. Its count request includes the selected model, system text, tool schemas and messages. Evidence must be inside those messages to be counted. The caller supplies the model's approved context limit. Each turn checks counted input plus reserved output before generation.

The tool loop asks only for authorized synthetic limit reads. If the model requests two independent reads, both can run with a concurrency cap of two. Each response carries the original tool-call ID. The next model request contains the full assistant call message followed by every tool result, including failed reads.

A request for place_trade returns unknown_tool and never executes. Repeated call IDs stop the loop. This example cannot book a trade, and a generated answer is still subject to application validation before any future write workflow uses it.

The HTTP test records request bodies through MockTransport. It checks that output reservation is sent with generation but not with the count request. Actual provider token counts remain unobserved. The usage report separates input, cache-read, cache-creation and output tokens; failed attempts can leave unreported billed usage.

Provider references: Claude token counting, tool schemas, and HTTPX timeouts. No credentials or provider calls are needed to inspect the code.

The fixture counts whitespace words to make the arithmetic inspectable. These are not token counts. It also uses exact fact references rather than generated prose, so it demonstrates provenance checks without claiming that free-form summaries are reliable. Practice: an old summary conflicts with current policy. Which input wins?

A. The newest summary text.
B. The verified policy record.
C. The longest context block.

Answer: B. Recency or length does not establish authority. The summary must be checked against the source and version.
