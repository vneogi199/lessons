RAG: trace the answer back to evidence

Retrieval-augmented generation supplies retrieved external material to a generator. The original RAG paper provides the research foundation; a production pipeline also needs identity, ingestion, versioning and evaluation. Retrieval can be lexical, vector, graph or document-tree based. RAG is not synonymous with a vector database, and attaching citations does not prove that an answer follows from them.

The offline path validates a source, parses it, preserves provenance, chunks/indexes it and publishes a ready generation. The online path authenticates the caller, retrieves permitted evidence, optionally reranks, constructs bounded context, generates and checks the answer. Keep source/version/span IDs attached throughout. Permission revocation must affect retrieval, parent expansion, caches and generated summaries—not just the original object.

Locate the failure before tuning

Fixture: D1 says refunds take seven days; D2 describes creating an account. The question asks about refunds. Write the expected behavior for four cases: D1 absent from the index, D1 retrieved but cut from context, D1 in context but the answer says thirty days, and D1 revoked for this user.

Compare your diagnosis

These are respectively ingestion/retrieval coverage, context assembly, generation/grounding and authorization problems. A stronger generator does not repair a missing source or a permission leak. In the revoked case, with no authorized replacement evidence, abstain rather than reuse the cached answer.

Build a held-out set with source IDs and answer expectations, including no-answer, contradiction and revoked-document cases. Measure retrieval recall separately from claim support, answer correctness, latency and cost. Hold corpus/model/prompt versions fixed when comparing a change. A fabricated good-looking answer is not a success. See the existing GraphRAG comparison and reranking exercise.

Pinecone: own the index contract

Pinecone is a managed retrieval service. An index defines relevant storage/search configuration; a namespace partitions its records. Records carry stable IDs, vectors and metadata. Bring-your-own vectors and integrated embedding indexes have different input APIs: do not send text to a vector-only query or assume the service chose your intended embedding model. See upserts and filtered search.

For a pre-existing two-dimensional learning index and Python SDK, the recipe below writes one synthetic record, then queries it. It can incur service charges. The host/key are trusted application configuration; tenant scope comes from authenticated identity. Do not run against a production namespace.

import os
from pinecone import Pinecone

pc = Pinecone(api_key=os.environ["PINECONE_API_KEY"])
index = pc.Index(host=os.environ["PINECONE_INDEX_HOST"])
namespace = "lesson-tenant-a"  # server-derived in the real service
index.upsert(namespace=namespace, vectors=[{
    "id": "policy:v1:0", "values": [1.0, 0.0],
    "metadata": {"status": "published", "source": "policy:v1", "page": 2},
}])
result = index.query(namespace=namespace, vector=[1.0, 0.0], top_k=3,
    filter={"status": {"$eq": "published"}}, include_metadata=True,
    include_values=False)

Check visibility using the deployment's documented freshness behavior; do not assume an immediate query proves a completed write. Use a bounded wait/retry in the lab. Add an identical record in tenant B's namespace and verify that an A-scoped service request cannot select B. A namespace parameter is not an authentication mechanism if callers can freely choose it.

Pin embedding revision, dimensions, distance metric and chunking version. Re-embedding into a new index/generation enables comparison and rollback. Upserts with stable IDs replace records, but do not remove stale chunks left by a shorter source. Keep a manifest and reconcile deletions. Benchmark filtered recall, p95 latency, read/write usage and ingestion lag with representative tenant sizes.

Interview: same dimensions, new embeddings—safe to reuse the index?

No. Equal shape does not imply a compatible vector space. Re-embed documents and change the query encoder together. Validate tenant isolation and retrieval quality before switching traffic; maintain a rollback generation.

RAGAS: use metrics as diagnostics

Ragas is an evaluation library, not an oracle. A sample records the user question, retrieved contexts, response and, where required, a reference answer. Faithfulness measures support in the supplied context; factual correctness compares against a reference; context recall asks whether needed reference information was retrieved. An answer can be faithful to an incorrect source. Read the official evaluation walkthrough and faithfulness definition.

from ragas import EvaluationDataset, evaluate
from ragas.metrics import Faithfulness, FactualCorrectness, LLMContextRecall

dataset = EvaluationDataset.from_list([{
    "user_input": "How long is the refund window?",
    "retrieved_contexts": ["Policy P1: refunds within seven days."],
    "response": "Refunds are available within thirty days.",
    "reference": "Refunds are available within seven days.",
}])

def score_with_approved_judge(evaluator_llm):
    # Supply a compatible, explicitly configured Ragas judge adapter.
    # This can make paid model calls; no default provider is selected here.
    return evaluate(dataset=dataset,
        metrics=[Faithfulness(), FactualCorrectness(), LLMContextRecall()],
        llm=evaluator_llm)

Prediction: the context contains the necessary information, but the answer contradicts it. You should expect poor answer-support/correctness judgments, not assert a particular numeric score from a probabilistic judge. Repeat with “seven days,” then with an empty context. Inspect per-sample explanations, parsing failures and missing scores before averaging.

Pin Ragas, metric configuration, judge model/prompt and corpus snapshots. Calibrate on human-labeled positives and negatives, including numbers, negation and misleading citations. Use holdouts, slices and repeated judge calls; a large score shift after a judge upgrade may not reflect product improvement. Do not treat missing/error scores as zeros without a declared policy. Record successful evaluation coverage alongside quality.

Interview: faithfulness improved while customers report worse answers—why?

The system may now repeat irrelevant context accurately or abstain more often. Check answer relevance, evidence recall, task success, abstention and source correctness. Compare paired examples and denominators; one metric cannot certify the whole application.

Parent–child retrieval: search small, explain with context

Small child chunks often make precise matches easier; a larger parent section preserves definitions, exceptions and neighboring explanation. Index children with a stable parent ID, source version and span. At query time, rank children, resolve their parents, deduplicate parents and fit authorized context into a token budget. This differs from merely increasing every chunk's size.

Worked case: two refund sentences point to parent P1; a third hit points to P2 from another tenant. Predict which parent IDs may reach the generator. This toy resolver assumes a parent is one permission unit and rechecks its current tenant and version.

parents = {
    "p1": {"tenant": "a", "version": 2, "text": "Refunds: seven days. Exceptions apply."},
    "p2": {"tenant": "b", "version": 2, "text": "Private policy."},
}
hits = [("p1", 2), ("p1", 2), ("p2", 2), ("p1", 1)]
def expand(hits, tenant):
    chosen = {}
    for parent_id, version in hits:
        parent = parents.get(parent_id)
        if parent and parent["tenant"] == tenant and parent["version"] == version:
            chosen.setdefault(parent_id, parent["text"])
    return chosen

assert list(expand(hits, "a")) == ["p1"]
assert expand([("missing", 1), ("p1", 1)], "a") == {}

In production, use the actual ACL rather than only tenant equality. If different parent spans have different permissions, do not expand the whole parent: partition it or fetch permitted spans. Keep child-span citations even when passing broader context. Deduplication prevents one parent from consuming the budget repeatedly; selecting parents should preserve the evidence ranking and avoid starving other sources.

Interview: why did retrieval improve but answers regress?

Parent expansion may add distracting text or crowd out other evidence. Measure child evidence recall, final-context coverage, supported answers and token cost separately. Test orphan children, version mismatch, revoked parents and very large sections. Bigger context is a tradeoff, not an automatic improvement.

Vectorless / PageIndex-style RAG: retrieve through a document tree

Vectorless retrieval means that vector similarity is not the selection mechanism. It can use lexical search, SQL or structured navigation; these are not all the same algorithm. PageIndex specifically builds a hierarchical document index and uses model-driven navigation to find relevant sections/pages. A tree node is a locator and summary, not independent factual evidence.

A typical path is document → section tree with page ranges → candidate branches → original pages → answer with citations. This can suit long, structured reports where headings and hierarchy matter. It is less attractive when headings are poor, relevant facts cross branches, OCR is unreliable or many unrelated documents need a fast first-stage search. Vector and tree retrieval can also be combined.

Practice branch selection and recovery

Fixture: a handbook has “Overview” on pages 1–3, “Billing” on 4–8 and “Refund exceptions” on 9–11. The query asks whether an annual plan can be refunded after cancellation. First select candidate nodes from titles/summaries; then read the actual pages. Include both billing definitions and exception pages if the answer depends on them. Do not let the overview's broad summary override a specific exception.

Check: a planner chooses only Billing—how should you respond?

Bounded sibling/backtracking search can recover the exception branch. If no supporting clause is found within the budget, abstain or ask for clarification. Never turn an index summary into a fabricated page citation. The test should record selected nodes, fetched pages and the precise supporting span.

In an already provisioned PageIndex environment, index an approved long PDF and compare tree retrieval with hybrid vector/keyword retrieval using the same questions, corpus and final context budget. Include cross-section, exact-number and no-answer questions. Measure source-page recall, supported answers, tree-building tokens, node visits, p95 latency and total model cost. Separate indexing from query expense.

Document edits invalidate page ranges and derived summaries; publish versioned trees and retain lineage. Apply permissions before sending summaries or pages to a model. Prompt injection can exist in headings and summaries too. “No vector DB” does not mean no index, no preprocessing, no hallucinations or no operating cost. Chain-of-thought: distinguish a technique from evidence

Chain-of-thought (CoT) prompting presents or elicits intermediate reasoning steps before an answer. Few-shot CoT provides worked examples; zero-shot variants request stepwise solving. The original paper studied gains on reasoning tasks under particular experimental conditions. It does not establish that longer explanations are always better or that generated rationales reveal the actual computation.

Separate internal model reasoning, a user-facing explanation, and an auditable tool trace. An explanation can be useful without exposing private internal reasoning. A trace records observable tool inputs/outputs, approvals and source references. Neither fluent prose nor a claimed “thought” proves factual correctness. With reasoning models, explicit requests to reveal a chain of thought are often unnecessary; follow the model's official prompting guidance.

Evaluate the answer, not the length of the rationale

Task: “A report lists 12 items at 25 cents each. Return the total in cents and a brief calculation.” Compare a direct instruction with a worked-example prompt on a held-out arithmetic set. Expected output for this item: 300 cents, with the concise calculation 12 × 25. For production financial totals, calculate with a deterministic tool rather than trusting either prompt.

Interview: is “show every thought” an observability strategy?

No. Ask for a concise justification and evidence instead. Record the arithmetic tool result, source IDs and final answer validation. Evaluate exact correctness, schema compliance, tokens and latency. More generated reasoning text can introduce unsupported claims and sensitive details.

Deep Agents: a harness, not a stronger model

LangChain's Deep Agents adds planning, context/file management and delegation around a tool-calling loop, using LangGraph infrastructure. A plan tracks intended work; it does not enforce completion or authorization. Subagents can keep detailed intermediate work out of the coordinator's context, but they add latency, costs and failure paths. Read the overview and subagent contract.

This construction recipe requires an existing compatible Deep Agents installation and explicitly selected provider model. It defines a policy specialist, but does not invoke the model. Built-in filesystem/delegation tools and a default general-purpose subagent may still exist; the explicit tool list is not a complete capability audit.

import os
from deepagents import create_deep_agent

def read_training_policy() -> str:
    """Return a synthetic policy and its source ID."""
    return "P1: production changes require approval."

agent = create_deep_agent(
    model=os.environ["DEEP_AGENT_MODEL"],
    system_prompt="Draft a recommendation with evidence; do not change systems.",
    tools=[read_training_policy],
    subagents=[{
        "name": "policy-reviewer",
        "description": "Find policy evidence for a proposed change.",
        "system_prompt": "Use the policy tool; return a concise claim and source ID.",
        "tools": [read_training_policy],
    }],
)

Exercise in an approved sandbox: ask for a deployment recommendation, inspect the effective tool inventory, and verify that no system-changing capability exists. Configure backend isolation and default-agent behavior for the pinned release before invoking. Give the specialist an output contract: supported claims, source IDs, unresolved questions and budget spent. Reject summaries with invented evidence.

Interview: when should you avoid delegation?

For a simple lookup, direct tool use may be clearer and cheaper. Compare one agent against the coordinator/specialist setup on the same tasks. Count total calls, evidence retention, failure rate and wall time. Context isolation is not security isolation if both workers still share credentials or filesystem access.

OpenAI Agents SDK: control the run and the tool boundary

The SDK's Agent declares behavior and tools; Runner manages the interaction loop. Function tools expose typed application functions. Handoffs transfer control to another agent, while an agent used as a tool returns a result to its caller. Sessions/state, tracing and guardrails are supporting mechanisms, not automatic business authorization. See the SDK quickstart and run lifecycle.

import asyncio
import os
from agents import Agent, Runner, function_tool

@function_tool
def read_ticket() -> str:
    """Read the single authorized synthetic ticket for this exercise."""
    return "T1: staging health check failed; no production change is approved."

agent = Agent(name="Operations drafter", model=os.environ["AGENTS_MODEL"],
    instructions="Read the ticket. Draft a diagnosis, cite its ID, and do not act.",
    tools=[read_ticket])

async def draft():
    # Configure tracing/privacy and provider spend limits before a real run.
    result = await asyncio.wait_for(
        Runner.run(agent, "Assess the staging incident."), timeout=20)
    return result.final_output

In a provisioned lab, first substitute an approved test model/transport, then evaluate one live run only within a budget. Assert that the ticket is read, that T1 is cited, and that output is a proposal—not a reported action. A timeout cancels local waiting; it does not prove the provider stopped computation or undo an external effect. Add the SDK's supported turn limits for the pinned release and enforce tool-call/spend limits outside model instructions.

Validate tool arguments, derive identity from trusted run context, check permissions at execution and use idempotency for writes. A guardrail that runs after generation cannot retroactively prevent a tool side effect. Review blocking versus concurrent behavior before relying on it. Bind approval to the exact action payload, actor and expiry. See guardrails and human review.

Interview: does a successful Runner result mean the workflow succeeded?

No. It may contain an unsupported statement or an unsuccessful tool result expressed fluently. Validate the task outcome against authoritative state and the trace. Test malformed arguments, denied actions, tool timeout, repeated calls and restart after approval.

Claude Agent SDK: runtime authority matters

The Claude Agent SDK wraps an agent runtime with tools, sessions and permission controls. It is different from sending one message to a model API: a run can inspect files or execute actions when those capabilities are enabled. Begin with a synthetic ticket, no repository secrets, an isolated working directory and a hard spending limit. Check the pinned SDK/runtime versions before adopting a recipe.

Read the permission evaluation order before configuring tools. allowed_tools pre-approves named tools; it is not an exclusive whitelist. Unlisted tools can still be available. dontAsk denies calls that would require a prompt, not necessarily every unlisted call. For a text-only baseline, current documentation supports disallowed_tools=["*"] to remove tool definitions. Recheck this behavior in the release you deploy.

Build the lab in two passes. First ask for a proposal from a synthetic ticket included in the prompt, with every tool removed. Then enable one narrowly scoped ticket-reading capability in a sandbox. Inspect the actual exposed tool inventory, not just your configuration list. Attempt an unrelated file read, a shell command and a write. Each prohibited action must fail at the enforcement boundary, with a recorded denial and no effect.

Keep authorization in the service that owns the data. A tool callback can be skipped by earlier auto-approval rules; use the documented pre-tool hook when a runtime check must precede every tool call, and still enforce access in the backing service. OS isolation and outbound-network controls limit damage if application controls fail. Avoid permission-bypass modes in this exercise.

Interview: why is a permission callback not a sandbox?

It governs a particular runtime decision path. It does not independently constrain subprocesses, network access or a backing service's credentials. A safe deployment combines verified tool exposure, service authorization, limited credentials and process/network isolation. Test every layer with an attempted violation.

Episodic memory: learn from an event without repeating its mistake

Semantic memory stores facts; procedural memory stores how to perform work; episodic memory stores a particular experience, including its context, action and observed outcome. A conversation transcript is not automatically useful episodic memory. A compact incident record might say: “Tenant A, policy v2, incident I17; restarting did not help; reverting configuration restored service; verified by error-rate recovery.” See the memory taxonomy.

Write an episode only after checking the outcome against authoritative evidence. Preserve unsuccessful attempts as unsuccessful: they can prevent repetition. Separate observation from interpretation, attach timestamps, source IDs, tenant, policy version, outcome and expiry, and remove secrets. A previous successful action is evidence to consider, not permission to repeat it.

Predict which episodes survive this filter before running it. The ranking stage comes later; eligibility must happen first.

episodes = [
    dict(id="I17", tenant="A", version=2, expires=200, verified=True, outcome="recovered"),
    dict(id="I18", tenant="B", version=2, expires=200, verified=True, outcome="recovered"),
    dict(id="I19", tenant="A", version=1, expires=200, verified=True, outcome="recovered"),
    dict(id="I20", tenant="A", version=2, expires=100, verified=True, outcome="recovered"),
    dict(id="I21", tenant="A", version=2, expires=200, verified=False, outcome="claimed success"),
    dict(id="I22", tenant="A", version=2, expires=200, verified=True, outcome="failed restart"),
]
def eligible(tenant, version, now):
    return [e for e in episodes if e["tenant"] == tenant
            and e["version"] == version and e["expires"] > now and e["verified"]]
assert [e["id"] for e in eligible("A", 2, 100)] == ["I17", "I22"]
assert eligible("C", 2, 100) == []

This fixture assumes trusted metadata and a fixed clock; it tests eligibility, not semantic retrieval, deletion propagation or real authorization. In practice, derive tenant identity from authentication and enforce document-level permissions too. Retain a link to the source so corrections or deletion can invalidate derived memories.

Practice feedback: what should the agent do with I22?

Use it as a counterexample to an unexamined restart recommendation. Check whether the current incident has the same cause before applying either episode. Stale, irrelevant or conflicting memories should trigger fresh investigation, not confident imitation.

Compare a no-memory baseline against episodic retrieval on ten held-out incidents. Count correct resolutions, harmful repeated actions, stale-memory use, latency and privacy failures. Tomorrow, reconstruct the episode schema and explain why storing only successes biases it.

Operational kill switches: stop authority, not just the chat window

A kill switch must stop new work and constrain queued or running actions. Closing a UI or cancelling a model request does not revoke a worker's credentials or undo a committed payment. Put an execution gate where effects occur, use short-lived authority, and record who stopped which tenant or run. The OWASP agent security guidance is a useful threat-model checklist.

This sequential fixture models generation-based fencing. Predict whether a queued job from generation 1 can execute after stopping and resuming.

# ponytail: sequential model; real effects need atomic receiver-side fencing.
state = {"enabled": True, "generation": 1}
effects = []
def dispatch(job_generation, action):
    if not state["enabled"] or job_generation != state["generation"]:
        return "denied"
    effects.append(action)
    return "applied"
def stop():
    state["enabled"] = False
    state["generation"] += 1
assert dispatch(1, "draft-only") == "applied"
stop()
assert dispatch(1, "queued-write") == "denied"
state["enabled"] = True  # Explicit operator-approved resume in the real system.
assert dispatch(1, "stale-retry") == "denied"
assert dispatch(2, "new-draft") == "applied"
assert effects == ["draft-only", "new-draft"]

This is not a distributed cancellation implementation. There is a check-to-effect race if the gate and mutation are separate. For a database effect, validate the fencing generation in the same serialized transaction as the mutation; all writers must obey it. For an external API, use provider-side revocation/cancellation where available and document the residual window. Already committed effects require reconciliation or an explicitly approved compensating action.

Run the operational drill in a provisioned test environment with a fake effect receiver: pause one worker before dispatch, leave another job queued, then activate the switch. Capture stop-request time, enforcement acknowledgements and the last accepted effect. Resume the paused worker and deliver the queued job twice. Neither stale attempt may create a new effect after the enforcement cutover. Restart a worker and repeat. Lose access to the control store and verify that sensitive actions fail closed.

Interview: what evidence proves the stop worked?

Receiver-side effect records, generation checks, queue disposition and worker acknowledgements—not a green UI badge. Report the measured stop latency and any in-flight effects accepted before enforcement. Resuming requires new authority; do not silently reactivate old jobs.

Gunicorn and Uvicorn: processes versus request handling

“Guvicorn” is interpreted here as Gunicorn. Uvicorn is an ASGI server suitable for FastAPI and supports its own worker-process mode. Gunicorn manages worker processes; the worker class determines the application protocol. A FastAPI ASGI application cannot simply be treated as a synchronous WSGI application.

For an already provisioned environment, a small Uvicorn deployment can start with uvicorn main:app --host 127.0.0.1 --port 8000 --workers 2. Do not combine production worker mode with development reload. See Uvicorn deployment. Bind addresses, trusted proxy headers and TLS termination must match your actual network boundary.

Current Gunicorn documentation also describes a native ASGI worker: gunicorn main:app --worker-class asgi --bind 127.0.0.1:8000 --workers 2. This is release-dependent: verify availability, maturity and supported features in your pinned release. Older deployments may use a separately maintained Uvicorn worker adapter. Do not copy a historical worker import path without checking its lifecycle. Neither command is executed by this lesson.

Every process has its own application state and usually its own connection pools. Four workers with a pool limit of ten can request forty database connections, plus migration/admin capacity. A model loaded in each worker can similarly multiply memory use. Async I/O allows a worker to wait efficiently; it does not make CPU-heavy PDF parsing nonblocking. Move that work to a bounded job executor.

Practice with a small test service: record the PID and request ID, send simultaneous slow requests, then replace one worker during traffic. Verify readiness, draining and response completion. For streaming, inspect proxy buffering, disconnect handling and time-to-first-byte. Configure a termination grace period compatible with bounded requests; long jobs should not depend on keeping an HTTP worker alive.

Interview: why not choose worker count from CPU cores alone?

Memory, database capacity, request concurrency, blocking code and latency targets can become the limit first. Measure throughput and tail latency under representative load, including slow clients and shutdown. More workers can make an overloaded dependency worse.

SAML: enterprise sign-in without confusing identity and access

SAML federation lets an identity provider (IdP) authenticate a user for a service provider (SP). In an SP-initiated flow, the SP sends an authentication request; the browser delivers the IdP response to the SP's assertion consumer service (ACS). The SP validates the response and creates its own session. An assertion is not an instruction to grant every application permission.

Use a maintained SAML implementation, vetted metadata and explicitly trusted signing keys. Do not write XML signature validation yourself. Validation must bind the authenticated, signed content to the values the application consumes. Check issuer, audience, destination/recipient, time conditions and—in an SP-initiated flow—the outstanding request correlation. Apply replay protection atomically and protect RelayState. Account for bounded clock skew and key rotation. Consult the OWASP SAML security checklist.

Tabletop exercise: an assertion is correctly signed but names a different audience; another is expired; a third has already been used; a fourth responds to an unknown request; a fifth is valid but its user has lost access to a document. Decide which boundary rejects each case before opening the answer.

Worked rejection boundaries

The first four fail the applicable federation validation/replay policy before session creation. The fifth can authenticate successfully, but application authorization must deny the document. Test IdP-initiated sign-in separately if intentionally supported: it does not have the same outstanding-request correlation and needs an explicit threat model, not an accidental bypass.

For RAG, map the stable federated identity to a local account and tenant. Resolve current groups and document permissions using trusted systems, not a model-selected tenant or an unverified claim. Apply access controls before retrieval and again before returning expanded parent documents. Cache entries must not leak responses across identities. Logout, session expiry and group revocation need a documented propagation policy.

In a provisioned identity test environment, exercise key rollover, replay, expired assertions and a removed group membership; retain redacted validation results, never raw production assertions. SAML covers federation, OAuth covers delegated authorization, and OIDC adds an identity layer to OAuth. None replaces your API's session/token validation or resource permissions.

ETL versus ELT: where transformation happens

Extract–transform–load (ETL) transforms records before loading the target system. Extract–load–transform (ELT) lands records first, then transforms them using the destination's compute. A landing zone is still a governed data store, not permission to retain arbitrary raw PII. See AWS's comparison. Many practical pipelines mix both: redact before landing, then normalize and aggregate downstream.

Choose based on sensitive-data policy, source formats, replay needs, compute capacity and how often transformations change. ETL can keep prohibited fields out of the destination; ELT can preserve an approved source representation for new transformations. Either approach needs schema contracts, lineage, access controls, retention, quarantine and reproducibility. CDC describes how changes are captured; it is independent of where transformation occurs.

For document ingestion, extraction produces source text and page evidence; transformation normalizes text, derives chunks and embeds them; loading publishes searchable records. Keep document version, chunker version and embedding-model version distinct. Use a versioned index or publication pointer so a user does not read a half-rebuilt document.

Predict the final state after out-of-order updates and a deletion. Here the source supplies an ordered revision per document; arrival time is not used as the authority.

latest = {}
events = [
    ("A", "d1", 2, "new text"),
    ("A", "d1", 1, "old text"),
    ("A", "d1", 3, None),
    ("A", "d1", 2, "late retry"),
    ("B", "d1", 1, "different tenant"),
]
for tenant, doc, version, text in events:
    key = (tenant, doc)
    if version > latest.get(key, (0, None))[0]:
        latest[key] = (version, text)
assert latest[("A", "d1")] == (3, None)
assert latest[("B", "d1")] == (1, "different tenant")
visible = {key: text for key, (_, text) in latest.items() if text is not None}
assert ("A", "d1") not in visible

The retained tombstone prevents an older update from resurrecting the document. A real implementation needs atomic compare-and-write, durable source offsets and a defined policy for equal-version conflicting payloads. If your source lacks ordered revisions, design reconciliation instead of pretending timestamps establish a total order. Deletion must reach chunks, vectors, caches and derived memories according to policy.

Interview: can you replay an ELT pipeline safely?

Only with a defined source snapshot/change log, deterministic or versioned transformations, idempotent outputs and publication rules. “We kept the raw data” is insufficient if permissions, source deletes or embedding versions are missing.

vLLM: operating an open-weight model service

vLLM is an inference-serving engine, not a model and not an agent framework. It schedules model execution and exposes serving interfaces, including an OpenAI-compatible API. Compatibility is an integration convenience, not a promise that every model supports identical tools, structured outputs or token accounting. Check the selected model, chat template, parser and server release with contract tests.

Read the vLLM serving reference. In an already provisioned GPU lab, use an approved model already present on disk and a pinned server image. Do not download or install anything to complete this reading exercise. A runbook must name the model license, weight revision, tokenizer, runtime, hardware and numerical precision so results are reproducible.

Distinguish prefill—the work over the prompt—from decoding successive output tokens. Measure time to first token, inter-token latency and total completion latency separately. Concurrent requests compete for compute and memory. Model weights are only part of memory use: KV cache, execution buffers and runtime overhead also matter. An eight-billion-parameter model at two bytes per parameter has roughly sixteen billion bytes of weights; that is not a sixteen-GB total-memory fit guarantee.

Practice a capacity experiment with fixed short/long prompt and output buckets. At each concurrency level record accepted throughput, p50/p95 latency, queue time, errors and peak memory. Repeat with the same quality evaluation after changing precision or context limits. Reject a configuration that looks faster only because it truncates required evidence or returns lower-quality answers.

Put the service behind authentication, per-tenant quotas, request-size limits and a bounded queue. Bind a local lab to loopback; production needs network isolation, TLS at the appropriate boundary, scoped credentials and redacted logs. A compatible endpoint should not be exposed anonymously. Separate readiness from liveness and test overload rejection, client cancellation, draining and model startup failure. Preserve an explicitly approved fallback policy rather than silently sending private data to an external provider.

Interview: when is self-hosting cheaper?

Compare cost per successful task at the required quality and latency, not GPU-hour price alone. Include utilization, spare capacity, operations, security, upgrades and failed requests. Low utilization or strict tail-latency targets can erase apparent savings. Data-residency requirements may still justify self-hosting independently of price.
