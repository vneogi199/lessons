Where an index leads, and when storage does the work

Read the shelf example first. Then trace one lookup and one update. Keep two questions separate: where are the rows stored, and how does the engine organize updates? These questions connect clustered indexes to B+ trees and LSM trees without treating them as interchangeable terms.

Clustered versus non-clustered indexes

Imagine books stored by catalogue number. Looking up a number takes you directly to the shelf position containing the book. A separate author catalogue contains the author's name and the book's catalogue number; you may need a second lookup to fetch the book. This is a useful analogy for clustered data and a secondary index.

Clustered rowstore index:
search key → internal pages → leaf containing the row

Non-clustered index over a clustered table:
secondary key → index leaf containing row locator → clustered lookup → row

Covering secondary index:
secondary key → leaf contains the requested columns → base lookup may be avoided

In SQL Server rowstore, the clustered index's leaf level contains table rows. A non-clustered index is separate and uses a row locator: a clustered key for a clustered table, or a row identifier for a heap. There is at most one clustered rowstore index per table, but several non-clustered indexes can support different queries. The primary-key constraint and the choice of clustering key are distinct decisions. See SQL Server index types.

Logical key order does not mean every page occupies adjacent physical disk space. Nor does an index promise SQL result order: use ORDER BY. A range can benefit from nearby rows while page splits, fragmentation, cache state and concurrent access still affect the actual work.

Read InnoDB clustered and secondary indexes and PostgreSQL CLUSTER. PostgreSQL CLUSTER takes an ACCESS EXCLUSIVE lock and needs additional disk space. Treat it as a planned maintenance operation, not a harmless query optimization to run on a live table.

For InnoDB, a wide primary key also occupies space in secondary indexes. A narrow, stable key can reduce that overhead. Random insert keys can spread writes and cause splits; increasing keys can concentrate writes on a hot edge. Do not turn either observation into a universal UUID-versus-integer rule. Measure contention, locality and workload requirements.

Trace a query before adding an index

Suppose trades have trade_id, account_id, created_at and amount. The screen requests the latest twenty trades for one account. An index beginning with account and then ordered time can narrow the search and support the ordering. Add a unique tie-breaker so equal timestamps produce a stable order.

-- PostgreSQL design example; run only in a disposable database with this schema.
CREATE INDEX trades_account_time
ON trades (account_id, created_at DESC, trade_id DESC)
INCLUDE (amount);

SELECT trade_id, created_at, amount
FROM trades
WHERE account_id = 42
ORDER BY created_at DESC, trade_id DESC
LIMIT 20;

Included columns provide payload, not another ordered search key. In PostgreSQL, an index-only scan may still visit heap pages to check visibility. The visibility map can make those checks unnecessary for eligible pages. Wider indexes cost storage, cache space and write work. See covering and index-only scans.

Compare this with a query selecting half the table. An index lookup followed by many base-row reads can be worse than a sequential scan. Selectivity, physical correlation, projected columns and row estimates all matter. Continue with lessons 0364 and 0365.

How a B+ tree finds a range

A B+ tree is a balanced search tree designed around pages with many keys. Internal pages hold separator keys and child references. Leaf pages hold the indexed entries. Those entries may contain rows or row locators, depending on the index. Linked leaf pages support ordered range traversal. Database documentation often uses “B-tree” for implementations in this family; do not assume every implementation uses the same page layout.

Root separator: 30
       ├─ keys below 30: [10, 20]
       └─ keys from 30:  [30, 40] → [50, 60]

Range 25..50: descend to the starting leaf, then scan leaves → 30, 40, 50

High fan-out keeps trees shallow. An insertion locates its leaf and changes a page; a full page may split and update its parent. Updates involve logging, dirty pages and later persistence, not necessarily one synchronous random disk write per row. Fill factor can leave room for future writes but increases space use. Inspect the engine's implementation, such as PostgreSQL B-tree internals, before making cost claims.

How an LSM tree postpones part of the work

A log-structured merge tree buffers updates in memory, then flushes sorted runs to storage. In a common durable setup, writes also enter a write-ahead log; acknowledgement durability depends on the configured persistence policy. Flushed sorted tables are often called SSTables. Background compaction merges runs and removes versions that are safe to discard. See the RocksDB overview.

write k=10 → WAL + memory table
flush      → sorted run A: {k:10}
write k=20 → memory table → sorted run B: {k:20}
read k     → choose the newest visible version: 20
compact    → merge runs; retain versions still needed by readers

Reads may inspect multiple runs. Indexes, caches and Bloom filters reduce unnecessary work. A Bloom filter can rule out a key from a run; a positive result still needs checking. Range reads merge ordered results and resolve versions. A delete writes a tombstone, a marker that hides an older value. Dropping it before the older value is safely removed can make deleted data reappear.

A snapshot may still need an older version. Safe compaction must consider visibility and which files contain older records. Our exercise assumes no snapshots and a complete set of runs when removing tombstones. It does not implement real engine compaction or crash recovery.

Define what you measure. If 100 MB of logical updates causes 600 MB of storage writes, write amplification is 6× for that accounting boundary. State whether WAL, replication and temporary files are included. Read amplification can mean bytes or I/O operations; use the same definition when comparing engines. Space amplification compares physical footprint with live logical data, with compression and replicas clearly accounted for.

Leveled compaction generally limits overlap and space at the cost of more rewriting. Tiered compaction can reduce rewriting while retaining more overlapping runs and increasing read/space costs. These are tendencies, not fixed ratios. Read RocksDB's compaction trade-offs. Measure steady-state writes while compaction is active; a short burst benchmark can hide work that the engine has postponed.

A trade blotter with selective reads and ordered account history may fit an existing B-tree database well. A high-ingest key-value workload may justify an LSM engine, provided its read behavior, compaction capacity and recovery model fit. Avoid “B+ trees are for reads, LSM is always faster for writes.” Compare realistic key distributions, record sizes, updates, deletes, cache budgets and p95/p99 latency.

Interview: is a primary key always a clustered index?

No. Explain the engine. PostgreSQL primary keys normally use separate unique indexes. SQL Server can separate the primary-key and clustering choices. InnoDB normally clusters by its primary key. Never infer the row layout from the words “primary key” alone.

Interview: why did adding a covering index slow writes?

Each relevant write now maintains another, wider structure. More payload can reduce reads but consume cache, storage and logging work. Measure the whole workload rather than judging only one SELECT.

Interview: inserts were fast for five minutes, then stalled. What would you inspect in an LSM engine?

Check pending compaction, flush backlog, level/run counts, disk bandwidth, free space and configured stall limits. Compare sustained throughput and read tails with the initial burst. Do not simply disable safety limits or compaction.

MCQ: a tombstone hides an older run's value. A) Drop it during any merge. B) Keep it until safe removal.

B. Removing the marker while an older value remains visible can resurrect the key. Snapshots and engine-specific visibility rules can delay safe removal further.
