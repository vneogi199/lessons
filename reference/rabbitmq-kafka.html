RabbitMQ and Kafka: choose from the workflow

Read the order example first. Then compare the two designs and try the crash exercise. The aim is to explain why a message can arrive twice, what your application must do, and which broker fits the requirement. This is design and offline practice; no broker installation is required.

A simple routing example

Imagine a restaurant. The order desk sends food tickets to the kitchen and drink tickets to the bar. The desk is an exchange, each destination's waiting tray is a queue, and a cook or bartender is a consumer. The routing rule is a binding. Two cooks sharing one tray divide the work; they do not each receive every ticket.

Producer → exchange: orders
              ├─ binding: food → kitchen queue → cook A or cook B
              └─ binding: drink → bar queue   → bartender

For two independent subscribers:
Producer → exchange → billing queue → billing worker
                    → audit queue   → audit worker

In RabbitMQ's AMQP 0-9-1 model, publish to an exchange with a routing key. Bind queues to the exchange. A direct exchange matches keys exactly; fanout routes to all bound queues; topic matches dot-separated keys with * for one word and # for zero or more words. A headers exchange routes using header conditions. A topic exchange is not a Kafka topic. See exchange types.

For example, binding order.*.created matches order.eu.created, not order.eu.priority.created. Binding order.# matches both. Do not use broad patterns for sensitive events without checking who can create bindings and read queues.

A connection is a network connection to the broker. Channels multiplex protocol conversations over it. A virtual host provides a logical namespace and permission boundary. Use separate credentials with only the required configure/write/read permissions, TLS and controlled network access. Do not put broker credentials in lesson code or message payloads.

Separate broker receipt from business completion

A publisher confirm covers publication to the broker under the selected queue's semantics. A consumer acknowledgement tells the broker that a delivery is handled. Neither establishes that another service completed the whole business workflow. With manual acknowledgements, acknowledge on the delivery's channel only after the intended durable effect. Prefetch bounds outstanding deliveries; tune it against processing time and memory. See confirms and acknowledgements.

When routing matters, use mandatory publication and handle returned unroutable messages as well as confirms. A publication can be confirmed yet have no matching queue. Treat connection loss before confirmation as an unknown outcome, not proof of rejection. Retrying can duplicate the publication. Keep a stable event ID across attempts.

1. Publish event e17.
2. Broker accepts it; producer loses the confirm.
3. Producer retries e17. A duplicate may now exist.
4. Worker commits e17's database effect.
5. Worker disconnects before its acknowledgement reaches the broker.
6. e17 is delivered again. The database must prevent a second effect.

For local database effects, insert an inbox identity and apply the change in one transaction. A uniqueness rule must include the intended consumer and tenant scope. Reject the same event ID with conflicting content. A separate “check whether processed” followed by a write races under concurrency. For email, payments or another remote effect, a local transaction alone is insufficient: use the destination's idempotency contract or reconcile an unknown result. Read RabbitMQ reliability guidance.

Choose the queue type and failure model

A durable queue declaration preserves queue metadata across restart; do not confuse it with confirmation of every business operation. Classic queues and quorum queues have different replication behavior. Quorum queues replicate using consensus and need a majority of their members available to make progress. A cluster containing several nodes does not make every queue replicated. Plan replica placement, disk capacity and failure recovery explicitly. See quorum queues.

For durable work, review queue type, message persistence, publisher confirms and consumer acknowledgements together. Losing a majority may sacrifice availability to preserve safety. Increasing replicas does not repair an application that acknowledges before committing its effect. Measure the required failure cases rather than promising zero loss from one configuration flag.

Retry without creating a hot loop

A transient error might succeed later; a malformed payload usually will not. For transient failures, choose a bounded attempt count, delay with jitter and a total deadline. Requeueing immediately during a database outage can repeatedly consume CPU without progress. After the retry budget, park the message for investigation and expose the reason safely.

A dead-letter exchange routes messages that leave a queue for configured reasons, such as rejection without requeue or expiration. Without the required dead-letter configuration, rejection can discard the message. Dead lettering itself has failure modes; do not assume every queue type and policy transfers messages with the same safety. TTL/retry-queue designs can delay messages beyond their nominal TTL because expired messages may wait behind other entries. Read dead-letter behavior.

If your application republishes a retry, confirm the replacement before acknowledging the original. A crash between those operations can still duplicate work. Retain the event ID and deduplicate effects. Record attempts durably; an in-memory counter resets after restart. Operators need a replay procedure that fixes the cause, checks expiry and preserves idempotency—not a button that blindly resends everything.

Kafka versus RabbitMQ

This table compares ordinary RabbitMQ work queues with Kafka's partitioned-log consumer-group model. RabbitMQ also has Streams: retained, replayable logs with non-destructive reading. Therefore, “RabbitMQ cannot replay” is too broad.

QuestionRabbitMQ work queuesKafka log model
How is work organized?Exchanges route to queues; consumers sharing a queue compete for deliveries.Records live in topic partitions; a consumer group assigns partitions to members.
How do independent applications subscribe?Give each application its own bound queue.Give each application its own consumer group.
What happens after processing?Acknowledged messages are removed from ordinary queues.Committed offsets advance group progress; retention controls record removal.
How does replay work?Use an explicit archive/replay design, or evaluate Streams.Read retained records from an earlier offset; expired data is not recoverable from the log.
What is ordered?Do not infer completion order with multiple consumers, redelivery or priority.Partition order, not one global order across partitions.
How is concurrency limited?Consumers, prefetch and application admission limits.Partition assignment and bounded processing; extra group members can be idle.
What happens after a crash?Unacknowledged work can be redelivered.Uncommitted progress can be processed again.

Kafka producer idempotence and Kafka transactions have defined broker-side scopes. They do not automatically make an arbitrary PostgreSQL write or HTTP call exactly once. Likewise, RabbitMQ confirms do not commit your database. Read Kafka's design and delivery semantics and specify the atomic boundary in your answer.

For a notification or document-conversion work queue, RabbitMQ is a reasonable candidate when explicit routing and independent job acknowledgement fit the workflow. For rates-market events feeding risk, analytics and replayable historical processing, Kafka is a reasonable candidate when partitioned ordering and retained consumption fit the workload. These are starting hypotheses. Compare retention needs, message sizes, failure recovery, required integrations and the team's operating experience. Do not invent a universal throughput winner.

Counterexample: must a task queue use RabbitMQ and an event pipeline use Kafka?

No. Kafka can distribute work, and RabbitMQ Streams can retain events for replay. Explain which model and operational trade-offs fit the requirement. An existing well-operated platform may be preferable to introducing a second broker.

Ordering and slow consumers

If two workers receive “set limit to 100” and “set limit to 200,” the second can finish first. Broker delivery order does not establish effect order. Use a per-entity version check, serialize work for that entity or make updates commutative where the business rule permits. A retry queue can allow later events to overtake a failed earlier event. Decide whether to block that entity, reject stale updates or repair a projection.

Monitor ready messages, unacknowledged deliveries, oldest-message age, retry/dead-letter growth, consumer capacity, disk alarms and connection churn. For Kafka, also inspect consumer lag per partition and rebalance behavior. A low queue count alone can hide a worker holding many unacknowledged messages. Autoscaling consumers will not fix an exhausted downstream database pool.

Connect this to outbox, sagas and transactions

Commit domain state and outgoing event intent together in a transactional outbox. The relay publishes and advances its progress only after the appropriate broker result. A relay crash can still cause duplicates. Consumers use inbox/idempotency rules for their local effects. This closes a dual-write gap; it is not a global database-and-broker transaction.

A saga coordinates business steps and compensations after local commits. Changing the broker does not remove compensation failures or irreversible actions. Two-phase commit has a different atomicity and availability contract. Continue with outbox/inbox, sagas and distributed transactions.

Trace the failure before running the exercise

  1. Use the offline exercise to route food and drink tickets. Predict exact-match and fanout destinations.
  2. Process e17, then simulate a lost acknowledgement by processing it again. Expect one database effect.
  3. Reuse e17 with a different amount. Expect rejection, not silent acceptance.
  4. Fail inside the transaction. Expect neither the inbox row nor the effect to commit. Retrying should then succeed once.
  5. Compare 12 failed attempts with a three-attempt budget. Only the first two failures should be eligible for another attempt; later failures go to review.

Before deploying a real adapter, test unroutable publication, lost confirms, disconnect before acknowledgement, broker restart, quorum loss, retry-target outage and poison-message handling. Verify delivery tags on the correct channel and actual SDK exception behavior. The offline model does not emulate RabbitMQ or Kafka and cannot establish those results.

Interview: the producer received a confirm. Can the API return “job completed”?

No. It can report the accepted publication only within the documented contract. Completion requires evidence from the business workflow. Expose a job ID and observable status rather than implying consumer success.

Interview: why does a dead-letter queue keep growing after scaling workers?

Inspect failure reasons, payload/schema compatibility, downstream capacity and retry policy. More consumers can accelerate failures. Repair the cause and replay with stable identities and limits; preserve the evidence of what failed.

MCQ: a worker commits, then loses its connection before ack. A) Duplicate delivery is possible. B) Duplicate delivery is impossible.

A. Deduplicate the local effect atomically. The broker cannot infer your database commit from a missing acknowledgement.

MCQ: two independent subscribers need every event. A) Share one ordinary queue. B) Bind two separate queues.

B for the RabbitMQ work-queue design. Consumers on one queue divide work. Separate queues retain independent progress; Kafka uses separate consumer groups for the corresponding log pattern.
