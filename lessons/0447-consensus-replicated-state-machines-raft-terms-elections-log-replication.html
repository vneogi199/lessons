04 · Detailed term guide

Elect one leader per term, replicate ordered commands to a majority, commit safely, apply deterministically, and change membership without allowing conflicting committed logs.

01

Consensus

Consensus lets fault-tolerant nodes choose one ordered history or value without two successful groups deciding conflicting results.

02

replicated state machines

Replicated state machines apply an agreed command sequence to deterministic state transitions across replicas.

03

Raft terms

Raft terms are monotonically increasing logical election epochs. Nodes persist the current term and vote; a higher term invalidates older leadership. A term can have no elected leader, and a term number alone does not prove a log entry committed.

04

elections

Elections select a leader under protocol rules; leadership must be tied to safety against stale or competing owners.

05

log replication

Log replication distributes ordered records and establishes commitment under a consensus or replication protocol.

06

safety

Distributed-systems safety means a forbidden outcome never occurs in executions allowed by the stated fault model. Arbitrary timing need not break safety, but stronger faults such as Byzantine behavior or lost durable state cannot be silently added to a crash-fault protocol's guarantees.

import assert from "node:assert/strict";
// Focused AppendEntries PRECHECK, not a Raft implementation. Trusted RPC fixture,
// serialized dispatch, zero-based log with sentinel term 0 at index 0.
async function onAppendEntries(node, message, persistHardState) {
  if (message.term < node.currentTerm) return { term: node.currentTerm, success: false };
  if (message.term > node.currentTerm) {
    // Higher term matters even when the log-prefix check will fail.
    await persistHardState({ currentTerm: message.term, votedFor: null });
    node.currentTerm = message.term;
    node.votedFor = null;
  }
  node.role = "follower";
  if (node.log[message.prevLogIndex]?.term !== message.prevLogTerm) {
    return { term: node.currentTerm, success: false };
  }
  // Deliberately STOP here: do not claim append success before log persistence.
  return { term: node.currentTerm, readyForLogProcessing: true };
}
const node = { currentTerm: 3, votedFor: "A", role: "candidate", log: [{ term: 0 }, { term: 3 }] };
const persisted = [];
const persist = async state => { persisted.push(state); };
assert.deepEqual(await onAppendEntries(node, { term: 4, prevLogIndex: 1, prevLogTerm: 2 }, persist),
  { term: 4, success: false });
assert.equal(node.currentTerm, 4);
assert.equal(node.votedFor, null);
assert.equal(node.role, "follower");
assert.deepEqual(persisted, [{ currentTerm: 4, votedFor: null }]);
assert.deepEqual(await onAppendEntries(node, { term: 3, prevLogIndex: 1, prevLogTerm: 3 }, persist),
  { term: 4, success: false });
assert.equal(persisted.length, 1);
assert.equal((await onAppendEntries(node, { term: 4, prevLogIndex: 1, prevLogTerm: 3 }, persist)).readyForLogProcessing, true);
await assert.rejects(onAppendEntries(node, { term: 5 }, async () => { throw new Error("disk failure"); }), /disk failure/);

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace a distributed request or message from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Partition the leader into a minority, elect a new leader, then let the old leader send a late write.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: Terms, votes, logs, commit indexes, membership, lease time, fencing token, rejected write, and applied state.
