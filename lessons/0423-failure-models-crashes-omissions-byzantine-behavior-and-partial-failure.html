Failure models, crashes, omissions, Byzantine behavior, and partial failure

An API defines communication rules. A distributed system coordinates work across processes and computers.

Senior practice for this track ↗ · The reading estimate excludes the lab and interview rehearsal.

Classify fail-stop, crash-recovery, send or receive omission, timing, corruption, and arbitrary faults while recognizing that one component can fail as others continue.

A distributed system is a team communicating by delayed letters: messages can arrive late, twice, out of order, or not at all, so correctness must survive uncertainty.

01

Failure models

Failure models define permitted faults such as crashes, omissions, partitions, or arbitrary behavior.

02

crashes

Crashes stop a participant's execution; recovery behavior depends on durable state and protocol design.

03

omissions

Omission failures lose a send, receive, or response while leaving uncertainty about other effects.

04

Byzantine behavior

A Byzantine component may behave arbitrarily or maliciously rather than merely stopping or omitting messages. It requires a stronger fault model and protocol.

05

partial failure

Partial failure means one component or link can fail while other parts continue, leaving observers with incomplete and sometimes contradictory evidence.

  { atMs: 300, action: "drop", link: "api->database", count: 1 },
  { atMs: 600, action: "reset", link: "api->client" },
  { atMs: 900, action: "pause", node: "worker-a", durationMs: 5000 },
  { atMs: 1200, action: "partition", groups: [["A"], ["B", "C"]] }
];

for (const fault of faultPlan) await injector.apply(fault);
await assertInvariant("one business effect per operation_id");
await assertBounded({ clientDeadlineMs: 2000, queueDepth: 100, attempts: 2 });
