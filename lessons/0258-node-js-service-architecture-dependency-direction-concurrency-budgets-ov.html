Node.js service architecture

Node service architecture keeps domain policy independent while adapters own HTTP, storage, queues, telemetry, configuration, and process lifecycle.

dependency direction

Dependency direction keeps application decisions from unnecessarily depending on transport or vendor details.

concurrency budgets

A concurrency budget caps in-flight work for each constrained dependency or execution boundary, turning overload into bounded waiting or rejection.

overload

Overload occurs when admitted work exceeds sustainable capacity. Queue growth increases latency until memory, timeouts, or dependencies fail unless the service sheds load.

resilience

Resilience preserves or restores useful behavior under failures using bounded work, isolation, recovery, and tested policies.

operations

Operations covers running, observing, changing, and recovering a service, with named owners and tested procedures.

A service needs capacity and ownership rules at each constrained boundary. Validation, persistence and total admission remain adapters and policies to supply in this sketch. Pipeline completion cannot undo rows already committed, so decide between partial imports and staged atomic publication. Optional telemetry should preserve the outcome; required audit storage needs an explicit failure contract. Size concurrency from measured capacity rather than an unused worker setting.

import http from "node:http";
import { pipeline } from "node:stream/promises";

export function createService({ repository, workers, telemetry, now }) {
  return async function ingest(request, response, signal) {
    const started = now();
    try {
      if (request.headers["content-type"] !== "application/x-ndjson") throw Object.assign(new Error("unsupported media type"), { statusCode: 415 });
      const validated = createValidationTransform({ maxLineBytes: 64 * 1024 });
      const persisted = createPersistenceSink(repository, { concurrency: 8, signal });
      await pipeline(request, validated, persisted, { signal });
      response.writeHead(202).end();
    } catch (error) {
      if (!response.headersSent) response.writeHead(error.statusCode ?? 500);
      response.end();
    } finally {
      telemetry.observe("ingest.duration", now() - started, { aborted: String(signal.aborted) });
    }
  };
}

// Integration sketch: supply validation/persistence adapters and authenticate before
// ingest. Bound total bytes as well as line bytes. The complete pipeline owns source
// errors and cancellation; request.pipe(transform) outside pipeline would not.
// Define whether a failed import permits committed rows: pipeline cannot undo prior
// database writes. Use staging plus atomic promotion for all-or-nothing imports, or
// document resumable partial success with per-record identities and saved outcomes.
// 202 requires durable acceptance of any remaining work; in-memory enqueue is not
// enough. Oversized request iteration may reset the socket before an error response.
// Evidence: body limit, queue depth, write backpressure, worker utilization,
// loop delay, latency, heap, stable errors, shutdown drain, and recovery runbook.
