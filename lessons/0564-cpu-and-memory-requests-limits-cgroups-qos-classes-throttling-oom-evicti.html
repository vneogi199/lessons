CPU and memory requests, limits, cgroups, QoS classes, throttling, OOM, eviction, and resource diagnosis

Kubernetes stores desired state in API objects. Controllers work continuously to make actual state match desired state.

Requests guide scheduling and resource accounting; limits constrain runtime consumption. A CPU quota can cause burst latency while average node use looks low. A memory limit can terminate a container, while node pressure can evict a Pod. The example's unequal requests and limits produce a Burstable configuration. CPU

CPU requests affect scheduling while limits can enforce throttling; CPU is not reserved by simply observing low average usage.

memory requests

A resource request is the amount used for scheduling and relative resource guarantees. Incorrect requests distort placement and autoscaling.

limits

A resource limit is enforced at runtime through cgroups. CPU is throttled, while exceeding a hard memory limit can terminate a container.

cgroups

Linux control groups account for and limit resources used by groups of processes, such as CPU and memory. Resource controls complement namespace isolation.

QoS classes

QoS classes categorize Pods from resource requests and limits and influence behavior under pressure.

throttling

CPU throttling limits execution when a configured quota is exhausted, potentially increasing latency without high node-wide CPU.

OOM

Out-of-memory failures occur when memory allocation exceeds a relevant limit or available capacity and can cause process termination.

eviction

Eviction removes Pods under supported pressure or administrative policies; it differs from a container restart.

resource diagnosis

Resource diagnosis connects symptoms to CPU, memory, I/O, queues, and limits using measurements before changing capacity or configuration.
