Production webhooks

A production webhook is an authenticated HTTP delivery from one system to another after an event. The receiver must expect delay, duplication, disorder, retries, and version changes.

event contracts

An event contract defines the event ID, type, version, time, subject, payload schema, and compatibility rules that providers and consumers share.

signatures

Webhook verification checks the provider's signed bytes and context using its specified algorithm. Stripe uses a shared-secret HMAC; other providers may use public-key signatures. Use the provider's verifier and preserve the original bytes.

timestamps

A signed webhook timestamp states when the provider created the delivery. A narrow acceptance window helps reject captured requests that are replayed later.

replay defense

A verified timestamp bounds accepted delivery age; it does not stop duplicates within that window. Scope event identity and atomically couple deduplication with local effects. External effects need their own idempotency or reconciliation boundary.

idempotency

Idempotency makes repeated execution of one logical operation produce no additional unintended effect. A durable unique key usually protects the business state.

retries

Retries repeat a failed delivery under a bounded schedule. Safe retries need timeouts, exponential backoff, jitter, idempotency, and a final failure destination.

ordering

Ordering describes which events are observed before others. Independent delivery attempts can complete out of order, so consumers use entity versions or current-state reads when order matters.

secret rotation

Secret rotation replaces signing credentials without interrupting delivery. A receiver temporarily accepts the active and previous secrets while recording which version verified each request.

// Integration exercise: Stripe SDK and your HTTP/database adapters are required.
// No SDK is installed by this review. Do not substitute a home-grown parser:
// Stripe-Signature can contain multiple v1 signatures during key rotation.
async function receive(request, stripe, endpointSecret, inbox, readBoundedRaw) {
  // Adapter must enforce the limit WHILE reading, before full allocation.
  const raw = await readBoundedRaw(request, 1_048_576);
  const signature = request.headers.get("stripe-signature");
  if (!signature) return new Response(null, { status: 400 });
  let event;
  try {
    event = stripe.webhooks.constructEvent(raw, signature, endpointSecret, 300);
  } catch {
    return new Response(null, { status: 400 });
  }
  // Adapter validates event type/schema, provider account and live/test mode,
  // then atomically stores scoped event identity + intent and durable job.
  // Replay returns the same acceptance; mismatched intent is rejected.
  await inbox.acceptVerifiedEvent(event);
  return new Response(null, { status: 204 });
}

// Local custom-HMAC mechanics are in 0414; that scheme is NOT Stripe-compatible.
// Integration evidence: original bytes succeed; reserialized bytes fail; invalid
// signature and stale timestamp return 400; rotation accepts active signatures;
// duplicate delivery creates one job; failed DB commit does not return 2xx.
// A timestamp window does not suppress in-window replay. Order workers by domain
// version or reconcile current provider state, not delivery arrival time.
// Keep endpoint secrets out of code/logs; record IDs and error categories only.
