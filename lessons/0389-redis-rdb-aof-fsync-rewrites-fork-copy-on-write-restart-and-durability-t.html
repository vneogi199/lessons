Redis RDB, AOF, fsync, rewrites, fork, copy-on-write, restart, and durability tradeoffs

A data system stores information and returns correct information when programs read or change that information.

RDB snapshots and AOF records preserve state through different policies and loss windows. Background persistence also needs memory for fork and copy-on-write activity. Inspect operation replies and persistence state rather than assuming snapshot and rewrite jobs start together. Multipart AOF recovery needs its manifest and referenced files. Verification or repair belongs on suitable offline copies, since repair can discard data.

Redis RDB

RDB persistence writes point-in-time snapshots, with potential loss of changes since the last recoverable snapshot.

AOF

AOF persistence records write commands for replay. Fsync policy controls the tradeoff among acknowledged-write loss, latency, and storage work.

fsync

fsync requests persistence through the OS storage stack; policy and storage guarantees affect acknowledged-data durability.

rewrites

AOF rewrites create a compact persistence representation while coordinating new changes and resource use.

fork

Redis persistence may fork a child process, introducing page-table and copy-on-write memory costs.

copy-on-write

Copy-on-write initially shares pages and copies them when modified, so concurrent writes can increase memory during persistence.

restart

Restart reconstructs Redis state from configured persistence; test the actual recoverable data rather than assuming all acknowledged writes survive.

durability tradeoffs

Durability trade-offs balance flush frequency, latency, throughput, and acceptable loss under specific failures.
