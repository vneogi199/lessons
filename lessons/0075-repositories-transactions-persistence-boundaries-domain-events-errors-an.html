Repositories, transactions, persistence boundaries, domain events, errors, and recovery

Low-level design assigns behavior and state to small software parts. Machine coding turns that model into a working, tested program under a time limit.

Senior practice for this track ↗ · The reading estimate excludes the lab and interview rehearsal.

A repository separates storage details from policy, but its name does not make several effects atomic. Writing a booking and then appending an event leaves a failure gap between them. A real transaction can store the booking and outbox intent together; publication can still happen more than once. Define stable identity, duplicate handling and recovery before describing the use case as atomic or safe to retry.

Repositories

A repository exposes persistence operations in terms of a domain contract, including transaction and failure expectations.

02

transactions

Transactions group operations under a defined atomicity and isolation contract. Effects outside the transaction need separate coordination.

03

persistence boundaries

Persistence boundaries identify where in-memory decisions become durable and where partial failure or concurrent updates can intervene.

04

domain events

A domain event records a business fact that has already happened in a domain model. Decide separately whether and how that fact becomes a stable integration contract.

05

errors

Errors report failed operations. Preserve useful causes, distinguish expected failures, and avoid leaking sensitive internal details.

06

recovery

Recovery restores a usable state after failure. Specify which data and effects survive, how work resumes, and how restoration is verified.

from dataclasses import dataclass

@dataclass(frozen=True)
class Booking:
    booking_id: str

class BookingRepository:
    def __init__(self) -> None: self.items: dict[str, Booking] = {}
    def add(self, booking: Booking) -> None:
        if booking.booking_id in self.items: raise ValueError("duplicate")
        self.items[booking.booking_id] = booking

def create_booking(booking_id: str, repository: BookingRepository, events: list[dict]) -> None:
    booking = Booking(booking_id)
    repository.add(booking)                 # authoritative change
    events.append({"type": "booked", "id": booking_id})  # separate in-memory effect, NOT an atomic commit

repository, events = BookingRepository(), []
create_booking("b-1", repository, events)
assert list(repository.items) == ["b-1"] and events == [{"type": "booked", "id": "b-1"}]
# A crash between add and append loses publication. A real implementation can
# commit booking plus outbox intent in one database transaction, then relay it.
