06 · Practical lab

Replace vague utilities with domain-named contracts when business meaning differs from mechanical transformation.

  1. Predict the state changes and one likely failure.
  2. Run the smallest working example and save the result.
  3. Change one condition, then run the same check again.
  4. Compare the evidence and explain the tradeoff.
type ElementOf<T> = T extends readonly (infer Item)[] ? Item : T;
type NonDistributive<T> = [T] extends [string] ? "text" : "other";
type EventName<K extends string> = `${K}Changed`;
type EventMap<T> = {
  [K in keyof T as K extends string ? EventName<K> : never]: T[K]
};

type A = ElementOf<string[] | number[]>; // string | number (distributed)
type B = NonDistributive<string | number>; // "other"
type C = Awaited<Promise<Promise<{ id: string }>>>;
type D = Pick<{ id: string; name: string; secret: string }, "id" | "name">;

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace a type-checking decision from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Change one inference site or union input and predict the instantiated result and cost.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: Quick Info, type assertion tests, diagnostic, declaration output, instantiation count, and check time.
