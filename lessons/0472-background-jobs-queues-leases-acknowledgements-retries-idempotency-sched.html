04 · Detailed term guide

How they connect: Follow a committed job through durable enqueue, reservation or visibility lease, execution, heartbeat, acknowledgment, retry, duplicate delivery, dead-letter handling, and graceful worker termination.

01

Background jobs

What it means: A background job is durable work executed outside the request that created it. The user-facing request stores intent, while workers process that intent later.

02

queues

What it means: A queue stores ready work between producers and consumers, absorbs bursts, and exposes lag, delivery, retry, and dead-letter state.

03

leases

What it means: A lease temporarily assigns a job to one worker until a deadline. If the worker disappears, expiry makes the unacknowledged job available again.

04

acknowledgements

What it means: An acknowledgement tells the queue that processing completed and the delivery can be removed. A crash before acknowledgement normally causes redelivery.

05

retries

What it means: Retries repeat a failed delivery under a bounded schedule. Safe retries need timeouts, exponential backoff, jitter, idempotency, and a final failure destination.

06

idempotency

What it means: Idempotency makes repeated execution of one logical operation produce no additional unintended effect. A durable unique key usually protects the business state.

07

scheduling

What it means: Job scheduling makes work eligible at a future time while preserving durable identity, cancellation, and behavior after downtime.

08

dead letters

What it means: A dead-letter store isolates jobs that exhausted attempts or cannot succeed, preserving error context for inspection, repair, replay, or deliberate discard.

09

worker shutdown

What it means: Worker shutdown stops claiming new jobs, gives in-flight work a deadline to finish, and safely releases or lets leases expire before the process exits.

from uuid import uuid4

# PostgreSQL-style lease algorithm. Each claim transaction commits BEFORE work.
# Schema: attempts NOT NULL DEFAULT 0; lease_owner stores an attempt UUID,
# not a reusable worker name. Worker identity is separate diagnostic metadata.
CLAIM = """
WITH candidate AS (
  SELECT id FROM jobs
  WHERE run_after <= now() AND (
    (state = 'ready' AND lease_until IS NULL)
    OR (state = 'running' AND lease_until < now())
  )
  ORDER BY run_after, id
  FOR UPDATE SKIP LOCKED LIMIT 1
)
UPDATE jobs SET state = 'running', attempts = attempts + 1,
  lease_owner = %(worker)s, lease_until = now() + interval '30 seconds'
WHERE id = (SELECT id FROM candidate)
RETURNING *
"""

def run_one(db, worker, stopping):
    if stopping.is_set(): return False
    owner = str(uuid4())
    job = db.fetch_one(CLAIM, {"worker": owner})
    if not job: return False
    try:
        # Business table has UNIQUE(job.id); repeated delivery cannot repeat effect.
        perform_idempotently(job)
        deleted = db.execute("DELETE FROM jobs WHERE id=%s AND lease_owner=%s AND lease_until > clock_timestamp()", job.id, owner)
        if deleted.rowcount != 1:
            raise LeaseLostError("do not acknowledge another attempt's work")
    except RetryableError as error:
        delay = min(3600, 2 ** min(job.attempts, 10))
        db.retry_after(job.id, owner, delay, safe_error_code(error))
    except PermanentError as error:
        db.move_to_dead_letter(job.id, owner, safe_error_code(error))
    return True

# On SIGTERM: stop claiming, extend or release owned leases, finish within the
# shutdown deadline, then exit. Another worker recovers any expired lease.
# retry_after/dead-letter/heartbeat adapters require the same owner + live lease
# predicate and check affected rows. LeaseLostError propagates to the supervisor.
# Uniqueness alone is not idempotency: receipt and business effect must commit
# together with intent checking; remote effects need provider idempotency or
# reconciliation. Lease expiry does not stop a paused worker from performing I/O.
# Integration test: pause attempt A past expiry, reclaim as B, resume A; A must
# not delete, retry or extend B's lease. Verify effect deduplication separately.

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace a background job delivery from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Crash after the business effect but before acknowledgment, wait for the lease to expire, and let another worker receive the same job.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: Job and idempotency IDs, enqueue commit, lease owner/deadline, attempts, heartbeat, business effect count, retry time, dead letter, and queue lag.
