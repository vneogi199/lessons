Networking moves messages between programs and machines. An operating system manages processes, memory, files, devices, and protected access to hardware.

A lock must protect the complete rule that concurrent operations could break. For a transfer, both the balance check and the debit and credit belong under the locks. Acquiring shared locks in a consistent order prevents circular acquisition for this operation. Every participant must use the same locks. A semaphore limits permits, while a condition variable waits for a predicate that must be rechecked after waking. Several atomic operations do not automatically make their combination atomic.

Race conditions

A race condition makes correctness depend on an uncontrolled ordering of concurrent actions.

locks

A lock coordinates access to shared state. Protect the whole invariant, define lock ordering, and release the lock on every exit path.

semaphores

A semaphore controls access using a count of permits. It can bound concurrent operations, but the waiting queue and cancellation behavior also need limits.

condition variables

A condition variable lets a thread wait for a predicate protected by a lock. Recheck the predicate after waking because notification alone does not establish it.

atomics

Atomic operations provide indivisible access and specified memory-ordering guarantees; composing several atomics does not automatically preserve a larger invariant.

deadlocks

A deadlock is a cycle of operations waiting for resources held by one another. Consistent ordering, bounded waits, and smaller critical sections can help prevent or recover from it.

lock ordering

Lock ordering requires code paths to acquire shared locks in a consistent order. It prevents a common class of circular waits when multiple locks are needed.

from dataclasses import dataclass, field
from threading import Lock, Thread

@dataclass
class Account:
    number: int
    balance: int
    lock: Lock = field(default_factory=Lock)

def transfer(source: Account, target: Account, amount: int) -> None:
    if type(amount) is not int or amount <= 0:
        raise ValueError("positive integer amount required")
    if source is target:
        raise ValueError("distinct accounts required")
    first, second = sorted((source, target), key=id)
    with first.lock, second.lock:  # one global lock order prevents circular wait
        if source.balance < amount:
            raise ValueError("insufficient funds")
        source.balance -= amount
        target.balance += amount

a, b = Account(1, 100), Account(2, 100)
threads = [Thread(target=transfer, args=(a, b, 10)), Thread(target=transfer, args=(b, a, 20))]
for thread in threads: thread.start()
for thread in threads: thread.join()
assert a.balance + b.balance == 200
assert (a.balance, b.balance) == (110, 90)
for source, target, amount in [(a, a, 1), (a, b, -1), (a, b, True), (a, b, 1000)]:
    try: transfer(source, target, amount)
    except ValueError: pass
    else: raise AssertionError("invalid transfer accepted")
# Object identity orders live locks within this process even if account numbers
# collide. Require one shared Account object per account; this is not a database
# or cross-process locking protocol, and all balance readers/writers must cooperate.
# The lock protects the total-balance invariant; ordering protects progress.
