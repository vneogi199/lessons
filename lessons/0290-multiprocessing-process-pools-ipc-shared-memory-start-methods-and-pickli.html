Multiprocessing

Multiprocessing uses separate processes for isolation and CPU parallelism. Inputs and results normally cross serialization and inter-process communication boundaries.

process pools

A process pool reuses worker processes for submitted callables. Startup, serialization, data copying, failure recovery, and shutdown can outweigh small tasks.

IPC

Inter-process communication transfers data or coordination between processes, using mechanisms such as pipes, sockets, or shared memory. Each mechanism has ownership and synchronization costs.

shared memory

Shared memory allows participants to access the same storage. It reduces copying but requires synchronization and explicit ownership.

start methods

Multiprocessing start methods control how a child process begins: spawn starts a fresh interpreter, fork copies the parent process state, and forkserver asks a server process to fork. Availability and defaults depend on platform and Python version; choose an explicit compatible context.

pickling

Pickle serializes Python-specific objects and can execute code during loading. Never treat untrusted pickle data as safe input.

A worker process has separate execution state. Sending work to it normally involves serialization and communication, which can outweigh the benefit for small jobs. A process pool reuses workers to reduce startup work. Shared memory can reduce copying but needs explicit ownership and synchronization. Start methods determine how workers begin and what they inherit; choose a supported method rather than assuming the same default on every platform.

ELI5 example

Two separate processes are like workers with separate notebooks. Changing a normal Python list in one process does not automatically change the other process's list.

They must exchange data or use explicit shared memory. Sending objects can require serialization, which costs time and can fail for unsupported objects. How a process starts also affects what it inherits.

Does a child process automatically share every ordinary mutable object with its parent?

No. Use an explicit communication or shared-memory design.

from concurrent.futures import ProcessPoolExecutor
import multiprocessing as mp

def count_primes(limit: int) -> int:
    def prime(value: int) -> bool:
        return value > 1 and all(value % divisor for divisor in range(2, int(value ** 0.5) + 1))
    return sum(prime(value) for value in range(limit))

if __name__ == "__main__":
    context = mp.get_context("spawn")
    with ProcessPoolExecutor(max_workers=4, mp_context=context) as pool:
        futures = [pool.submit(count_primes, limit) for limit in (40_000, 42_000)]
        try:
            print([future.result(timeout=10) for future in futures])
        except BaseException:
            for future in futures:
                future.cancel()
            raise

# Save this as a real .py file; spawn workers must import the main module.
# Top-level callables and arguments cross the process boundary via serialization.
# Future timeout/cancel does not terminate running work, and context-manager exit
# waits for running jobs. Use cooperative stop or an explicit process supervisor
# when shutdown has a hard deadline.
