TCP flow control, congestion control, slow start, AIMD, retransmission, backpressure, and overload

Networking moves messages between programs and machines. An operating system manages processes, memory, files, devices, and protected access to hardware.

Senior practice for this track ↗ · The reading estimate excludes the lab and interview rehearsal.

The receiver's window limits how much outstanding data it can accept. The congestion window limits sending according to estimated network capacity. The smaller window constrains outstanding data; subtract bytes already in flight to find the allowance for new data. Slow start and later growth respond to acknowledgements and congestion signals. Retransmission repairs missing stream data. Applications also need admission limits and backpressure, because bounded socket buffers cannot bound an upstream work queue.

TCP flow control

TCP flow control uses the receiver's advertised window to avoid sending more outstanding data than it can accept.

congestion control

Congestion control adapts sending pressure to network conditions, distinct from a receiver's buffer capacity.

slow start

Slow start increases TCP's congestion window rapidly from a small starting point until a threshold or congestion signal changes behavior.

AIMD

Additive increase and multiplicative decrease cautiously raises sending allowance and sharply reduces it after congestion evidence.

retransmission

Retransmission sends unacknowledged data again after loss is inferred. The receiver must distinguish repeats from new bytes.

backpressure

Backpressure makes a producer slow down when a consumer cannot keep up. It limits queued work rather than allowing memory and latency to grow without bound.

overload

Overload occurs when offered work exceeds sustainable capacity, growing queues or causing rejection and failure.

# Toy round/RTT-level trace, NOT an update for every ACK or a real TCP stack.
def congestion_trace(rounds: int, loss_at: int) -> list[int]:
    window, threshold, trace = 1, 8, []
    for step in range(rounds):
        trace.append(window)
        if step == loss_at:
            threshold = max(2, window // 2)
            window = 1
        elif window < threshold:
            window *= 2                 # slow start
        else:
            window += 1                 # additive increase
    return trace

trace = congestion_trace(9, loss_at=5)
assert trace[:5] == [1, 2, 4, 8, 9]
assert trace[6] == 1

receiver_window = 6
window_limit = min(trace[4], receiver_window)
assert window_limit == 6
in_flight = 3  # same toy units as the windows, not measured bytes
new_data_allowance = max(0, window_limit - in_flight)
assert new_data_allowance == 3
# Flow control protects the receiver; congestion control protects the path.
# This reset models a timeout, not fast recovery after duplicate ACKs. Real
# slow start grows with acknowledgments (roughly doubling per RTT), and modern
# implementations differ in initial window, recovery and congestion algorithm.
# Application backpressure must still bound work before bytes reach the socket.

A window limit is not all new capacity

The toy trace reaches congestion window 9. The receiver advertises 6, and 3 units are already in flight.

Outstanding-data limit
min(9, 6) = 6
New-data allowance
6 − 3 already in flight = 3

These are toy units and RTT rounds, not measurements from a live TCP implementation.

Answer checkpoints

No. That would raise outstanding data to 9 and exceed the limit of 6. Subtract in-flight data first.
