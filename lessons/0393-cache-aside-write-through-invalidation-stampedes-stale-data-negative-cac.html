04 · Detailed term guide

How they connect: Trace cache hits and misses against an authoritative store, version or invalidate entries, bound staleness, collapse concurrent fills, randomize expiry, and protect missing-value lookups.

01

Cache-aside

What it means: Cache-aside reads the cache first, loads a miss from the authoritative store, and writes the result back. The application owns invalidation, stampede control, and outage fallback.

02

write-through

What it means: Write-through caching updates the cache as part of the write path under a defined failure and ordering policy.

03

invalidation

What it means: Invalidation prevents stale cached data from being served after a relevant change. Coordinate keys, versions, and races explicitly.

04

stampedes

What it means: Cache stampedes occur when many misses trigger duplicate expensive work; coordination and expiry spreading can reduce them.

05

stale data

What it means: Stale data reflects an earlier state; define which staleness is acceptable and how clients detect or recover from it.

06

negative caching

What it means: Negative caching stores absence or failure results briefly to avoid repeated work, with careful invalidation and error classification.

07

consistency

What it means: Consistency specifies which combinations and orderings of observations are permitted. Name the model instead of treating consistency as a boolean.

// Adapter core: authorize tenant/project BEFORE cache access; validate inputs.
// Redis commands need client-enforced deadlines; DB fallback needs bounded
// admission. Catching a rejection alone cannot stop a hung operation.
async function loadProject(tenant, id, version, redis, database) {
  const key = "project:" + JSON.stringify([tenant, id, version]);
  try {
    const cached = await redis.get(key);
    if (cached !== null) {
      const value = JSON.parse(cached);
      if (value === null || (value.tenantId === tenant && value.id === id && value.version === version)) return value;
    }
  } catch {
    // Cache read/parse failure is a miss; production records failure metrics.
  }

  // Production: use bounded single-flight per key to collapse concurrent fills.
  const project = await database.findProjectVersion(tenant, id, version);
  // Adapter must return this exact version or null, never the latest row under
  // an older version's key. A historical read needs historical storage.
  if (project !== null && (!project || project.tenantId !== tenant || project.id !== id || project.version !== version)) {
    throw new Error("database returned the wrong project version");
  }
  const ttlSeconds = project !== null ? 300 + Math.floor(Math.random() * 60) : 15;
  try {
    await redis.set(key, JSON.stringify(project), { EX: ttlSeconds });
  } catch {
    // Cache fill is optional; production records failure metrics.
  }
  return project;
}

// PostgreSQL remains authoritative; DB errors propagate, not cached as null.
// The caller still needs an authoritative version for "latest" reads; versioned
// keys alone do not provide freshness. A negative hit can hide a newly created
// version for 15 seconds. Read the primary for read-after-write guarantees.
// ponytail: single-flight and admission control are exercise requirements,
// not implemented by this small adapter; add them before outage/load testing.
