Technical writing and architecture decisions

01 · Core foundation

This topic belongs to software engineering work. Software engineering uses repeatable tools and records to change software safely.

Senior practice for this track ↗ · The reading estimate excludes the lab and interview rehearsal.

02 · Mental model

Understand how written context reduces coordination cost in distributed teams.

Write for the reader's next action. A README explains purpose and entry points; a runbook gives symptoms, safe checks, mitigation, verification and escalation; an incident note separates observed timeline from hypotheses; a pull-request description states what changed, why, tests and rollout risk. An ADR records a significant choice with context, alternatives and consequences. Keep assumptions distinguishable from measurements. Under the linked ADR process, accepted decisions are superseded by a new record when circumstances change, rather than silently rewriting their historical rationale.

A decision record is the reasoning attached to a fork in the road, so the next team knows both why you turned and when a different route would make sense.

06 · Practical lab

Write READMEs, runbooks, ADRs, incident notes, and concise pull-request descriptions.

Tabletop writing exercise, not runnable shell code or an implemented outbox. Rewrite the proposed decision below after changing notification delivery from required to best effort. Then write a five-line runbook for rising outbox age: symptom, safe diagnosis, mitigation, verification and owner. Do not invent measured latency or a completed failure-injection test.

  1. Predict the state changes and one likely failure.
  2. Prepare the specified fixture or tabletop scenario, carry out the exercise, and save the evidence. The specification itself is not executable code.
  3. Change one condition, then run the same check again.
  4. Compare the evidence and explain the tradeoff.
# Exercise: worked decision record — synthetic assumptions, not measured facts
Title: Start the notification worker with a database outbox
Status: Proposed
Context: Notification loss after order commit is unacceptable. Assume 20 events/s
and a five-second delivery objective. One team owns the database and worker.
Options: Direct post-commit publish; transactional outbox; distributed transaction.
Decision: Write order and outbox row in one database transaction; relay separately.
Reason: Direct publish has a crash gap. An outbox keeps the durable intent with
the order while avoiding a distributed transaction in the request path.
Consequences: Relay can publish duplicates. Consumers need stable event identity
and idempotent effects. Monitor oldest unpublished age and retained row growth.
Verification: Kill the worker after publish but before marking the row sent;
expect redelivery without a second business effect. Measure delivery lag at load.
Revisit: If polling cost or latency misses the objective, evaluate CDC with evidence.
Owner: Name the team that handles replay, retention, and incidents before approval.
# Practice: defend direct publication if notifications become best-effort analytics.
# Feedback: a strong answer changes the decision when the loss constraint changes;
# a weak answer calls the outbox exactly-once or ignores cleanup and ownership.

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace an engineering change from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: If notification loss becomes acceptable, which complexity can be removed?

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: A decision record must separate assumed numbers from measured evidence and explain when its conclusion changes.

Explain the database-commit/publish crash gap and why durable intent does not remove duplicate delivery. A consumer must make its local effect idempotent atomically with deduplication, or use the external provider's idempotency contract; merely remembering an event ID is insufficient. Best-effort analytics may justify simpler direct publication. A good record states this changed constraint, rejected alternatives, operational cost, owner and revisit trigger; it does not describe the preferred technology as universally best.
