Treat the interview as collaborative constraint discovery followed by explicit invariants, critical paths, rough capacity, failure handling, observability, security, and staged evolution.

01

System-design interviews

A system-design interview is a collaborative exercise in clarifying constraints, defining guarantees, estimating scale, tracing critical paths, and evolving a defensible design.

02

requirements

Requirements state observable needs and constraints. Separate required behavior from an implementation someone happens to prefer.

03

estimates

Estimation approximates quantities from explicit assumptions. Show the calculation, plausible range, and sensitivity to uncertain inputs.

04

APIs

An API exposes an interaction contract: inputs, outputs, failures, permissions, and compatibility obligations.

05

data

Data is a representation of observations or state. Its meaning depends on schema, provenance, units, and freshness.

06

scaling

Scaling increases capacity for a defined workload. Identify the limiting resource and the new coordination or cost introduced.

07

reliability

Reliability is sustained correct service under stated conditions. Define failure, measure it, and test recovery instead of relying only on availability claims.

08

evolution

Evolution changes a system while supporting existing users and data. Plan compatibility, rollout order, and rollback constraints.

Common mistakes

Memorizing the label

A definition is not enough. Trace an interview decision and its evidence from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Change one dominant constraint mid-answer and evolve the design while preserving its key invariant.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: Requirements, estimate, diagram, invariant, failure path, metric, evaluation, and decision.
