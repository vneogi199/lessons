01 · Beginner foundation

This topic belongs to software design. Software design arranges code, state, and dependencies so correct behavior is clear and future changes remain safe and reasonably small.

Input → output
Something starts the operation. The system returns a value, effect, message, or error.
Boundary and state
A boundary separates system parts. State is information a part keeps or changes.
Mechanism and evidence
The mechanism does the work. A test, log, trace, or state change shows what happened.
Failure and tradeoff
A failure mode describes how it can break. A tradeoff is the cost of choosing one solution over another.
02 · Mental model

Treat smells as investigation signals, capture current observable behavior, create a controllable seam, apply one named transformation, run tests after each step, and separate structural change from feature change.

Analogy: Software design is arranging a workshop: frequently changing work stays easy to reach, dangerous machinery sits behind guards, and each tool earns its space by solving a real task.

04 · Detailed term guide

How they connect: Treat smells as investigation signals, capture current observable behavior, create a controllable seam, apply one named transformation, run tests after each step, and separate structural change from feature change.

01

Code smells

What it means: Code smells are quick signals that may indicate a deeper design problem. A smell starts investigation; it does not prove that code is wrong.

02

characterization tests

What it means: Characterization tests record the observable behavior of existing code, including surprising behavior, before risky restructuring begins.

03

refactoring

What it means: Refactoring changes internal code structure through small behavior-preserving steps to make future work safer or cheaper.

04

seams

What it means: A seam is a place where behavior or a dependency can be changed or controlled without editing the code that uses it.

05

small steps

What it means: Small refactoring steps keep each transformation easy to review, test, diagnose, and reverse.

06

behavior preservation

What it means: Behavior preservation means refactoring keeps the externally required outputs, side effects, failures, and contracts unchanged.

07

review evidence

What it means: Review evidence is the focused test, diff, dependency graph, measurement, or explanation that supports a claim that design improved without breaking behavior.

06 · Practical lab

Refactor a long conditional with duplicated calculations using extract function, introduce parameter object, and replace conditional with strategy while keeping every commit executable.

  1. Predict the state changes and one likely failure.
  2. Run the smallest working example and save the result.
  3. Change one condition, then run the same check again.
  4. Compare the evidence and explain the tradeoff.
type LegacyOrder = { kind: "standard" | "member"; subtotal: number; shipping: number };

// Characterization tests capture current observable behavior before restructuring.
function legacyTotal(order: LegacyOrder): number {
  const discounted = order.kind === "member" ? order.subtotal * 0.9 : order.subtotal;
  return discounted + order.shipping;
}

const cases = [
  { input: { kind: "standard", subtotal: 100, shipping: 5 } as const, expected: 105 },
  { input: { kind: "member", subtotal: 100, shipping: 5 } as const, expected: 95 },
];

type Discount = (subtotal: number) => number;
const discounts: Record<LegacyOrder["kind"], Discount> = {
  standard: subtotal => subtotal,
  member: subtotal => subtotal * 0.9,
};
function refactoredTotal(order: LegacyOrder) { return discounts[order.kind](order.subtotal) + order.shipping; }

for (const test of cases) {
  console.assert(legacyTotal(test.input) === test.expected);
  console.assert(refactoredTotal(test.input) === test.expected);
}

07 · Code reading guide
  1. Find the setup and the input that starts the example.
  2. Follow the lines that read state, make a decision, or produce an output.
  3. Change one input. Predict the result, run the code, and compare.

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace a requirement-driven code change from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Refactor one smell through separate executable commits and deliberately break a characterization test between two steps.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: Baseline outputs, test result per commit, diff, complexity, dependency count, runtime profile, and review explanation.
