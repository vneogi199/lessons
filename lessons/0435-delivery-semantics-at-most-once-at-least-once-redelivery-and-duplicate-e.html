Delivery semantics, at-most-once, at-least-once, redelivery, and duplicate effects

An API defines communication rules. A distributed system coordinates work across processes and computers.

Senior practice for this track ↗ · The reading estimate excludes the lab and interview rehearsal.

Acknowledging before an effect risks losing work after a crash. Acknowledging afterward permits delivery again when the effect succeeded but acknowledgement failed. An inbox can make repeated delivery safe for a local effect when both commit in one transaction. That guarantee depends on identity, retained records and durable storage. It does not extend automatically to an external business action.

Delivery semantics

Delivery semantics describe message-delivery guarantees under failures, not automatically the number of external business effects.

at-most-once

At-most-once processing avoids duplicates by acknowledging before or instead of retrying, which allows loss when failure occurs.

at-least-once

At-least-once delivery permits redelivery while retaining unacknowledged work under stated durability, retention and eventual-recovery assumptions. It does not guarantee delivery after arbitrary data loss or expiry, nor does it prevent duplicate business effects.

redelivery

Redelivery retries message delivery after uncertain or failed processing and can repeat previously completed effects.

duplicate effects

Duplicate effects occur when repeated attempts apply a business action more than intended; deduplicate at the authoritative effect boundary.

// Integration core; caller authenticates producer, authorizes tenant and validates
// the envelope before this point. The database adapter is scoped to this tenant
// and logical consumer, NOT to a transient worker-instance ID.
async function consume(record, database, broker) {
  await database.transaction(async tx => {
    const claimed = await tx.inbox.insertIfAbsent(record.eventId, record.data);
    if (!claimed) return; // already committed locally
    await tx.applyBusinessEffect(record.data);
  });
  await broker.ack(record); // crash before this line => safe redelivery
}

// Ack before the transaction risks loss. Ack after it risks redelivery.
// Atomic inbox + local effect turns redelivery into the same local outcome;
// external effects need their own operation identity and reconciliation.
// Required adapter contract: a unique (tenant, logical consumer, event ID) claim
// and effect commit together; exceptions roll back both. Duplicate claims must
// compare canonical intent and reject changed data rather than silently discard it.
// Keep inbox entries through the replay window. Deleting them permits repeats.
// broker.ack must acknowledge this delivery only (or a contiguous completed
// offset prefix), never skip unfinished earlier work. An ack error after commit
// means replay is possible; it does not justify undoing the committed effect.
