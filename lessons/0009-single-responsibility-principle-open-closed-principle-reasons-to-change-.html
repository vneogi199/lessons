01 · Beginner foundation

This topic belongs to software design. Software design arranges code, state, and dependencies so correct behavior is clear and future changes remain safe and reasonably small.

Input → output
Something starts the operation. The system returns a value, effect, message, or error.
Boundary and state
A boundary separates system parts. State is information a part keeps or changes.
Mechanism and evidence
The mechanism does the work. A test, log, trace, or state change shows what happened.
Failure and tradeoff
A failure mode describes how it can break. A tradeoff is the cost of choosing one solution over another.
02 · Mental model

Analogy: Software design is arranging a workshop: frequently changing work stays easy to reach, dangerous machinery sits behind guards, and each tool earns its space by solving a real task.

04 · Detailed term guide

How they connect: Identify actors and independent change axes, then add variation behind a proven stable contract without turning every conditional into an interface or predicting requirements that do not exist.

01

Single Responsibility Principle

What it means: The Single Responsibility Principle says a module should be responsible to one actor or cohesive reason to change, not that every function must contain one line.

02

Open-Closed Principle

What it means: The Open-Closed Principle says a stable unit can support a proven kind of variation through extension without repeatedly modifying its trusted core.

03

reasons to change

What it means: Reasons to change are independent actors, policies, technologies, or requirements that can evolve on different schedules.

04

extension points

What it means: An extension point is a deliberate contract where known variation can be added. It earns its cost only when real alternatives exist.

05

plugin boundaries

What it means: A plugin boundary loads independently implemented behavior through a stable contract while controlling compatibility, authority, lifetime, and failure isolation.

06 · Practical lab

Split mixed pricing and notification policy, add a second pricing rule through one tested extension seam, and compare the simpler conditional alternative.

  1. Predict the state changes and one likely failure.
  2. Run the smallest working example and save the result.
  3. Change one condition, then run the same check again.
  4. Compare the evidence and explain the tradeoff.
type Quote = { subtotal: number; customer: "standard" | "member" };
type PricingRule = { name: string; applies(quote: Quote): boolean; price(quote: Quote): number };

const memberDiscount: PricingRule = {
  name: "member-discount",
  applies: quote => quote.customer === "member",
  price: quote => quote.subtotal * 0.9,
};

const standardPrice: PricingRule = {
  name: "standard",
  applies: () => true,
  price: quote => quote.subtotal,
};

export function price(quote: Quote, rules = [memberDiscount, standardPrice]): number {
  if (quote.subtotal < 0) throw new RangeError("subtotal");
  const rule = rules.find(candidate => candidate.applies(quote));
  if (!rule) throw new Error("no pricing rule");
  return rule.price(quote);
}

// Pricing owns pricing changes. Notification belongs elsewhere. Add a rule only
// when a real variation exists; one stable conditional can remain a conditional.
console.assert(price({ subtotal: 100, customer: "member" }) === 90);

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace a requirement-driven code change from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Apply one realistic change before and after the refactor and compare how much unrelated code must be understood or edited.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: Passing behavior tests, dependency graph, affected files, mutation points, complexity, reader explanation, and review feedback.
