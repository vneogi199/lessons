Single Responsibility Principle, Open-Closed Principle, reasons to change, extension points, and plugin boundaries

Software design arranges code, state, and dependencies so correct behavior is clear and future changes remain safe and reasonably small.

Senior practice for this track ↗ · The reading estimate excludes the lab and interview rehearsal.

Pricing and notification rules may have different owners and change at different times. Separating them gives each responsibility a clear place to change. Within pricing, an extension point can support a known variation, such as a second discount rule. It also adds a contract and ordering rules to maintain. Compare it with a conditional before assuming every future variation needs a plugin.

01

Single Responsibility Principle

The Single Responsibility Principle says a module should be responsible to one actor or cohesive reason to change, not that every function must contain one line.

02

Open-Closed Principle

The Open-Closed Principle says a stable unit can support a proven kind of variation through extension without repeatedly modifying its trusted core.

03

reasons to change

Reasons to change are independent actors, policies, technologies, or requirements that can evolve on different schedules.

04

extension points

An extension point is a deliberate contract where known variation can be added. It earns its cost only when real alternatives exist.

05

plugin boundaries

A plugin boundary loads independently implemented behavior through a stable contract while controlling compatibility, authority, lifetime, and failure isolation.

type Quote = { subtotal: number; customer: "standard" | "member" };
type PricingRule = { name: string; applies(quote: Quote): boolean; price(quote: Quote): number };

const memberDiscount: PricingRule = {
  name: "member-discount",
  applies: quote => quote.customer === "member",
  price: quote => quote.subtotal * 0.9,
};

const standardPrice: PricingRule = {
  name: "standard",
  applies: () => true,
  price: quote => quote.subtotal,
};

export function price(quote: Quote, rules = [memberDiscount, standardPrice]): number {
  if (!Number.isFinite(quote.subtotal) || quote.subtotal < 0) throw new RangeError("subtotal");
  const rule = rules.find(candidate => candidate.applies(quote));
  if (!rule) throw new Error("no pricing rule");
  return rule.price(quote);
}

// Pricing owns pricing changes. Notification belongs elsewhere. Add a rule only
// when a real variation exists; one stable conditional can remain a conditional.
console.assert(price({ subtotal: 100, customer: "member" }) === 90);

The first matching rule wins. Putting the always-true standard rule first therefore suppresses every discount. Explain which real variation justifies ordered rules instead of a conditional. SRP separates pricing and notification ownership; it does not require a class for every line. OCP supports the chosen kind of variation, not every future requirement. The example trusts its in-process rules. Untrusted plugins also need permission checks, output validation and failure isolation, which a TypeScript interface cannot supply.
