Coding interview method

A coding interview method is a repeatable collaboration loop: clarify, test examples, establish a correct baseline and invariant, optimize, implement, verify, and reflect.

clarification

Clarification resolves ambiguity with a concrete question or example before assumptions become costly implementation choices.

examples

Examples give concrete inputs and expected outcomes. Include boundary and counterexamples so a rule's limits are visible.

invariants

An invariant is a statement that remains true before and after each relevant step. Saying it aloud makes the algorithm and debugging path easier to verify.

brute force

Brute force enumerates possibilities directly. It supplies a correctness baseline and can be the best choice at small scale.

optimization

Optimization improves a measured objective without violating required behavior. Establish a baseline and verify the improvement under the same workload.

complexity

Complexity describes how resource use or reasoning burden grows. Distinguish algorithmic growth from implementation and operational complexity.

tests

Tests compare actual behavior with an explicit expectation under controlled conditions. A passing test proves only the cases and assumptions it exercises.

Clarify whether the result contains indices or values, whether indices must differ, and whether any valid pair is acceptable. Ask what to return when no pair exists. For this fixture, return two distinct indices or null. Duplicates are allowed. Inputs and relevant arithmetic must stay within the safe-integer contract.

Try every i < j pair as a baseline. This uses O(n²) time and O(1) extra space. For a large input, store prior values in a Map. At j, compute the needed partner, check the Map, then insert the current value. With expected constant-time Map operations, this uses O(n) time and O(n) extra space.

Trace [3, 3] with target 6. At j = 0 the Map is empty; store 3 → 0. At j = 1 the Map contains the needed 3, so return [0, 1]. If insertion came first, the single-element input [3] could incorrectly match itself. This counterexample tests the invariant directly.

The current algorithm returns on the first matching second index. When duplicate values overwrite earlier Map entries, it does not promise the earliest possible first index. A contract that requires a particular pair order needs a different selection rule.

If extra memory must be O(1), revisit the baseline. Sorting and two pointers can reduce time, but mutation and original-index requirements matter. Copying values with their indices uses O(n) space. Do not claim constant extra space merely because the pointer scan uses two variables.

Use minutes 0–4 to clarify the contract and examples, 4–8 for a baseline and invariant, 8–18 for implementation, and 18–25 for tests and changed constraints. These are practice targets, not an employer's scoring policy. If stuck, trace the smallest failing input and identify the first step that violates the invariant.

// Worked rehearsal: find two DISTINCT indices summing to target, or return null.
// Contract for this fixture: safe integers, and all subtraction results remain safe.
// Baseline: check all i < j pairs, O(n²) time and O(1) extra space.
// Improvement: remember earlier values. Before index j, seen contains only i < j.
function pairSum(values, target) {
  const seen = new Map();
  for (let j = 0; j < values.length; j++) {
    const needed = target - values[j];
    if (seen.has(needed)) return [seen.get(needed), j];
    seen.set(values[j], j);
  }
  return null;
}
console.assert(JSON.stringify(pairSum([2, 7, 11], 9)) === "[0,1]");
console.assert(JSON.stringify(pairSum([3, 3], 6)) === "[0,1]");
console.assert(pairSum([3], 6) === null && pairSum([], 6) === null);

Common mistakes

Optimization changes the contract

A sorted answer may lose original indices. State the required output before proposing a different algorithm.

Passing examples replace reasoning

Test duplicates, an empty input, a single element, negatives and no match. Explain the invariant as well as the results.

All-pairs output is [0,1], [0,2], [1,2]. Store every prior index for each value, emit matches before insertion, and count output size k: expected O(n + k) time and O(n) auxiliary storage, plus O(k) if results are collected. For a window, expire indices before lookup and keep only eligible entries; one index per value loses duplicate matches. In a self-review, mark contract, invariant, implementation, tests and tradeoff as demonstrated or needs practice. Correct output alone does not demonstrate all five.

Lookup before insertion preserves distinct indices, so [3,3] succeeds and a single [3] does not. The Map keeps a prior matching index, not necessarily the earliest possible pair under every selection rule. The fixture assumes safe integer subtraction and does not validate arbitrary input. Expected linear time trades for linear storage; clarify mutation and index requirements before proposing sorting.
