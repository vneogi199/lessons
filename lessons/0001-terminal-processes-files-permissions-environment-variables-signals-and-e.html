02 · Mental model

Understand shells, process trees, standard streams, PATH lookup, and OS boundaries.

The shell parses quoting and expansions, selects a builtin or resolves an executable (often through PATH), connects standard input/output/error, and starts the command. A child inherits exported environment values; changing them in the child does not update its parent. Check executable identity, working directory, permissions and stderr before changing application code. On Unix, directory execute permission means search/traversal, not running the directory. Signals are a separate control channel: SIGTERM permits handling and cleanup; SIGKILL cannot be caught. A shell exit status summarizes termination, not whether the intended business work happened.

A pipeline is a relay of bytes, not a relay of success: the receiver can finish normally even when the sender failed.

04 · Detailed term guide

Understand shells, process trees, standard streams, PATH lookup, and OS boundaries.

01

Terminal

A terminal is a text interface that sends commands to a shell and shows the output from programs.

02

processes

A process is a running instance of a program. The operating system gives each process memory, resources, and an identifier.

03

files

A file is a named sequence of bytes stored by a file system. Programs use paths and file descriptors to access files.

04

permissions

Permissions are rules that state which users and processes can read, change, or execute a file or resource.

05

environment variables

Environment variables are named text values that a parent process gives to a child process at startup.

06

signals

A signal is an operating-system notification that asks a process to handle an event such as termination or interruption.

07

exit codes

An exit code is an integer that a process returns when it ends. Zero usually means success, and other values identify failures.

Build diagnostic shell workflows and troubleshoot a broken local service.

Core check: run the read-only pipeline below in a separate Bash process so its shell options do not alter your session. Extension: diagnose a disposable service using its command path, working directory, required environment names (not secret values), stderr and exit status. No service fixture is supplied here.

# Run with Bash, not an arbitrary sh. No files or services are changed.
# Predict: does a successful consumer make a failed producer successful?
set +e
set +o pipefail
bash -c 'exit 7' | tee /dev/null
without_pipefail=$?
set -o pipefail
bash -c 'exit 7' | tee /dev/null
with_pipefail=$?
test "$without_pipefail" -eq 0 || exit 1
test "$with_pipefail" -eq 7 || exit 1
printf 'without pipefail=%s; with pipefail=%s\n' "$without_pipefail" "$with_pipefail"
# Expected: 0 then 7. Capture $? immediately; another command replaces it.
# pipefail returns the RIGHTMOST nonzero status, not necessarily the producer's.
# Senior follow-up: distinguish a signal, process exit, and successful work.
# A zero exit code is only the program's claim; verify the required artifact.
# Never dump the entire environment into a diagnostic log: it can contain secrets.

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace an engineering change from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: What happens if both processes fail?

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: The example reports 0 without pipefail and 7 with it; that alone does not prove business success.
