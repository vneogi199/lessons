04 · Detailed term guide

How they connect: Trace an invocation through environment reuse, initialization, execution, concurrency admission, retries, destinations, and logging.

01

Lambda execution environments

What it means: Lambda admits an invocation to an execution environment, initializes code when needed, runs the handler, and applies event-source-specific retry and concurrency behavior.

02

handlers

What it means: A Lambda handler is the runtime entry point for an invocation. Its input/return contract and effect handling depend on the invoking service or event-source mapping.

03

cold starts

What it means: A cold start includes initialization needed for a new execution environment before useful handler work. Measure it separately from warm execution and distinguish reserved capacity limits from provisioned initialized capacity.

04

concurrency

What it means: Concurrency allows tasks to make overlapping progress. Shared state still needs an explicit ordering or ownership rule.

05

event sources

What it means: Lambda event sources invoke functions directly or through poll-based mappings. Retry, batching, acknowledgement and failure destinations depend on that integration.

06

layers

What it means: Lambda layers package shared dependencies or runtime content for supported deployment types. Version, architecture and runtime compatibility matter; layers do not remove dependency patching responsibilities.

07

failure semantics

What it means: Lambda failure semantics specify how a particular invocation path treats exceptions, timeouts, throttling and partial batches. Synchronous callers, asynchronous delivery and queue mappings do not share one retry contract.

# Python 3.10+. Local batch algorithm; no AWS calls or deployed handler.
# Integration MUST enable ReportBatchItemFailures on the SQS event-source mapping.
def process_batch(event, process_record, *, fifo=False):
    failed = []
    records = event["Records"]
    for index, record in enumerate(records):
        try:
            process_record(record)
        except Exception:
            failed.append({"itemIdentifier": record["messageId"]})
            if fifo:
                failed.extend({"itemIdentifier": rest["messageId"]}
                              for rest in records[index + 1:])
                break
    return {"batchItemFailures": failed}

event = {"Records": [{"messageId": str(i)} for i in range(3)]}
seen = []
def work(record):
    seen.append(record["messageId"])
    if record["messageId"] == "1": raise RuntimeError("fixture failure")

assert process_batch(event, work) == {"batchItemFailures": [{"itemIdentifier": "1"}]}
assert seen == ["0", "1", "2"]
seen.clear()
assert process_batch(event, work, fifo=True) == {"batchItemFailures": [
    {"itemIdentifier": "1"}, {"itemIdentifier": "2"}]}
assert seen == ["0", "1"]
assert process_batch({"Records": []}, work) == {"batchItemFailures": []}
# A deployed handler passes its durable, idempotent record processor here.
# Never acknowledge a batch after handling only Records[0]. A timeout or crash
# can replay successful work too. A separate in-memory "claimed" flag cannot
# prove an external effect completed; bind durable identity to the effect.
# Bound per-record work by remaining invocation time and return unprocessed IDs.
# Retain privacy-safe failure telemetry; this toy collects IDs but does not log.

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace a concurrent task from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Change one identity, Region, quota, or dependency and predict the API and workload outcome.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: AWS API response, resource state, CloudTrail, CloudWatch, quota, cost, and client behavior.
