04 · Detailed term guide

How they connect: Replicate each partition from one leader to followers, track sufficiently caught-up replicas, combine producer acknowledgement with minimum replica policy, elect replacement leaders through cluster metadata, and avoid unsafe recovery claims.

01

Kafka replication

What it means: Kafka replication keeps partition copies on multiple brokers while one leader handles reads and writes for the partition.

02

leaders

What it means: A partition leader receives client operations and defines the ordered log that followers copy.

03

followers

What it means: Followers fetch the leader's records and may become leader after a valid election.

04

in-sync replicas

What it means: In-sync replicas are copies that meet Kafka's configured lag requirements and may participate in durable acknowledgement and safe election.

05

acknowledgements

What it means: Producer acknowledgements define how many replication conditions must be met before a send reports success.

06

min.insync.replicas

What it means: min.insync.replicas is the minimum number of in-sync copies required for writes using all-replica acknowledgement.

07

controllers

What it means: Kafka controllers coordinate cluster metadata, broker state, and partition leadership.

08

elections

What it means: A leader election selects a replica to serve a partition after assignment or failure.

09

failure recovery

What it means: Failure recovery elects leaders, catches replicas up, restarts processing, and verifies durability and consumer progress after faults.

06 · Practical lab

Run a three-broker lab, stop leaders and followers under different acknowledgement settings, inspect ISR changes and elections, and record which acknowledged events survive.

  1. Predict the state changes and one likely failure.
  2. Run the smallest working example and save the result.
  3. Change one condition, then run the same check again.
  4. Compare the evidence and explain the tradeoff.
# Topic durability policy: a leader accepts an all-replicas acknowledgement
# only while at least two in-sync replicas are available.
kafka-configs.sh --bootstrap-server localhost:9092 --alter \
  --entity-type topics --entity-name order-events \
  --add-config min.insync.replicas=2,unclean.leader.election.enable=false

# Producer side must request the matching acknowledgement strength.
acks=all
enable.idempotence=true
delivery.timeout.ms=120000

# Observe ISR shrink and leadership during controlled broker loss.
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic order-events

# replication.factor=3, min.insync.replicas=2, and acks=all tolerate one replica
# loss for writes. If another required replica is unavailable, safe writes fail.

08 · Common mistakes

Memorizing the label

A definition is not enough. Trace a domain command and event from input to output.

Testing only success

The happy path can hide a weak design. Try this failure: Crash leader, producer, and consumer at different boundaries for one keyed event and inspect whether it is lost, repeated, reordered, or delayed.

Changing too much

Change one condition at a time. Otherwise, you will not know what caused the result.

Guessing

Check the system instead: Key and partition, producer ID and sequence, leader/ISR, offset, segment, group assignment, committed position, duplicate effect, lag, and business outcome.
